version: 0.1.15
date: 2026-10-26
headline: devbin ships formula render and publish and a macOS app's release as shared built-ins, a project can name its cargo workspace root, the release pre-flight can require CI green on the base commit, the version line names no path, a Swift gate that ran nothing is refused, a stray byte in a test log can no longer seal an empty run green, and a source commit that changed no vendored file is no longer called an update.
status: released

**Why this release exists.** It carries everything since 0.1.14: issues `0220` to `0235`, and amendments A1 to A4 of the dev, opt and brew contract (`docs/dev-opt-brew.md`), which Molt, Utilz, Intent, devbin and one other tool share for every tool released through Homebrew. Two built-ins move into devbin what each project carried for itself: formula render and publish for a tool released through Homebrew, and a macOS app's sign, notarise and attach. It keeps a 0.1 number, as 0.1.8 to 0.1.14 did, because every consuming project pins a `^0.1` caret.

## Added -- new commands, checks and routes

- **`formula render` and `formula publish` are a shared built-in, in source and assets modes (issue `0227`).** It is opt-in (`commands.formula.enabled`), and `formula.mode` chooses the mode. Both modes fill a template the project keeps, so its own Ruby (desc, caveats, an install layout, a service block) stays its own, and nobody types a tag, a commit or a checksum. Source mode fills `@@TAG@@` and `@@REVISION@@` from git, and refuses a missing or lightweight tag. Assets mode fills `@@VERSION@@` from the tag and each `@@SHA256:<asset>@@` from the release's sums file, read by exact name and never computed from a download, and one of `@@INSTALL@@` or `@@FINISH@@` with an install body devbin generates: the binaries' modes, the contract's manifest under `libexec`, and the links. A cask (`formula.cask`) is rendered from the same release and pushed in the same tap commit. A placeholder left after filling, and a key the mode does not read, are refused by name. `publish` renders the newest release into a temporary clone of the tap, writes nothing in the tree, refuses an uncommitted template, leaves a tap that already carries the render alone, and otherwise names the tap and asks before it pushes, with no `--yes`. devbin's own formula command is retired into the built-in, whose render of the previous release is byte-identical to the retired command's.
- **A macOS app's release is a built-in, `macos` (issue `0226`).** It is opt-in, and a project's own `macos` handler or `run:` still wins. Its subcommands, `doctor`, `store-creds`, `app-sign`, `app-notarize`, `app-verify` and `publish`, sign a staged copy of the app with the Developer ID, notarise it, staple it, verify it, and attach the zipped app at the tag. Off macOS every subcommand refuses before it reads the config or any tool. Credentials stay in the login keychain under the declared prefix, and nothing prints a value. `app-sign` refuses unless HEAD is the release tag of the project's version in a clean tree, stages its copy outside the project, and refuses a staged copy whose bundle id or version is not the release's. `bin/devbin help macos` names the `macos:` keys.
- **`release attach <version> --from <dir>` attaches a directory's files to a release (issue `0226`)**, through the same file checks, upload, sums and read-back as an attach from a workflow run, so there is one way an asset reaches a release. With `release.assets.workflow` declared, it refuses until the run's own attach has finished.
- **`project.cargo_root` names the directory that holds a cargo workspace's `Cargo.toml` (issue `0225`).** devbin runs its catalogue's rust lines there (`fmt rust`, `check clippy`, `test rust`, `check format`'s rust arm and dormancy's legs), and `check targetdir`'s shared tree is that directory's `target`. Absent, it is the project root, as before. A value that is empty, absolute, not a directory, or a directory holding no `Cargo.toml` is refused by `doctor`, and by a cargo line before cargo runs. A project's own `run:` still runs at the project root. A seal records an `at:` line when its run's directory is not the project root.
- **The release pre-flight can require CI green on the base commit before a cut (`release.ci.base`, issue `0223`).** With it on, and `ci.query` declared, the pre-flight asks the query once about the commit the release commit is made on, before any stamp, commit or gate, and refuses anything but green, naming the commit, what the query said and the remedy: push the branch, wait for CI green on it, then cut. A run still going is refused as still running, never as failed, and is not waited on. `release.ci.tag`, on by default, can turn off the ci step's read of the tag's run, for a project whose tag run takes longer than a cut should wait; with both off, a declared `ci.query` is refused as a query nothing asks. devbin's own cut turns `ci.base` on and reads the tag's run after the cut.

## Changed -- a script or a config may get a different result

- **The version line names no path (issue `0230`).** `--version`, `version`, `use`'s report and `doctor` print `devbin <version> (<tree>, <sha12>[+dirty])`, or `(dev, unknown)` where the dev tree's git cannot be read, and `command -v devbin` says where the running copy lives. A reader reads the line up to its closing parenthesis and ignores the rest, so a line in the old shape, with ` at <root>`, still reads as the same identity. `docs/dev-opt-brew.md` T4 says the same (amendment A3).
- **A forward move of the source that changes no vendored file is not called an update (issue `0224`).** doctor's source row says every vendored file is level with the devbin it came from, and that the source's commit has moved on outside them, naming both; the update notice and the offer stay quiet. A forward move that changes a vendored byte is an update, as before, and so is one whose bytes cannot be compared.
- **The switch rests at brew, and a release ends back on the brew install it made (issue `0228`).** `docs/dev-opt-brew.md` carries amendment A1 under T5, and A2 as T4's `+dirty` sentence: a compiled tool's `+dirty` is read over its build inputs, from the build system's dependency record. A released cut of a project whose `formula` command is active ends its report on a note naming `brew upgrade`, `use brew` and the version line to read; it never runs brew and never points a link. doctor notes, and never fails, a link that names dev or opt while Homebrew's devbin is at that tree's version or past it. `docs/releasing.md`'s checklist ends there.
- **`use brew` refuses, removing nothing, when no Homebrew devbin would answer once the link is gone (issue `0235`).** It used to remove `~/.local/bin/devbin` first and only then say that Homebrew had no devbin, which left none on PATH. Now it asks what would answer `devbin` on PATH without the link, leaving out empty and relative entries, and unless that is Homebrew's keg it exits non-zero, naming the link, the tree it serves, why no Homebrew copy would answer (the formula not installed, its keg not linked, Homebrew's bin not on PATH, or another devbin first) and that case's remedy, or staying on dev or opt. `docs/dev-opt-brew.md` carries the rule under T5 as amendment A4, which Molt, Utilz, Intent and one other tool take in their own releases.
- **A cut's `after:` commands are told when the confirm step was answered at its prompt (issue `0227`).** The core hands them `DEVBIN_RELEASE_CONFIRMED`, naming the tag, only then and never under `--yes`, and `formula publish` takes it as the yes for that tag's push and says so. A cut under `--yes` publishes no formula, and its after row says why.

## Fixed -- reaches every project

- **A Swift gate that ran nothing is refused (issue `0229`).** The xcodebuild counter reads XCTest's indented summary, strips swift-testing's leading U+200B before its glyph rules, counts parallel XCTest's lower-case `Test case` lines, and counts a completed test action that named no test as zero, which the gate promotes to FAILED. A build-only run, build-for-testing and a test action whose build failed stay uncounted. `docs/configuration.md` names the usual cause of an empty run: a swift-testing display name handed to `-only-testing`, which matches a type name.
- **A test log holding a byte that is not valid UTF-8 can no longer seal an empty run green (issue `0231`).** macOS awk under a UTF-8 locale stopped at that byte, and the gate read the counter's failure as no count. Every awk over a run log now reads it as bytes, under `LC_ALL=C` set on the command alone, so the gate's own tools keep the person's locale. A counter that exits non-zero is promoted to FAILED, naming awk's status and its first diagnostic line, in the output and the seal, and `--allow-empty` does not cover it. dormancy's INCONCLUSIVE report says the count could not be read.

## Fixed -- devbin's own tree

- **CI's Ubuntu job finds rustup's toolchains again (issue `0222`).** Each arm's own home now carries the runner's `RUSTUP_HOME`, as it carries mix's and hex's, so cargo's rustup proxy on the runner finds its toolchains. Only Linux went red, where cargo is rustup's proxy.
- **The formula built-in's prompt arms skip where `expect` is not installed, as every other prompt arm does (issue `0232`).** They asked for `expect` inside bats' `run`, whose subshell swallowed the skip, so CI's Ubuntu runner, which has no `expect`, ran them on to a failure. No shipped file changed.
- **The read-only arms' fixtures start no background git maintenance with their own commits (issue `0233`).** A fixture's `git commit` started git's automatic maintenance in the background, and a repack it wrote under `.git` after the arm had marked the repository read as devbin writing, so CI's Ubuntu runner failed the `--version` and `doctor` arms now and then. The fixture's commits switch git's automatic maintenance off, and devbin's own git calls keep git's defaults. No shipped file changed.
- **The no-cargo arm hides every cargo on `PATH`, not just the first (issue `0234`).** It shadowed only the directory `command -v cargo` names, through a substitution that could rewrite other entries too, so on a machine with a second cargo, as one with both Homebrew's and rustup's has, the arm still found one and failed. It now rebuilds `PATH` entry by entry and fails by name if a cargo is still found. No shipped file changed.
- **Comments and test titles write no count down, and name what they point at rather than its position (issues `0220`, `0221`).** Each count is deleted rather than corrected, and each positional name now names the field, the function, the test or the thing it meant. The version command's invariants are named. Comments that had become false are made true.

## Known limitations

- **The built-in `macos` has not yet signed or notarised a real app (issue `0226`).** Its arms run against stand-ins for `security`, `codesign`, `xcrun`, `spctl` and `lsregister`, and the first release that uses it proves real signing and notarisation by hand.
- **CI green before the cut proves the base commit on the Tests workflow's summary (issue `0223`).** devbin's base run proves Ubuntu, and the tag's run, which adds macOS and the WSL leg, is read after the cut.
- **On a forward move of the source, doctor's source row, the update notice and the offer compare the vendored set's bytes, which takes far longer than comparing commits (issue `0224`).** The notice asks at most once a day on a terminal.
- **`-only-testing` matches a type name, and devbin does not resolve a swift-testing display name to its type (issue `0229`)**; the empty-run refusal is where such a filter shows.
- **The Homebrew tap is private while devbin's repository is, and the formula's url is `ssh://` (ST0009)**, so `brew install` needs a GitHub ssh key on every machine.
- **ST0008 is not finished, and devbin does not run natively on Windows.** AC-2.1's clause on WSL 2 behind a VPN is not yet measured, and waits on a real Windows machine. AC-6.4, an adopting project running the smoke list on one of its own repositories inside WSL, is not yet received. The WSL leg is a CI runner's WSL 2, not a developer's machine, and the smoke list's server is a stub that writes a marker and sleeps, not a real application server.
- **The smoke list asserts the critic gate on the fixture carrying `intent/` by `check all`'s exit alone (ST0008 WP-06).** The gate is active there by construction, but its own lines stay in the job's `smoke.log` inside WSL and are not readable from CI.
- **A project's name has no shape, so no test holds the vendored set to naming none (issue `0202`)**; review holds it. The domain arm reads only the vendored reference yamls.
- **`text_shown` prints a url whose password holds a raw `/` (issue `0218`)**, a malformed url, as it stands.
- **An interceptor that forges AA is read as the zone's own answer, and the interception probe proves only what reaches TEST-NET-2 (issue `0193`)**, so a path that intercepts only some addresses leaves its replies without AA unexplained, though every read still says what came back.
- **`infra` follows no CNAME (issue `0196`).** A CNAME inside the zone whose target has no record of the type asked reads NOT MEASURED rather than as the absence it is, and for a chain of CNAMEs the line names the first hop, not the end of the chain.
- **Each remote has its own read-back in the push step, so a remote that does not answer holds a cut for over two minutes (issue `0194`)**, and a failure to make the read-back's scratch directory reads as a read-back that waited.
- **Install's line-ending block gives a project's newline-less last line a newline, since the block cannot follow it otherwise, and converts no file already carrying CR bytes (ST0008 WP-01).** doctor names each such file, and the fix is the operator's: `dos2unix`, or `upgrade --force` for a vendored one. Intent writes its own block for its hooks; devbin writes none for it.
- **A Windows shim with no extension, found where the Linux tool is missing, is not modelled by the Windows PATH arms (ST0008 WP-04)**; the runtime runs no such tool, and a missing Linux tool is already reported by `require` and the hints.
- **Some of devbin's own test files still build their fixtures per test (issue `0192`):** `upgradeoffer.bats`'s publish history and `releasecut.bats`'s project and remote carry each test's own directory in committed config, so a copy would not be the state a fresh build gives. Every file builds both caches in `setup_file`, including the ones that never install.
- **`fullcycle.bats`'s slow-y arm reads a charged wait green when the time before the prompt and after the gate passes a few seconds (issue `0199`)**, which load can cause, so on such a run it misses a regression of `0096` rather than reporting a false one.
- **`fullcycle`'s artefact check reads a `release/` it cannot list as holding no binary (issue `0177`).** Where a build tree cannot be listed and neither can its `release/`, the tree's warning and the summary's line for a tree listed while its own `release/` held no binary both say that `release/` holds no binary, which the check cannot know; the warning that it cannot be listed prints beside them. A tree that comes back between the check's tests reads as one it cannot search, or as one behind a link that cannot be followed exactly. Both fail closed, at rc 1.
- **Where git cannot say, whether a repository is there is read from the filesystem, and some cases read otherwise than git would (issues `0179`, `0185`).** A `.git` past a filesystem boundary still counts, where git's discovery stops; so does a `.git` git passes over, an empty `.git` directory or a dangling `.git` link; `GIT_CEILING_DIRECTORIES` is read only to its first newline, so a ceiling listed after one is not honoured; and a bare repository counts as none. With no git on `PATH`, a gate's log directory in a repository gets no ignore file, and the run says git could not say whether it is tracked, with no line from git.
- **`vendor` does not refuse a devbin that is no checkout and has no manifest, so it names no variable there (issue `0178`)**; `upgrade` refuses one, naming `DEVBIN_INSTALL_PREFIX` where the variable placed it.
- **A check `check lint` runs again alone is not always alone, and nothing times a check out (issue `0184`).** A check whose worker was killed can still be running when its file's second run starts; the second runs go one at a time; and a check that never returns holds the gate, in the second run as in the parallel run. The parallel run is still sized by CPUs, never by free memory. A lint gate killed outright leaves its scratch, and its workers finish into it; nothing in devbin kills the gate.
- **The release pre-flight still refuses a `tmp/` committed as a link to a directory outside the tree, and an untracked link on that path inside the tree (issue `0186`).** A `tmp/` that is a submodule passes until `tmp/release/` holds a `.gitignore` of its own, as after a run has written there, and is then refused, with git's `is in submodule` line. `--version` prints the bare commit over a tree whose status answered after skipping a directory it could not open.
- **devbin's own `docs/authoring-commands.md` still recommends `postgresql://user:$PGPASSWORD@host/db`, and arms in `gendoc.bats` and `neutral.bats` plant the shape (issue `0187`)**, so a secret scanner over devbin's own repository can find them; a project that vendors devbin carries only the vendored set, which is clean.
- **A dry run's `no step failed` speaks for the steps it reaches (issue `0181`)**; the NOT REACHED list above it names what it could not predict.
- **`release` leaves out of a url only what it can read as a userinfo (issues `0188`, `0189`).** A url it cannot read that way reaches its refusals and git's words whole, as one holding a raw `/` in its userinfo does where the url has no scheme, where no `:` stands ahead of that `/`, or where the password runs only digits up to it. Where a raw `/` follows a raw @ in the password, the userinfo ends at that @, as git reads it, and the rest of the password reaches them as the host and the path. A `://` anywhere in a url is read as its scheme's, and a secret elsewhere in a url, as in its query, is not looked for. In the scp form an @ in the path's first segment ends the userinfo, and so does an @ in the path of a url whose password holds a raw `/`, so the host, and the path ahead of that @, are left out too. A remote call killed at its bound prints none of what git said and leaves git's words in a file under `TMPDIR`. ssh's refusal names its user.
- **A manifest written before 0.1.9 keeps its recorded path through that project's first upgrade from a runtime older than 0.1.9 (issue `0153`)**, which runs that older runtime and records the path again; the upgrade after it, run by the new runtime, writes the kind of source. Both old forms still resolve meanwhile.
- **A project's own `.gitignore` in a gate's log directory is left as it is, even one that ignores nothing (issue `0157`)**, so that directory can still dirty the tree: where it is `tmp/release` the release pre-flight still refuses, and elsewhere the cut fails at the commit step once a gate writes there. Where git cannot say what a repository tracks, as of one it refuses to read, no ignore file is written and the run says so; one is written only where no `.git` sits at the project root or above it, as far up as git's own discovery looks (issue `0179`).
- **The cargo config order `check targetdir` and `fullcycle` read is cargo 1.99.0's as measured (issue `0164`)**: with both `.cargo/config` and `.cargo/config.toml` in one directory, cargo reads `config`. A build line run from outside the workspace does not read the workspace's config, so `fullcycle`'s offered `build.target-dir = "target"` does not reach it.
- **A `CARGO_TARGET_DIR` that resolves to `/` through `.`, `..` or a link reads "resolves to /, outside the project" rather than "is the filesystem root" (issue `0166`)**, and is refused all the same.
- **`check targetdir` does not see a cargo config inside a directory `find` cannot read at all, or deeper inside one it can search but not list (issue `0163`)**, nor a directory whose ACL denies only search (issue `0145`). A workspace below the project root whose own config pins `target-dir = "target"` fails over an unreadable directory beneath it (at the project root that target is the shared tree, and it passes), since only what the directory hides tells a member from a second workspace; the failure says to make it readable or move it out of the workspace. Where `find` meets a directory it cannot read, `check targetdir` walks a second time.
- **`clean` still never removes `<root>/target` for a nested crate with no root `Cargo.toml` (issue `0167`)**; `check targetdir` does not endorse that tree instead, since removing it would mean running cargo inside `clean`.
- **`fullcycle`'s artefact check does not see a release lost while another was built, the tree's own or a target triple's, and does not read custom profiles (issue `0168`).** A per-session directory built with `CARGO_CACHE_RUSTC_INFO=0`, or under a `build.build-dir` set to another directory, carries no `.rustc_info.json` and is read as a target triple.
- **cargo is asked from each crate's own directory (issue `0150`)**, so a build line that runs cargo from elsewhere, or passes `--target-dir` or `--config` itself, is not followed.
- **The lint arm skips where shellcheck is not installed, and reaches a change only in a run that includes `contract.bats` (issue `0155`).** An explicit empty `senders.*.dkim.type` is now refused, and no test holds that (issue `0161`).
- **A commented key in the reference config with prose directly above and below it reads as prose, so the schema check does not see it (issue `0173`).** None is written that way today.
- **The neutrality tests do not read a citation or a count split across two lines, other than a line ending in "issue" or one opening with an issue-shaped number, nor a line opening with `#` inside a heredoc or a multi-line string, nor a bare four-digit number, nor a count of machines (issue `0172`).** Each would be indistinguishable from innocent text in the tree; the test file declares them.
- **The `MIX_ENV=prod` refusal does not reach a project's own `db` handler (issue `0132`).**
- **The shipped pages are checked for prettier stability only where prettier is installed.**
- **`infra` checks DNS and mail records only.** The Fly runtime and `infra mail dmarc check` are devbin's ST0006, which is not built.
- **Intent and one other project still release with their own orchestrators.** Intent runs devbin's `release check` and `release attach` beside its own.
- **The vendored-set scans fold case in ASCII letters only (issue `0205`)**: under C, GNU grep's `-i` does not fold the dotless i (U+0131) to `i` or the long s (U+017F) to `s`, so a lookalike of a name in those letters would pass the case-insensitive scans. The vendored set holds no byte outside ASCII today, and nothing refuses one.
- **The arm that holds a runtime to one digest under every locale runs where the runner has an en_US UTF-8 locale (issue `0204`)**: on CI's Ubuntu and macOS legs, and not on the WSL 2 leg, which has none and says so in its skip.
- **Assets reach a release after it is published (ST0008 WP-08).** That works while immutable releases are off, as they are on devbin's and Intent's repositories, as measured; a repository that turns them on needs its release object made as a draft first, which the core does not do.
- **`release status` and `release attach` read a release's assets as consistent, not as complete (ST0008 WP-08).** The object row reads `already` when `SHA256SUMS` names exactly the release's other assets and each of its lines equals the digest GitHub reports for that asset, and an attach that reads the same stops there, reading no run. Neither reads the run's artifacts to decide it, so an asset taken off both the release and `SHA256SUMS` is not seen, and running the attach again does not put it back. The attach writes `SHA256SUMS` last, so one that stopped part-way reads `pending`.
- **An attach reads its assets from the run's artifacts, which GitHub keeps for a limited time unless the workflow or the repository says otherwise (ST0008 WP-08).** A release whose attach finished needs no artifact: running the attach again reads `already` however long ago they expired. If the earliest successful run's artifacts expire before its release's attach has finished, the attach cannot finish: it ships that run's files only, so a run started later cannot stand in, and whether a rerun of that run (`gh run rerun <id>`) gives them back is not measured.
- **Each call the attach makes to GitHub is cut off at a fixed bound, and its reads of the release object, its `SHA256SUMS` and the run list at the time its wait has left, never below a floor (ST0008 WP-08)**, so an asset larger than one upload or download can move in that time is out of reach.
- **The earliest successful run is chosen by its creation time (ST0008 WP-08).** A failed run rerun to success keeps its id and, as GitHub's re-run attempts are understood, its creation time, so it can become the earliest after another run's files shipped. An attach that has finished reads no run and stays `already`; one that has not refuses that run's other bytes, never replacing what shipped. Not measured.
- **The release core's reads before the first push are not time-limited**, nor is `release status`.
- **A cut under `object: ci` depends on the project's workflow running.** If CI does not start a job, the tag and the pushes stand and the object step fails at `object_wait`.
