date: 2026-11-26
headline: every notarytool call names the notary profile in the login keychain file, so a cut's notary submit no longer fails when the Mac's screen locks during the cut; `<cmd> all <args>` refuses before any option runs when an option it would run takes no arguments
status: released

**Why this release exists.** It ships one fix that reaches every project with a macOS stage, and one change to how `all` treats arguments. A cut whose screen locked after its pre-flight failed at the notary submit with "No Keychain password item found for profile", though the profile was stored. notarytool kept the profile in the data-protection keychain, and macOS makes that keychain unreadable while the screen is locked. So a cut that ran while nobody used the Mac failed once the display dimmed. A course attendee found that `bin/devbin check all --files <file>` went red at four check options that take no arguments, though nothing was wrong with the project.

## Fixed -- reaches every project

- **Every notarytool call names the notary profile in the login keychain file (issue `I7679181`).** `macos app-notarize`, `macos bin-notarize` and `macos doctor` pass notarytool `--keychain ~/Library/Keychains/login.keychain-db` beside `--keychain-profile`. `macos store-creds` stores the profile in that file. The file stays readable while the screen is locked, as the Developer ID key in it does. So the pre-flight's doctor and the notary submit read the same profile, locked or not.
  - A submit that gets no submission id names the keychain file and notarytool's `Error:` line. It tells you to run `macos doctor`, and to run `macos store-creds` only if doctor reads the profile NOT USABLE. Before, it told you to store the profile again, though it was stored.
  - **Before the next cut with a macOS stage, run `bin/devbin macos store-creds` once on each Mac that cuts.** A profile that an earlier devbin stored is in the data-protection keychain, and this release does not read it. Until you store it again, `macos doctor` reads the profile NOT USABLE and a cut's pre-flight refuses.

## Changed -- a script or a config may get a different result

- **`<cmd> all <args>` refuses before any option runs when an option it would run takes no arguments (issue `If738d64`).** `all` gives each option it runs the same arguments. Before, an option that takes none failed or dropped them: `check all --files x` failed at `check format`, `check toolchain`, `check autotests` and `check targetdir`, and `fmt swift` and `docs agents` ignored them. Now `all` exits 1 with nothing run and no seal written. It names each option that takes none and each that takes them, and you give the arguments to one of those by name, eg `bin/devbin check critic --files x`.
  - devbin's own flags, such as `--purge`, are not arguments here, and `all` with no arguments runs as before.
  - Each clean option takes arguments, so `clean all --dry-run` runs as before.
  - A project's own option takes arguments, as before. A new key, `commands.<cmd>.options.<opt>.takes_args: false`, declares that it takes none, and `all` then refuses arguments and names it. A project's own `run:` line over a built-in option keeps the built-in's default: set `takes_args: true` on it when that line takes arguments.
