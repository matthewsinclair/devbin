version: 0.1.11
date: 2026-10-17
headline: devbin installs with Homebrew, `shell-init` gives bash the same `dvb` as zsh, a project's repository holds devbin's runtime to LF line endings, `infra` measures a DNS record only from its zone's own answer, and a cut's step 8 waits through a read-back that got no answer.
status: released

**Why this release exists.** It carries everything since 0.1.10: the issues `0192` to `0200`, `0192` moved from 0.1.10 and the other eight filed since, every one closed; and the first five work packages of devbin's ST0008, devbin on Windows through WSL 2 with no native port, which are WP-07, WP-02, WP-03, WP-01 and WP-04. It ships what has landed rather than waiting on ST0008's last work packages. Most of it came out of making devbin installable as a package: `0195` gives it a Homebrew formula, `0197` stops a checkout publish fighting that install, and ST0008 makes the runtime hold up under WSL, where git converts line endings, PATH carries Windows directories, and a checkout may sit on a Windows drive. `0193` and `0196` came from another project's report of `infra` reading a VPN tunnel's answers as its zone's. It keeps a 0.1 number, as 0.1.8 to 0.1.10 did, because every consuming project pins a `^0.1` caret.

## Rolling it out -- a one-time effect on every project

- **The first upgrade run by a 0.1.11 runtime writes `.gitattributes` in every project (ST0008 WP-01).** A project's upgrade is run by the runtime it already vendors, so the upgrade that brings 0.1.11 in, run by 0.1.10's, writes nothing there; the next one, run by 0.1.11, adds devbin's line-ending block to the project's root `.gitattributes`, creating the file where there is none. A `fleet` sweep runs a second pass only when a project's provenance is not yet current, so the sweep that rolls 0.1.11 out writes no `.gitattributes`, and the sweep after it, or any later upgrade, does. That sweep's commit pathspec needs `.gitattributes` beside `bin/devbin` and `bin/.devbin/`, or it leaves every project dirty. This is the same two-step the `upgrade` page states for the manifest's kind of source. `fleet`'s own seam scope does not include it, so a sweep does not count it as seam dirt. After that first upgrade, an upgrade keeps the block as written, without a word.

## Added -- new commands, checks and routes

- **devbin installs with Homebrew, from its release tag, on macOS and Linux (issue `0195`).** A formula kept in devbin's tree, `packaging/homebrew/devbin.rb`, fetches the release tag and its commit by git, depends on bash on macOS, runs `bin/devbin install --prefix libexec --managed-by brew` into the keg, links `bin/devbin`, and tests `devbin --version` against the version. It is a template: devbin's own `bin/devbin formula render <tag> <out>` fills its tag and revision from git, refusing a tag or a template it cannot fill and writing nothing, and `bin/devbin formula publish [--tap <url>]` renders the newest release into a fresh clone of the tap, commits it and pushes it, publishing nothing where the tap already carries it. With no `DEVBIN_INSTALL_PREFIX` and no machine pointer, a project finds the machine install at `$HOMEBREW_PREFIX/opt/devbin/libexec`, the path Homebrew keeps across upgrades; a pointer or `DEVBIN_INSTALL_PREFIX` still wins, so a machine set up from a checkout is not moved by installing the formula. For a project vendored from an install, doctor names the install it resolves to and what chose it. devbin's own `install` and `upgrade` refuse to write into a keg, naming `brew upgrade devbin`. A publish records its checkout's whole history as ancestry, so a fresh keg places a project's vendored commit as behind or level. The url is `ssh://` while devbin's repository is private: under Homebrew 7, an scp-like url is refused as no URI, and https fails inside the fetch sandbox, which keeps it from the Keychain. The README's Homebrew section, `docs/releasing.md` and the `install`, `upgrade`, `shell-init`, `doctor` and `formula` pages say how.
- **`shell-init bash` gives bash the same `dvb` as zsh (ST0008 WP-03).** `eval "$(bin/devbin shell-init bash)"` in `~/.bashrc` defines `dvb` as `shell-init zsh` does, both bodies rendered from one source in the subset the two shells share. `--autoload` stays zsh's, and `shell-init bash --autoload` is refused by name. The README, the `shell-init` page and `usage-rules.md` name bash.
- **Under WSL, doctor notes a project on a Windows drive, with the drive, the cause and the fix, and never fails on it (ST0008 WP-04).** A new `location` row, under WSL alone, reads the project root physically and says `location: <root> is on the Windows drive at <drive>, under WSL`, with the cause (WSL reaches the drive through its bridge to Windows, so it is slower, exec bits come from the mount options, and names ignore case) and the fix (clone the project again inside WSL's own filesystem and work there); inside WSL's own filesystem the row passes, and off WSL there is no row. WSL is recognised by its own marks, the `WSLInterop` or `WSLInterop-late` handler or `microsoft` in the kernel release, and `DEVBIN_WSL=1` or `0` overrides the probe, any other value refused before doctor prints a row. `DEVBIN_WSL_MOUNT_ROOT` names an automount root that `wsl.conf` moved from `/mnt`. The `doctor` page has a section on it.
- **The README says what devbin needs on Windows: WSL 2, and nothing native (ST0008 WP-02).** A section at the end of Install names WSL 2 with an Ubuntu LTS, the clone and the work inside WSL's own filesystem, WSL's own git and the packages to install, and Constraints carries a WSL 2 line. Its line on a VPN is WSL's documented behaviour, and says it is not yet measured here.

## Changed -- a script or a config may get a different result

- **A project's repository holds devbin's runtime to LF: install writes a marked block into the project's root `.gitattributes`, upgrade keeps it, and doctor asks git whether it holds (ST0008 WP-01).** A checkout that converts line endings broke a shell runtime with nothing pointing at the cause: git on Windows checks text out CRLF unless the repository says otherwise, a shebang then reads `bash\r`, and every converted vendored file read as edited in place. Now `install` writes one block between `# >>> devbin: line endings >>>` and `# <<< devbin: line endings <<<`, holding `bin/devbin` and `bin/.devbin/**` to `text=auto eol=lf`, keeping the project's own lines byte for byte and appending after them, and fails, naming the file, where it cannot write it. A project's upgrade puts the block back where it is missing or differs, saying so on its own line, and keeps one as written without a word; a run that changed only `.gitattributes` says so, and is not `Already up to date.` A marker that does not make one block is refused by name, with the file left as it was. devbin writes no rule for another tool's files. doctor's new line-endings check asks `git check-attr eol` about `bin/devbin` and every file under `bin/.devbin/`, so a later rule that undoes the block, or a nearer `.gitattributes`, is found, and names each file not held to LF, with the fix; outside a git checkout it is a note. **A vendored file carrying CR bytes now fails doctor by name, `CRLF line endings, not an edit`,** and the manifest check's `edited:` line for it adds `(it carries CR bytes: CRLF line endings, see line endings below)`; a file doctor cannot read is the manifest check's to fail, and the line-endings check notes it as unchecked. devbin's own root `.gitattributes` holds every file in its tree to LF. See Rolling it out for the sweep.
- **On a machine whose install is Homebrew's, a publish from a checkout to `install.prefix` leaves the machine's install as it is and says so, `--point` is the explicit override, and `fleet` sweeps from Homebrew's install (issue `0197`).** After 0195, a publish or publish-upgrade to `install.prefix` wrote the machine pointer, so every project went back to the checkout's install, and `fleet` refused a sweep unless the machine named `install.prefix`, a refusal whose remedy undid the move to Homebrew. Now, where the machine has no pointer and no `DEVBIN_INSTALL_PREFIX`, so that its install is Homebrew's, such a publish writes its files and leaves the pointer unwritten, saying whose install the machine keeps. `--point`, in the publish modes only, makes the checkout's install the machine's; it is refused by name when vendoring, in a project's upgrade, and for a prefix that is not `install.prefix`. On a brew machine `fleet` distributes from the keg's opt path and does not ask for `install.prefix`; on any other it distributes from `install.prefix` and refuses unless the machine names it, as before. The plan names the install and what chose it, as doctor does. A machine that publishes from a checkout behaves as before, and a pointer that cannot be read is never passed over for Homebrew's install. The `install` and `upgrade` pages and `fleet`'s help say so.
- **`infra check` and `infra init` read a record without recursion and measure it only on an authoritative answer: a reply without AA is NOT MEASURED, and says what came back (issue `0193`).** Both took any NOERROR reply as the authoritative server's answer and never read its AA flag, so a VPN tunnel that answered port 53 itself read as 37 ttl drifts, and a cache that matched the profile read as held. Now every record read, MX, the SPF and `_dmarc` TXT, each DKIM record, the wildcard RRsets and the wildcard CNAME, asks dig with `+norecurse`, and a reply without AA is NOT MEASURED, whatever its status, saying `answered without AA: <status>, flags <flags>` in check's row and in init's entry alike. A referral is NOT MEASURED, never an absence, so a DKIM name delegated away from the domain no longer reads as a HALF PAIR; devbin reads each name from the domain's own nameserver and follows no delegation. A run that met a reply without AA asks one question of `198.51.100.1`, in TEST-NET-2, after every domain, and when anything answers there it names the cause once: check prints it as a `Cause:` line under COULD NOT MEASURE, and init records it under `unreviewed:` as `interception`. A dig that cannot ask the question is said in place of a cause, in dig's own words. init abstains on a record read without AA, so a profile proposed through a cache takes no ttl from it. The authority read is unchanged. On a network that does not intercept, a lame or refusing nameserver, or a delegated name, now costs one probe timeout per run, up to `DEVBIN_INFRA_DNS_TIMEOUT` times `DEVBIN_INFRA_DNS_TRIES` seconds, 6 by default; a run whose every reply carries AA pays nothing.
- **A record read answered by a CNAME and no record of the type asked is NOT MEASURED, naming the asked name and the target, never a measured absence (issue `0196`).** So DMARC a provider hosts by CNAME is NOT MEASURED, where it read `NO _dmarc record`, and a DKIM key declared TXT and published as a CNAME is NOT MEASURED, where it read as a HALF PAIR. Every read through the reader gets it, `_dmarc`, a DKIM selector declared TXT, SPF and MX, and it sends no interception probe. A CNAME inside the zone, answered with its target's records, reads as before, and so does the wildcard, whose profile entry declares the zone's own record at `*.<domain>`. init records it under `unreviewed:`, in check's words, and proposes nothing about that facet. Following a CNAME is not built, and the `infra` page says so.
- **Every Homebrew install hint in the vendored runtime also names a Linux route that puts the tool on PATH (ST0008 WP-02).** The seven hints that named Homebrew alone, in `check`, `doctor`, `fmt`, `lib/helpers` and the `repl` page, each name `apt-get install <tool>` beside brew, or, for swift-format alone, which no Ubuntu package puts on PATH, swift.org/install; bash's refusal, for one, now says `brew install bash, or apt-get install bash`. devbin's own two Homebrew-only hints, for jq in `shell-gate` and bats-core in `test`, name apt too, as `apt-get install jq` and `apt-get install bats`.

## Fixed -- reaches every project

- **`shell-init` fills the install path into `dvb` as data, so a path holding `&`, `|`, `\`, `$`, `}` or `'` names exactly that path (issue `0200`).** It put the path into sed's replacement and then, unquoted, into `local prefix=${DEVBIN_INSTALL_PREFIX:-<path>}` in the body every shell evals. So an `&` rendered a wrong path at rc 0 (`/opt/a&b` came out as `/opt/a@@DEVBIN_INSTALL_PREFIX@@b`), a `|` broke the sed, a `\` inside the path was dropped at rc 0 (`/opt/a\b` came out as `/opt/ab`), a `$` was expanded as a variable, unbound under `nounset`, and a `'` was an unterminated quote. Now the body single-quotes the path, any `'` in it closed, escaped and reopened, and bash's own quoted replacement fills it, never sed, so one fill serves zsh, `--autoload` and bash. The emitted `local prefix=` line now carries the path in single quotes.
- **A cut's step 8 waits through a read-back that got no answer, up to the push's own bound, and says such a read as one that could not tell, never as the remote not holding the release (issue `0194`).** The 0.1.10 cut pushed `main` and `v0.1.10` to both remotes and stopped at step 8, `upstream does not hold the release after the push: did not answer within 15s`, while upstream held it; the resume three minutes later read it back as held. Step 8 read each remote back once, within the floor's 15 s, and failed any answer but `already` as the remote not holding the release, at the one point in a cut where the pushes cannot be taken back. Now a read that got no answer, or an ask cut off at its bound, is asked again every 15 s (`DEVBIN_RELEASE_POLL_SECONDS`, never below 1 s), up to the push's own 120 s (`DEVBIN_RELEASE_READBACK_SECONDS`, by default `DEVBIN_RELEASE_CALL_SECONDS`); still unanswered there, the row says `could not read back whether <remote> holds the release after the push, in the <n>s a read-back waits`. The worst case is about 135 s per remote. A remote that answers with a head this checkout does not hold, or a tag that is not this one, fails at once as `could not read back whether <remote> holds the release after the push`, without the wait, since no later ask can clear it, and one that answers without the release still fails at once as `does not hold the release`. `release status`, pre-flight and step 6 read as before. The `release` page says how step 8 waits.
- **No pipeline under `pipefail` lets its reader stop before its writer has finished (ST0008 WP-07, AC-7.1).** A reader that exits early, as `head -1`, `grep -q` and an `awk` or `sed` that quits do, leaves its writer to be killed by SIGPIPE if it is still writing, and under `pipefail` that fails the pipeline, or not, depending on timing. Every such reader in `bin/`, `lib/`, `tests/` and `.github/` now reads a here-string, a variable or a bash match, or carries a comment above it saying why the shape is sound by construction, and a `contract.bats` scan keeps the shape out, red on main at 111 sites before the fix.

## Fixed -- devbin's own tree

- **Every fixture in devbin's own suite is a copy of one real install per file, where each ran the installer (issue `0192`).** `setup_file` runs the real installer once into a read-only cache, and `install_devbin` copies what an install writes, `bin/devbin`, `bin/.devbin/lib/` and the manifest, path, byte and mode, under umask 022 and 002, and writes install's line-ending block into the fixture through install's own writer, never copying a `.gitattributes`; the fixtures that need install's starter config come the same way from one starter install per file. Each cache's sum, taken when it is built, is checked at `teardown_file`, which fails the file by name when a cache moved, is gone, or cannot be summed. The installer still runs per test where it is the subject, and where a fixture has no config yet. The nine profiled files took 26.9% less, 1359.7 s against 993.9 s, run alone under BSD, part of it load; the whole suite ran in 10m16s, against 17m52s and 16m13s for the two suites before it.
- **`targetdir.bats`'s clouded-probe arm runs on a machine with no cargo on PATH (issue `0198`).** It said it needed no cargo and failed without one, since the probe checks for cargo first. A stub cargo first on PATH now fails loudly if run, and the arm asserts the probe looks for cargo and never runs it; its comment says the probe looks for cargo on PATH first, then gives up at the config above TMPDIR before cargo would run.
- **`fullcycle.bats`'s slow-y arm bounds the gate's wall against the run's own length, less half the wait, where it bounded it at 9 s absolute (issue `0199`).** Under the parallel lane's load the phases alone took 14 s, so the arm read red with the wait left out. It now reads green on a slow machine with the wait left out, and red with it charged.
- **The runtime holds with a Windows PATH appended, held by arms (ST0008 WP-04).** `windowspath.bats` runs `help`, `help --why`, `version`, `-v`, doctor, `check all`, `test all`, `shell-init bash` and `dvb`, each required to succeed, with and without a `Program Files (x86)` entry and a `WINDOWS/system32` one, each full of stub `.exe` files that record any run, and compares them; one `clean.bats` arm names an in-tree entry with spaces and parentheses whole and refuses it, and another holds that, with nothing of the tree on PATH, clean proceeds and runs no `.exe`. The runtime needed no change: it splits PATH on colons into arrays used quoted and finds every tool by its exact name, so a `git.exe` cannot answer for `git`.
- **`shellinit.bats` runs every behavioural arm under zsh and bash with `nounset` on, and a missing zsh fails on CI (ST0008 WP-03)**; one arm holds the two bodies to one source.
- **Each test file an ST0008 acceptance-test row cites carries that row's id literally, so `intent at lint ST0008` passes:** `AT-1.1` to `AT-1.3` in `lineendings.bats`, `AT-2.2` in `installhints.bats`, `AT-3.1` in `shellinit.bats`, `AT-4.1` in `windowspath.bats` and `clean.bats`, `AT-4.2` in `doctor.bats`, and `AT-7.1` in `contract.bats`. The vendored set's lister and its shown-lines rule moved to `tests/lib/vendored_set.bash`, shared by `neutral.bats` and the new `installhints.bats`, so the two read one lister.

## Known limitations

- **ST0008 is not finished, and devbin does not run natively on Windows.** WP-05, the suite under uutils' coreutils, and WP-06, a Windows CI leg, are not started. AC-2.1's clause on WSL 2 behind a VPN is not yet measured, and waits on a real Windows machine (Intent's ST0082). No part of this release has run on real WSL: the WSL probe is held only on a fixture's `/proc`, and a container on a WSL 2 kernel reads as WSL.
- **The Homebrew tap does not exist yet, as this note is written (issue `0195`).** Creating it is publishing, and whether it exists and how visible it is are the owner's to decide, so no `after:` step is declared and the README's Homebrew section names the tap as not yet created. The ssh fetch from GitHub was not rehearsed, and neither was Linux's Homebrew, its sandbox, or uutils; the formula was rehearsed on macOS from a local tap against a local clone. Moving a machine onto the brew install means deleting its machine pointer, or writing the opt path into it verbatim, never through a writer that resolves it to the Cellar keg. Ancestry comes from the checkout's history, so a history rewrite at publication would make every older vendored commit read unknown.
- **A first publish to a linked spelling of `install.prefix` is refused `--point` (issue `0197`)**, and no arm runs a `fleet` sweep with `--apply` end to end on a brew machine.
- **An interceptor that forges AA is read as the zone's own answer, and the interception probe proves only what reaches TEST-NET-2 (issue `0193`)**, so a path that intercepts only some addresses leaves its replies without AA unexplained, though every read still says what came back.
- **`infra` follows no CNAME (issue `0196`).** A CNAME inside the zone whose target has no record of the type asked reads NOT MEASURED rather than as the absence it is, and for a chain of CNAMEs the line names the first hop, not the end of the chain.
- **Each remote has its own step 8 read-back, so two remotes that do not answer hold a cut for about 135 s each (issue `0194`)**, and a failure to make the read-back's scratch directory reads as a read-back that waited.
- **Install's line-ending block gives a project's newline-less last line a newline, since the block cannot follow it otherwise, and converts no file already carrying CR bytes (ST0008 WP-01).** doctor names each such file, and the fix is the operator's: `dos2unix`, or `upgrade --force` for a vendored one. Intent writes its own block for its hooks; devbin writes none for it.
- **A Windows shim with no extension, found where the Linux tool is missing, is not modelled by the Windows PATH arms (ST0008 WP-04)**; the runtime runs no such tool, and a missing Linux tool is already reported by `require` and the hints.
- **Two of devbin's own test files still build their fixtures per test (issue `0192`):** `upgradeoffer.bats`'s publish history and `releasecut.bats`'s project and remote carry each test's own directory in committed config, so a copy would not be the state a fresh build gives. Every file builds both caches in `setup_file`, including the ones that never install.
- **`fullcycle.bats`'s slow-y arm reads a charged wait green when the time before the prompt and after the gate passes about 3 s (issue `0199`)**, which load can cause, so on such a run it misses a regression of `0096` rather than reporting a false one.
- **`fullcycle`'s artefact check reads a `release/` it cannot list as holding no binary (issue `0177`).** Where a build tree cannot be listed and neither can its `release/`, the tree's warning and the summary's line for a tree listed while its own `release/` held no binary both say that `release/` holds no binary, which the check cannot know; the warning that it cannot be listed prints beside them. A tree that comes back between the check's tests reads as one it cannot search, or as one behind a link that cannot be followed exactly. Both fail closed, at rc 1.
- **Where git cannot say, whether a repository is there is read from the filesystem, and four cases read otherwise than git would (issues `0179`, `0185`).** A `.git` past a filesystem boundary still counts, where git's discovery stops; so does a `.git` git passes over, an empty `.git` directory or a dangling `.git` link; `GIT_CEILING_DIRECTORIES` is read only to its first newline, so a ceiling listed after one is not honoured; and a bare repository counts as none. So `fleet` reads a root whose only `.git` sits above it, past a filesystem boundary or past a ceiling listed after a newline, as `not its own checkout`, where 0.1.9 said `not a checkout`. With no git on `PATH`, a gate's log directory in a repository gets no ignore file, and the run says git could not say whether it is tracked, with no line from git; 0.1.9 wrote the file there unannounced.
- **`vendor` does not refuse a devbin that is no checkout and has no manifest, so it names no variable there (issue `0178`)**, as in 0.1.9; `upgrade` refuses one, naming `DEVBIN_INSTALL_PREFIX` where the variable placed it.
- **One frozen name freezes two projects where the same path sits under two roots (issue `0182`)**, since both carry one label. 0.1.9 froze by basename, so a bare name froze every project of that name.
- **A check `check lint` runs again alone is not always alone, and nothing times a check out (issue `0184`).** A check whose worker was killed can still be running when its file's second run starts; the second runs go one at a time; and a check that never returns holds the gate, in the second run as in the parallel run. That holds on every xargs now, where on GNU xargs 4.9.0 0.1.9 stopped waiting once a worker was killed by a signal (issue `0180`). The parallel run is still sized by CPUs, never by free memory. A lint gate killed outright leaves its scratch, and its workers finish into it; nothing in devbin kills the gate.
- **The release pre-flight still refuses a `tmp/` committed as a link to a directory outside the tree, as 0.1.9 did, and an untracked link on that path inside the tree (issue `0186`).** A `tmp/` that is a submodule passes until `tmp/release/` holds a `.gitignore` of its own, as after a run has written there, and is then refused, with git's `is in submodule` line, where 0.1.9 said `add tmp/ to .gitignore`. `--version` prints the bare commit over a tree whose status answered after skipping a directory it could not open, as 0.1.9 did.
- **devbin's own `docs/authoring-commands.md` still recommends `postgresql://user:$PGPASSWORD@host/db`, and arms in `gendoc.bats` and `neutral.bats` plant the shape (issue `0187`)**, so a secret scanner over devbin's own repository can find them; a project that vendors devbin carries only the vendored set, which is clean.
- **A dry run's `no step failed` speaks for the steps it reaches (issue `0181`)**; the NOT REACHED list above it names what it could not predict.
- **`release` leaves out of a url only what it can read as a userinfo (issues `0188`, `0189`).** A url it cannot read that way reaches its refusals and git's words whole, as one holding a raw `/` in its userinfo does where the url has no scheme, where no `:` stands ahead of that `/`, or where the password runs only digits up to it. Where a raw `/` follows a raw @ in the password, the userinfo ends at that @, as git reads it, and the rest of the password reaches them as the host and the path. A `://` anywhere in a url is read as its scheme's, and a secret elsewhere in a url, as in its query, is not looked for. In the scp form an @ in the path's first segment ends the userinfo, and so does an @ in the path of a url whose password holds a raw `/`, so the host, and the path ahead of that @, are left out too. A remote call killed at its bound prints none of what git said and leaves git's words in a file under `TMPDIR`. ssh's refusal names its user.
- **No verb writes the machine's install pointer alone (issue `0153`).** A publish to `install.prefix` writes it, and so does the publish-upgrade that rolls this release out; a `fleet` sweep refuses until one has, unless an exported `DEVBIN_INSTALL_PREFIX` names `install.prefix`, in which case it runs and warns that a shell without the variable will not find the install.
- **A manifest written before 0.1.9 keeps its recorded path through that project's first upgrade from a runtime older than 0.1.9 (issue `0153`)**, which runs that older runtime and records the path again; the upgrade after it, run by the new runtime, writes the kind of source, and `fleet upgrade --apply` makes both passes itself. Both old forms still resolve meanwhile. The `upgrade` page now says a second upgrade is needed (issue `0178`).
- **The machine's frozen list for `fleet` is declared nowhere yet (issue `0154`).** devbin's built-in list is empty, so a sweep plans an upgrade for every project the roots reach, archived ones included, until the machine declares `DEVBIN_FLEET_FROZEN`.
- **A project's own `.gitignore` in a gate's log directory is left as it is, even one that ignores nothing (issue `0157`)**, so that directory can still dirty the tree: where it is `tmp/release` the release pre-flight still refuses, and elsewhere the cut fails at step 5 once a gate writes there. Where git cannot say what a repository tracks, as of one it refuses to read, no ignore file is written and the run says so; one is written only where no `.git` sits at the project root or above it, as far up as git's own discovery looks (issue `0179`).
- **The cargo config order `check targetdir` and `fullcycle` read is cargo 1.99.0's as measured (issue `0164`)**: with both `.cargo/config` and `.cargo/config.toml` in one directory, cargo reads `config`. A build line run from outside the workspace does not read the workspace's config, so `fullcycle`'s offered `build.target-dir = "target"` does not reach it.
- **A `CARGO_TARGET_DIR` that resolves to `/` through `.`, `..` or a link reads "resolves to /, outside the project" rather than "is the filesystem root" (issue `0166`)**, and is refused all the same.
- **`check targetdir` does not see a cargo config inside a directory `find` cannot read at all, or deeper inside one it can search but not list (issue `0163`)**, nor a directory whose ACL denies only search, as 0.1.8 already said of every walk (issue `0145`). A workspace below the project root whose own config pins `target-dir = "target"` fails over an unreadable directory beneath it (at the project root that target is the shared tree, and it passes), since only what the directory hides tells a member from a second workspace; the failure says to make it readable or move it out of the workspace. Where `find` meets a directory it cannot read, `check targetdir` walks a second time, about 1.8 times one walk.
- **`clean` still never removes `<root>/target` for a nested crate with no root `Cargo.toml` (issue `0167`)**; `check targetdir` does not endorse that tree instead, since removing it would mean running cargo inside `clean`.
- **`fullcycle`'s artefact check does not see a release lost while another was built, the tree's own or a target triple's, and does not read custom profiles (issue `0168`).** A per-session directory built with `CARGO_CACHE_RUSTC_INFO=0`, or under a `build.build-dir` set to another directory, carries no `.rustc_info.json` and is read as a target triple.
- **cargo is asked from each crate's own directory (issue `0150`)**, so a build line that runs cargo from elsewhere, or passes `--target-dir` or `--config` itself, is not followed.
