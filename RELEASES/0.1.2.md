## Added

- **`release`, opt-in: the release core's declaration, its notes and status verbs, and a cut that tags, pushes and makes the release object (ST0007).** The release core is one release sequence shared by every project that releases. This series carries its catalogue row, its `release:` block and its argument loop. A project enables it with `commands.release.enabled: true`; a `release:` block does not enable it by being present, and `doctor` notes a block in a project that has not enabled `release` as declared and inert. Every key has a default and a block names only what differs (`docs/configuration.md`), and a key the declared mode never reads is refused rather than ignored. `--help` or `-h` anywhere in any invocation prints usage and acts on nothing, and a bare `release` exits 1. `release check` validates the block and prints every key with its value and whether it was declared. `release notes` regenerates the generated notes views, and `release check` also checks them and the project's own note. `release status <version>` reads every step of the sequence from the repository, its remotes and the release object, never from a state file, and prints the table a cut's summary prints: each step `already`, `pending`, `skipped`, `not re-run`, or `UNREADABLE` with the reason, which is never reported as pending. It writes nothing and never fetches, and it exits 1 when any row could not be read. A remote it reads cannot ask for a password, passphrase or host key at the terminal (issue `0088`): git's prompt is off and ssh runs in batch mode, added to the person's own ssh command, so a run at a terminal fails the way an agent's or CI's does rather than waiting. Every `gh` call names its repository: `release.repo` (`OWNER/NAME` or `HOST/OWNER/NAME`), by default read off the remote a release pushes to first, and a repository that cannot be resolved is `UNREADABLE` naming the key, never left to `gh`'s own choice. **A cut runs its first five steps** -- resolve the version, pre-flight, stamp, commit, and the gates on the release commit -- each reading its postcondition first, so running the same target again continues. Pre-flight names every refusal in one run, including a dirty path outside what the release owns, a remote that could not be fast-forwarded, and a tag for the target whose commit does not carry the release, which is never moved. A gate that changes or creates a path fails, naming it. `--dry-run` writes nothing and names what it could not reach. **Then it asks once**, naming the tag, the release commit and everything other machines will see, or takes `--yes`; with no terminal and no `--yes` it stops at exit 2 having tagged and pushed nothing. It makes an annotated tag at the release commit whose message is the note's body, pushes to each remote only what that remote lacks, and makes the release object under `object: local`, titled from `title:`. An existing object whose title or notes differ is named and changed only in a confirmed run, and is never made twice. A resume asks again naming only what is left. Under `object: ci` the core makes no release object: it waits up to `object_wait` for the project's workflow to make one, and fails the step naming it when none appears. `after:` commands run next, each reported. When `ci.query` is declared, the cut asks it about the tagged commit, waiting up to `ci.wait` while it answers `pending` or `none`. The release stands whatever it answers, and anything but `green` exits 1, naming the run and the remedy: fix forward and cut the next patch, never move the tag. Every call to another machine from the first push on is bounded -- each push and each `gh release create` or `edit` at 120 seconds, every read-back and every ask of the query within its wait -- and a call cut off at its bound is stopped with everything it started, so a push, a `gh` call or a query that hangs cannot hold a published release open. A push cut off mid-flight is reported as unknown, for `release status` to read.
- **A project adds its own checks to `doctor` in `bin/.devbin/cmd/doctor.d/` (issue `0093`).** A project could get its checks into `doctor` only by replacing devbin's doctor with a handler, which stopped devbin's own checks running, or by calling `lib/cmd/doctor` by path from that handler, which depends on devbin internals no contract promises. Every executable in `doctor.d/` now runs after devbin's own checks and is counted into the one summary, and `devbin doctor <check>` runs one alone. A line whose first word is `ok`, `FAIL` or `note` counts as devbin's own do, and other output is shown under it. A check fails on a `FAIL` line or on a non-zero exit, and neither hides the other. A file there that is not executable is a note and is not run. A handler at `cmd/doctor` still replaces doctor outright. **The limit:** a check is not time-limited, so one that reaches another machine should bound itself. See `docs/authoring-commands.md`.

## Changed

- **devbin releases itself with the release core (ST0007).** `docs/releasing.md` is now the human steps -- write the note, name the version, move the `devbin_version` constraint if it needs moving -- and `bin/devbin release v<version>`. devbin's `release:` block declares the `releases` notes kind, `object: ci` (its release workflow makes the GitHub release), its repository, and `doctor` as a gate after `check all` and `test all`, so a constraint the new version outgrew fails the release commit before anything is tagged.

- **A gated tool reads no input: its stdin is `/dev/null`, so a gate run from a terminal takes the same path as one run by an agent or CI (issue `0088`).** `run_gate` handed the tool the caller's stdin, so from a terminal the tool had the person's keyboard: a tool that asks, such as mix offering to install Hex, stopped and waited, while every agent and CI run read end-of-input and took the tool's no-answer path. The two measured different things and nothing said so. It covers every gate in every project -- a `run:`, a catalogue command line, devbin's own built-in verbs and every tool they start, such as mix under `check format` -- and a census of the consuming projects' `run:` gates found none that reads input. The gate still says whether a person is at a terminal, through `DEVBIN_GATE_TTY`, so `clean` still asks before it removes. There is no key to hand a gate the terminal; a command that needs one runs without `log:`, as `iex` and servers already do.
- **`fullcycle`'s test phase is `test all`, so every test option a project declares runs in a full cycle (issue `0083`).** It ran `test rust` alone: a project's other declared test options never ran in a full cycle, and nothing a project declared could change that without editing a vendored file. `fullcycle` and `test all` now run the same tests. An option marked `in_all: false` is kept out of both and reported as skipped, and a `test` handler that declares no options receives `all` from the cycle, as it does from `test all`. A project that declares only `rust` runs exactly what `test rust` ran. When `all` runs a project's options, a failure exits 1, so a cycle whose tests fail finishes `rc=1` where `test rust` passed cargo's own code through, and a test phase that `in_all: false` leaves empty refuses a verdict and stops the cycle red. The refusal for a project with no build command lists the rest of the cycle from the phase list, where it named `test rust` itself. `README.md`, `docs/configuration.md` and `docs/authoring-commands.md` said `all` is synthesised for a command with more than one option; it is synthesised for any command with at least one, and they say so.

## Fixed

- **`devbin test bats` runs the paths and flags it is given (issue `0092`).** devbin's own test handler ran `bats tests/unit` whatever followed it, so `test bats <paths>` and `test bats --filter <re>` ran the whole suite and dropped the rest without a word. The handler now passes its paths and flags to bats, runs `tests/unit` only when it is given no path, and takes `--purge`, `--purge-only` and `--allow-empty` for the gate, as every other gate does. It tells a flag's value from a path by a list of the bats flags that take one, and a test holds that list to the installed bats's own `--help`, so a flag bats adds is caught rather than taken for a path. `commands.test.options.bats` in devbin's config carried a `run:`, `grammar:` and `log:` that the handler meant were never read; they are gone, and `help/test.md` names the seal the handler makes, `.bats.out`.

- **The BEHIND-you warning fires when the source is a machine install (issue `0059`).** `upgrade` warns before it writes when its source is behind what a project vendored, because it syncs unconditionally and a downgrade otherwise prints `updated` per file and leaves doctor green. It placed the two commits with `git merge-base` in the source, and an install has no git history, so for every project vendoring from an install -- every consuming project since the 0.1.1 sweep -- the answer was `unknown`, and `unknown` is silent. A publish now runs that question in the checkout it publishes from: the install's manifest carries an `ancestry` line for every commit it has held, placed against the commit it holds now and recomputed on every publish, so a rewind is still seen however many publishes later. `upgrade` and `vendor` look a project's recorded commit up in that table. A commit the install never held stays `unknown` rather than being guessed -- and `unknown` is no longer silent: when the direction cannot be established and a vendored byte would change, `upgrade` says it cannot tell whether the source is ahead or behind. A record carrying `+dirty` now reads `unknown`, as `vendor`'s help always said; it read `same` against a source holding the commit the dirty bytes started from. The warning's `upgrading to:` line names the install's commit instead of `unknown`. **Two limits:** the table begins at the first publish made by a devbin carrying it, and a publish from a checkout rewound to before this fix writes no table.
- **The update notice, the upgrade offer and doctor say which way the source moved, and offer an upgrade only when it moved forward (issue `0079`).** All three compared two commits for equality and called any difference "behind", so a project AHEAD of a rewound install or an older checkout was told "An update to devbin is available", and answering yes ran the upgrade that reverts it. `upgrade`'s own BEHIND warning (`0059`) came after the choice was made. They now read the direction `upgrade` and `vendor` read, which moved from `lib/install` to `lib/helpers` so the launcher can reach it before it offers. **Forward** is an update, as before. **Behind** is reported as the source being BEHIND this project, and upgrading is never suggested. **A difference in no known direction** -- a commit the install never held, or a source on another history -- is reported as a difference, not an update, and is never offered. A record carrying `+dirty` at the source's own commit no longer reads level, and a record too short to name a commit is no longer compared. The README's notice example named `bin/devbin devbin upgrade`, which is not a command; it names `bin/devbin upgrade`.
- **The `fleet` census says whether each project's seam is committed, and a scan that could not read everything fails and names what it missed (issue `0056`).** `fleet audit` and `fleet doc` read manifests off disk and never asked git, so a re-vendor nobody committed read as level; four projects were found in that state, none by the census. A `Seam committed` column now reports, per project, whether `bin/devbin`, `bin/.devbin/lib` and the manifest match that checkout's HEAD: `committed`, `DIRTY`, `not watched` (a seam file marked assume-unchanged or skip-worktree), `not tracked` (an ignored file under the seam, or a symlink, whose target git never reads), `not a checkout`, `not its own checkout` or `UNREADABLE`. It reports and never judges, so a frozen project that is dirty on purpose does not stop `doc`. Git is asked with untracked and ignored files listed, submodule ignore settings overridden, the repository's `core.fsmonitor` hook and untracked cache turned off, and every one of git's local environment variables cleared; settings outside those, such as a global excludes file, still apply. It says only what it measures: nothing about whether that commit is pushed. **The same question now answers the provenance stamp `install` writes and the publish gate in front of it**: the stamp asked a plain `git status` and could record a clean commit over bytes the census called DIRTY, and a publish now also refuses when devbin's half carries an ignored file, a symlink or a file git was told not to watch, naming it as `seam: <state>`. **Separately, a scan could come up short and exit 0**: a root `find` could not read in full ended the scan early, silently. Now any root not read in full, any manifest that cannot be read, any seam with no launcher or no lib to digest, and any project git cannot answer for is named on stderr, carried in its row as `UNREADABLE`, and makes `audit` exit non-zero; `doc` and `fleet upgrade` refuse to proceed. The prune list (`.git`, `_build`, `node_modules` and the rest) is now a real prune, so a build churning under `_build` does not fail a scan.
- **`doctor` fails on a yes-or-no key holding any other word, naming it (issue `0080`).** `commands.<cmd>.enabled`, `commands.<cmd>.options.<opt>.enabled` and `.in_all`, and `options.<name>.flag` are read through the true and false words, and nothing checked that a value was one of them: `enabled: off` is neither, so a built-in stayed active and an opt-in stayed off. `doctor` now names the key, the value and the six words it accepts, read from the same lists the readers use, and a test holds every boolean reader in `lib/` to the validator's one list of those keys. `log:` and `options.<name>.value` take other words and are not checked. **The limit:** as with a misspelled key, only `doctor` validates. The command you run still reads `enabled: off` without a word.
- **devbin's true and false words, and its `-` sentinel, are read by one predicate each (issue `0066`).** `true`/`yes`/`1`, `false`/`no`/`0` and `-` were spelled out at thirteen sites across `lib/resolve`, `lib/runlog` and `lib/builtins`, and nothing held them in step -- 0065 was one of those copies diverging. They are now word lists read by `is_true_word`, `is_false_word` and `is_no_default` in `lib/helpers`. A test searches `lib/`, `bin/devbin` and `bin/.devbin/cmd` for any list of two of those words joined by `|`, in any order or quoting, and for `-` compared or used as a case alternative, and fails on a hit outside `lib/helpers`; it does not search for a single-word comparison such as `= true`. Another test holds the `log:` decline spellings stated in `docs/configuration.md` and `lib/config.reference.yaml` to the lists. `lib/builtins` now refuses to load without `lib/helpers`, where a missing predicate read its own `-` wrongly and silently. **`grammar: "-"` now means the generic grammar** at option and command level, through one resolver, `gate_grammar`, as it always did for the catalogue's own `-`; a project writing it was told `unknown grammar '-'`. **`server --iex` reads `yes` and `1` as true**, where a project declaring `options.iex.value: yes` got the plain command line.
- **A config value can no longer name one of the variables devbin exports to its handlers (issue `0081`).** `project.root_var` and `options.<name>.export` are refused when they name a variable of devbin's own, and that list had fallen behind what the dispatcher exports: `root_var: DEVBIN_RUN_ID` put the project root in place of the run id at exit 0, and so did `DEVBIN_RUN_STAMP`, `DEVBIN_RUN_REFERENT` and `DEVBIN_CLI_TASK`; a `root_var` naming `DEVBIN_LANGUAGES` or `DEVBIN_FMT_ARMS` got devbin's value in place of the project root, and an option exporting into any of the six put its own value there. Those six and the `DEVBIN_ACTIVE_*` family are now refused, naming the value, and a test holds the list to every name devbin adds to the environment of a project handler, an option's `run:`, alone and under `all`, and a `notes.run` command, so an export added on any of those paths without joining the list fails it. `DEVBIN_TREEINDEX_DIRS`, which devbin stopped exporting with `0032`, is no longer refused. **The limit:** names devbin reads but does not export, such as `RUNLOG_KEEP_RUNS`, are not reserved, since an option exporting into one is a way to set it.
- **A file that is a symbolic link is written through, and the link survives (issue `0084`).** Every writer that replaces a file through a temporary renamed the temporary over the path it was given, so a link became a regular file holding the edit, the file it named kept its old content, and the command exited 0. `version set` wrote a linked `VERSION` through its link and left a linked `Cargo.toml`, `package.json` or `mix.exs` target at the old version, after which `version check` agreed with the copies; `release notes`, dating a note, `generated_doc_write` and `fleet doc` did the same to a linked view, note or document, and `fleet doc`, which staged its document in TMPDIR, also left that document 0600 on every run. The chain of links is now followed to the file at its end, which is replaced beside itself and keeps its mode, and every link stays a link. A link that leads to no file, dangling or in a loop, is refused naming it. Writing through a link to a file in a directory that cannot be written is refused, naming that file, where it replaced the link with a regular file at exit 0. For a project's own handlers, `lib/helpers` gains `follow_links`, and `rename_staged` for a caller that stages two files before renaming either. **Two limits:** a hard link is still split by the rename, as it always was, and `install` and `upgrade` still replace a vendored file that is a link with a regular file, leaving the file it named as it was.
- **Every `run:` word is a glob pattern, devbin says so, and a `run:` with no words in it is refused naming its key (issue `0082`).** A declared command line was expanded unquoted at eight sites -- an option's `run:` bare and under a gate, a command's exec'd and under a gate, `commands.fullcycle.restore`, `release.notes.run`, and the two that run devbin's own catalogue lines -- so how a command line becomes words was stated eight times, each reading the caller's `IFS` and whatever glob options the process happened to have. Every word was also a glob pattern matched in the directory the command runs from, which no document said: `run: bats opt/*/test` hands `bats` one directory per match, and the same config runs a different command line when the files there change. **The globbing is KEPT and documented**, after a census of all 30 installs read every `run:`, `restore:` and `notes.run` value with devbin's own parser and found exactly one word across them that globs, Utilz's, matching 16 directories, and no value anywhere that a refusal would break. The eight sites now ask one helper, `run_words` in `lib/helpers`: it splits on spaces, tabs and newlines whatever the caller's `IFS`, matches each word where the command runs, passes a word matching nothing through as written, never `eval`s, and pins the glob options for the split alone, so an inherited `SHELLOPTS=noglob` or `BASHOPTS=nullglob:dotglob` cannot quietly change what a declared line runs. **A `run:` of nothing but spaces used to run the arguments typed after the command AS the command, at exit 0 and with no message**, at option and command level alike; it is now refused, naming the key, at the site and in `doctor`'s validation. **`run: ""` is refused too**, where it fell through to devbin's own catalogue line and ran that instead -- every other reader in devbin already treats a declared key as declared. `docs/configuration.md`, `README.md`, `docs/migration.md`, `usage-rules.md` and `lib/config.reference.yaml` all say what a word is. **The limit:** `GLOBIGNORE` and `GLOBSORT` are not pinned, because both arrive from the environment inert and a `local GLOBIGNORE` would ACTIVATE an inherited one as it left scope; a test holds devbin to assigning neither.
- **A sealed gate now records where its command line came from, at every one of the six places devbin opens one (issue `0085`).** `run_gate --source` is what puts the `from:` line in a seal, and `note_invocation` prints that line only when it is non-empty -- so five of the six callers wrote a seal that named the argv devbin ran and nothing about where that line was declared. Since `0082` the argv holds the RESULT of the glob matching, which means the declared line could not be recovered by reading it either. The one that already named its source was an option's `run:`; a command's `run:`, the catalogue's own command line, a catalogue option implemented by a devbin function, `fullcycle` and devbin's own test handler all said nothing. Each now names what it is: a config key in the same sentence for the two declared sites, the catalogue row for the catalogue's line, and the function for the three that run devbin's own code, where there is no command line to go looking for. **The comment above the command-level gate asserted that it "seals on exactly the terms an option-level one does"** and it did not; `0082` had widened the difference by making the one source line that existed say more. A test compares the two seals with their keys removed, and another holds every `run_gate` call in `lib/` and `bin/` to carrying a source -- which is what found the sixth site, a project handler the census had read past.
- **A replace of a read-only file no longer stops dead on a terminal prompt, so `test all` from a terminal finishes (issue `0086`).** `rename_staged` renamed its temporary over the file with a bare `mv`, and POSIX `mv` prompts when the destination exists, permissions do not allow writing it, and standard input is a tty -- which is exactly a replace of a read-only file, the case `stage_beside` goes to the most trouble to support. `bin/devbin test all` run from a terminal reached the arm that replaces a `chmod 444` file, printed nothing further, and waited **8h13m** until it was interrupted. `mv` is now `mv -f`, as `lib/install` already wrote for its own rename; those are the only two `mv` calls in the runtime. **The reach is wider than the suite**: `replace_file` and `sed_inplace` are how devbin rewrites a file whose mode it does not own -- the version stamp, a dated note, a generated view, the `fleet` census document -- so any of those replacing a read-only file from a terminal blocked the same way. **Why it was never seen: the prompt is tty-gated and nothing that normally runs the suite has a tty**, so every agent run and both CI jobs passed, including the run that reported 1372 ok. A test holds the runtime's `mv` lines to exactly those two, byte for byte: any other line naming `mv` in `lib/` or `bin/` fails it, and so does either known line disappearing. It is an allowlist because two rules about flags were each beaten by spellings they did not read (a second `mv` after `;`, an `-i` on a continuation line, a quoted `'-n'`). **The limit, declared:** the arm reads text, because a bats run has no tty and so no arm here can watch the prompt appear. It cannot see an `mv` behind a variable, an alias or a function of another name, or one spelled so its text does not read `mv`, and it does not scan `tests/`, where nineteen bare `mv` calls each move a file the test just created and can write. A test that moved over a read-only fixture would hang the suite identically and the arm would not see it.
- **`--purge`, `--purge-only` and `--allow-empty` work at a command-level gate, and are no longer handed to the tool as arguments (issue `0087`).** A command with its own `run:` and `log:` is a sealed gate like an option, but it forwarded its argv whole: `devbin <cmd> --purge` ran the tool with `--purge` on its command line and purged nothing, and `--allow-empty` -- the per-invocation "this emptiness is intended" override -- reached the tool instead of the gate, so the gate still failed. No warning either way. The option-level and catalogue gates already split these flags out through one parser, whose own comment said it served "both" gate sites; the command-level gate was a third, added later. It now takes the same path, and the sites are held by an arm that refuses any gate forwarding a raw argv rather than by a comment that counts them.
- **`fullcycle` asks a person at a terminal before it removes the build trees: once, after showing what goes (issue `0089`).** Without `--force` it refused with `no tty` every time, at a terminal too. Each phase got the rest of the phase list on its stdin, and since `0088` a phase's own gate reports that nobody is there. It now shows what the clean phase would remove, asks on the terminal, and on a y runs the cycle. An n stops it before anything is removed. With nobody to ask it refuses and says to pass `--force`. `clean` and `fullcycle` ask through one helper, so the rule for whether a person is there is written once. The `--dry-run` preview names the question, and its clean phase is `clean rust --force-blocked --force` with or without `--force`, because that is what runs after a y.

## Known limitations

- **Utilz, another project and Intent still release with their own orchestrators.** They adopt the release core in that order, after this release (ST0007 WP-08).
- **The release core's reads before the first push are not time-limited**, nor is `release status`: a remote that hangs there holds the run, but nothing has been published and nothing is written.
- **A cut under `object: ci` depends on the project's workflow running.** If CI does not start a job, the tag and the pushes stand and the object step fails at `object_wait`; the workflow's run for the tag has to be re-run before the cut can finish.
