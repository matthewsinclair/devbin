version: 0.1.8
date: 2026-09-26
headline: Help for every built-in reaches every project, exit 2 is left to an unknown or inactive command, and `db all`, `clean` and `upgrade` stop removing what they should keep.
status: released

**Why this release exists.** It is the stable release that draws a line under devbin. Everything open goes into it, rather than a release for each fix, and every open issue closes before it is cut, with nothing cut short for time. So it closes every issue filed since 0.1.7, `0113` to `0150`; fourteen of them were found while devbin's help pages were being written or checked against the code, claim by claim. It keeps a 0.1 number because every consuming project pins `^0.1.0` or `^0.1.1`, and 1.0.0 would fail that caret.

## Changed -- a script or a config may get a different result

- **A bare `bin/devbin shell-init` exits 1, not 2, and prints its usage on stderr (issue `0119`).** Naming no shell is a usage error, and 2 is the code the contract keeps for an unknown or inactive command, which `shell-init` is not. The usage moved to stderr because a shell rc evals this command's stdout and the usage carries runnable examples, so an eval of the bare command now evaluates nothing. `-h` still prints the usage on stdout and exits 0.
- **`infra check` and `infra init` exit 1, not 2, when something could not be measured (issue `0126`).** In a project where infra is inactive, `bin/devbin infra check` also exits 2, so a caller could not tell "infra is not set up here" from "a DNS read failed". Drift and an unmeasured domain now both exit 1, and the report ranks them, printing COULD NOT MEASURE above any drift, so a script that told the two apart by the code must read the report. When this was measured, nothing in any consuming project read the 2: no workflow or script invokes infra, and the one infra user outside devbin documents only zero against non-zero.
- **`bin/devbin release` exits 1, not 2, when nobody is at a terminal to confirm and `--yes` was not given (issue `0130`).** 2 is the dispatcher's code for an unknown or inactive command, so a script could not tell a cut that stopped for want of a person from a release that is not enabled here. Exit 1 is what `fullcycle` and `clean` already do; step 6's row says which refusal it was, "declined at the prompt" or "nobody to ask". This supersedes the exit 2 of ST0007's AC-5.3.
- **`version set`, `version bump` and `version sync` are refused, exit 4, from outside the project they would write (issue `0124`).** The wrong-tree guard exempted `version` whatever followed it, so `<project>/bin/devbin version bump patch` typed in another directory rewrote that project's VERSION at exit 0, and `dvb`, which falls back to `$DEVBIN_SOURCE` when it finds no project, bumped whichever tree that names. Only the forms that write nothing are exempt now: `version` alone, `show`, `check` and its help, and `-v` and `--version`.
- **`infra` refuses a `$DEVBIN_INFRA_PROFILE` that names a missing file, and `infra profiles` refuses a profile that does not validate (issue `0121`).** A typo in the variable fell through to `<project root>/infra.yaml` and checked a different profile without a word, while the same file named with `--profile` was refused. `infra profiles` said it validated every profile and only loaded them, so one that `show` and `check` would refuse passed; it now prints what validation says under each file and stops at the first that fails. Three smaller fixes ride with it: a profile with no `name:` shows as `(unnamed)`, as the reference promises; `infra mail dmarc --help` calls `check` planned instead of offering a verb that does not exist; and `infra --help` names the reference where it really is, which was wrong in devbin's own checkout.
- **`db all` leaves `reset` out, and `MIX_ENV=prod` is refused before any `db` line runs, whoever supplies it (issue `0132`).** `db all` ran setup, migrate, reset and seed, then reported that all db options passed, and reset is `mix ecto.reset`, which drops the database. `reset` now ships outside `all`: `db reset` by name still runs, `in_all: true` on it brings it back, and every `db all` names it as skipped. The production refusal sat where only devbin's own lines reached it, so an override such as `setup.run: mix ash.setup` ran under `MIX_ENV=prod` and sealed at exit 0; now only a project `db` handler, a file or one mapped with `commands.db.handler`, gets past it. A mistyped option of any built-in gate command is told the options offered and `help <cmd>`, where `db migrat` was told to try `db all`.
- **`install --into <project> --force` removes the files devbin stopped shipping, edited or not, and names each one (issue `0129`).** It copied devbin's half back, deleted nothing, and dropped the retired file from the manifest, after which no `upgrade` could reach it: a retired `lib/cmd/<name>` handler went on answering its name. A re-vendor now retires each file the previous manifest recorded that the source no longer ships, including an edited one, since `--force` already copies over edits; a plain `upgrade` still hands an edited file back to the project instead. A file no manifest recorded is left in place, since it may be the project's own, and nothing outside `bin/.devbin/lib/` is touched.
- **Whether a project owns a command is decided in one place, and `all` is refused over a command-level `run:` with no option to run (issue `0128`).** A `run:` line now owns its command as a handler does, so `clean all` no longer runs devbin's own removal where `commands.clean.run` replaced it. `all` sweeps where there are options, is handed to `server`, `iex`, `cli` and `repl` and to a project handler with no declared options, and over a `run:` with no option to run is refused at exit 1, naming the bare command: handed `all`, `commands.test.run: cargo test` ran no test and exited 0 over a failing suite. The same holds when `all` or an option name follows devbin's gate flags, as in `test --purge all`. `--iex` no longer counts over a `run:` line unless `options.iex.commands` names it, and `help --why`, `doctor` and `check format` read the same answer the dispatcher acts on. When this was measured, no consuming project's behaviour changed: four commands across them are owned by a `run:` line, and none declares options.
- **`doctor` fails a `log:` key that nothing reads, and names what runs instead (issue `0133`).** `log:` acts beside an option's own `run:` and on a command whose own line runs; anywhere else a handler runs the command and seals as it seals, and the key validated and did nothing. `check.md` and `test.md` said `log: false` alone ran a shipped option unsealed, and now say where it is read. When this was measured, all 60 `log:` keys across the 17 consuming projects were read, so none turns red.

- **An infra profile key devbin has no field for is refused before anything is read, and so is a config key indented under a key that already has a value (issue `0143`).** Such keys parsed, validated and went unread, which is how a profile's `dmarc.sp`, a second DKIM record and a wildcard all printed "0 drift" at exit 0 before 0.1.8 could read them. `infra check` now names the key, the file and whether the key exists elsewhere, and asks no nameserver. The nesting refusal is in devbin's config parser, so it reaches every devbin config; when this was measured, all 23 config files across the consuming projects passed, and every profile among them reads as it did.

## Fixed -- reaches every project

- **`bin/devbin help <command>` answers with devbin's own page for all 28 built-ins, in every project (issues `0113` and `0115`).** The pages lived in devbin's own `bin/.devbin/help/`, which no install writes, so on 0.1.7 a consuming project got the generated stub for a built-in, telling it to write devbin's page itself (216 of 289 probes across 17 projects), and 13 of the 28 had no page anywhere, which 0.1.7's note missed: its test counted only the commands active in devbin's own tree. The pages now ship in devbin's runtime, at `bin/.devbin/lib/pages/` in a consuming project, each rewritten to be true wherever devbin's implementation runs and checked claim by claim against the code. A project's own page in `bin/.devbin/help/` is still read first and printed whole; devbin's page answers only where the project does not own the command, followed by `In this project:`, which says how the command resolves there, which options are offered, and why any others are not.
- **The `release` page no longer lists an exit 3 or says a dry run writes nothing (issue `0118`).** No step of a cut returns 3: a failing gate, a failing `after:` command and a CI verdict other than green all stop at 1. A dry run makes no release and writes no `tmp/release/` log of its own, but it runs the gates for real and they seal their logs under `tmp/`. The page also adds three things it left out: pre-flight's refusal of a tree where `tmp/` is not ignored, step 3's `derived:` commands, and where step 8 pushes when no `remotes:` are declared.
- **`help --why`, `doctor` and the refusal agree when devbin's handler for a built-in is missing from an install (issue `0117`).** With `lib/cmd/version` removed, `bin/devbin version` said devbin's handler was missing while `help --why` said the catalogue ran it: the disagreement 0.1.7's note said could not happen again, one case over. `help --why` now gives the refusal's own reason, and `doctor` no longer counts such a command as runnable.
- **Four refusals and notes name the true cause (issue `0136`).** A command whose options config had all switched off was told it was not enabled, or to declare a language the project already declares; it is now told which options are switched off. `doctor` no longer reports a project's `commands.precommit.run` as shadowing the built-in, since devbin ships nothing behind that name to shadow. A file at `bin/.devbin/cmd/<name>` without its executable bit is named as one, with the `chmod +x`, where the refusal told the project to add the file it already had; and `help` shows devbin's summary beside a declared `--iex` that has none of its own.
- **`doctor` finishes its list when the config fails validation (issue `0120`).** A config that parses but fails validation, such as one with an unknown key, ended doctor at the config check: exit 1 after three checks, the rest never run and no count printed, so the exit code was right and nothing said that the other checks were never reached. The config check is now one FAIL naming each problem, and every later check runs and is counted. A config that does not parse at all is still refused by `bin/devbin` itself, naming the line, before doctor starts.
- **`clean` stops listing trees it must not remove -- one outside the project, a source directory, another tool's cache -- stops reporting as skipped a tree it removes, writes nothing on a dry run, and exits 1 over a scan it could not read in full (issues `0131`, `0137` and `0141`).** A sibling such as `target.bak` no longer splits a build tree into skipped trees of its own, and nothing `clean` runs is found through PATH.
- **`fullcycle --dry-run` stops running the project's build, and a cycle no longer removes the build trees before a build or test phase that cannot run (issue `0134`).** The cycle probed its build with `bin/devbin build --help`, and a `commands.build.run` line takes `--help` as one more argument, so a script that ignored it built under "DRY RUN -- nothing below is executed". Each phase is now worked out from devbin's own answers without running anything: `<command> all` where there are options to sweep, the bare command over a lone `run:` line, and a refusal, before anything is shown, asked or removed, where the phase would run nothing -- a line with no words, a handler that does not resolve, or options all kept out of `all`, each named. The PATH watch follows each link to where it resolves, so a relative link into the build tree is watched, and every question devbin asks takes `y` or `yes` in any case.
- **`dormancy` counts a suite that runs nothing by default instead of calling it INCONCLUSIVE, puts `--all-features` where cargo reads it, and refuses up front when `test rust` will not run the line it prints (issue `0135`).** It now runs the line `test rust` runs here, as the dispatcher answers it, and refuses before either leg, in the dispatcher's words, when that is not a cargo test line of `test rust`'s own: a project handler, a command-level `run:`, `test` switched off, a line with no words, a line declared unsealed, or a config that is missing or will not load. Each leg is sealed as `test rust` is and is a run of its own, and a project declaring rust beside another language is measured, which it never was.
- **On a disk that folds case, `upgrade`, `install --force` and publishing keep a file devbin renamed only in case (issue `0140`).** On APFS as macOS formats it, `Foo` renamed to `foo` is one file, and each removal compared paths byte for byte: `upgrade` printed `updated .../foo`, then removed `Foo` as no longer shipped, taking the file it had just updated, at exit 0, and an edit to the file was overwritten without the edited-in-place refusal. Each now recognises a path that is, on this disk, a shipped file under another spelling, renames it to the shipped spelling and says so, and `upgrade` refuses an edit to it as an edit. On a case-sensitive disk, where the two are two files, the old spelling is retired as before.
- **Publishing the machine install removes what devbin stopped shipping (issue `0123`).** Publish copied every shipped file into the install and deleted nothing, and every consuming project vendors from the install, so a file devbin stopped shipping would stay in every one of them as devbin-owned, where `upgrade` could never retire it. Publish now removes what the install holds under `bin/.devbin/lib/` that the source no longer ships, prunes the directories that leaves empty, and names each removal. When this was found, no file devbin had stopped shipping was waiting in the install, so nothing was exposed yet.
- **`install --into` and `upgrade --from` refuse a source they cannot read in full, and `doctor` fails when it cannot list `bin/.devbin/lib/` (issue `0127`).** devbin's list of vendored files came from a find whose errors were thrown away and whose status nobody read, so a directory find could not read listed as empty: `install --into` from such a source vendored 45 of its 60 files at exit 0, and `upgrade --from` it exited 1 and printed nothing. All seven reads now stop on the status and leave find's error on stderr, and a test fails any read added without that check. It lands with `0123` and `0129` because both remove files on the answer those reads give.
- **A command that could not read everything under a directory stops reading it as complete (issue `0139`).** `infra profiles` and `infra mail dmarc parse` refuse a listing they could not read in full, `check format swift` and devbin's own syntax, lint and critic gates refuse a partial corpus, `fullcycle`'s artefact check and PATH watch fail the cycle, the runtime digest behind `--version` reads UNREADABLE, `check autotests` gives no verdict, and `new` says its search was partial and goes on. `fullcycle`'s artefact check now resolves a path a name at a time, following each link, before it calls a build tree gone, and counts a crate's test targets by cargo's own rule, a capitalised `Main.rs` included. A test fails any find added under `lib/` or `bin/` that loses its error or its status without a stated reason.
- **A directory `find` can list but not search is named, never read as empty (issue `0145`).** macOS's find passes over a directory of mode 0444 or 0644 below its start point in silence and exits 0, so every walk that descends -- the shell gates' corpus, `clean`, `fullcycle`'s artefact check, `doctor`, `install`, `fleet`, the runtime digest and the rest -- read what lay beneath one as absent. One walk, used by all of them, now names such a directory (`cannot search <dir> -- nothing beneath it was looked at`), prunes it and makes the walk partial, under BSD and GNU find alike, and a test fails any find added under `lib/` or `bin/` that descends without it or a stated reason. Measured on the `fleet` census, it costs within 5% of a plain find.
- **`fullcycle` refuses, before anything is removed, a `CARGO_TARGET_DIR` its artefact check cannot judge, and fails a cycle whose build tree kept its release artefacts through the clean (issue `0148`).** A relative value was read from the project root where cargo reads it from the build line's directory, one holding a newline was split, and one outside the project was never cleaned, so the last cycle's release binary read as this cycle's and a debug-only build finished green. A value that is relative, empty, holds a newline, is the filesystem root, or resolves outside the project, through a link or not, is now refused by name with its remedy, and `check targetdir` refuses an empty one in the same words. And after the clean, any tree the check will examine that still holds release artefacts is named and not compared, so the cycle fails rather than pass on artefacts it cannot date.
- **`fullcycle` and `check targetdir` find a build tree moved by `CARGO_BUILD_TARGET_DIR` or `build.target-dir`, by asking cargo where it is (issue `0150`).** devbin read only `CARGO_TARGET_DIR`, so a tree moved another way was never examined and the check gave no verdict at exit 0. Where a carrier is present -- either variable, or a cargo config naming `target-dir` or `include` in or above a crate or in cargo's home -- each crate is asked with `cargo metadata --offline --no-deps`, which leaves `Cargo.lock` alone, and cargo's answer is judged as a `CARGO_TARGET_DIR` is. With no carrier, nothing changes and cargo is not run. A fork set only in the machine's own cargo config is reported by `check targetdir`, not failed. When this was measured, none of the 37 crates across the consuming projects built anywhere but its own workspace's `target`, and no config among them sets a carrier.
- **A file devbin cannot read, its manifest included, is named as unreadable wherever devbin reads it (issue `0144`).** A checksum run that failed on one file came back one row short at exit 0, so `upgrade` could stop partway with files already replaced, `vendor` could call two unreadable copies level, and `doctor` ended early with no count. An unreadable manifest read as a manifest of no entries: `doctor` passed `0 vendored files intact` and `upgrade` overwrote an edited file at exit 0. Now `install`, `upgrade`, `vendor` and publishing refuse before they write, naming each file, `doctor` fails the manifest check and runs on to its count, and the version of such an install reads `unknown`, never the project's own `VERSION`.
- **An install with no manifest is unchecked, never clean (issue `0146`).** With `bin/.devbin/manifest.sha256` gone, `vendor` read an edited file as `behind`, `upgrade --from` replaced it at exit 0 and wrote a fresh manifest over it, and the next `doctor` passed, while `doctor`'s remedy for the missing manifest was that same `upgrade`. Now `upgrade` and `vendor` refuse it before any write, naming both remedies and what each costs: `upgrade --from <dir> --force`, which replaces every vendored file, or a re-install. `doctor` fails it and its version, and publishing says every file is replaced unchecked. When this was measured, no install on the machine lacked its manifest.
- **`infra mail dmarc report` no longer calls a failing DKIM signature your own mail (issue `0147`).** An infra user's archive held five records under "your own mail, failing", and none was: one was signed at a selector the domain never published, one carried an empty signer. The heading now says "own mail broken in transit, or a forged signature", each row prints every signature's signing domain and selector, and the report says how to tell the two apart. The profile-aware check that would tell them apart for you is `infra mail dmarc check`, devbin's ST0006, which is not built.
- **Release step 11 now puts the release tag in the CI query's environment, as `DEVBIN_RELEASE_TAG` (issue `0149`).** A cut pushes the release commit to its branch and pushes the tag, and CI may run a workflow for each on that one commit; a query that read every run on the sha could end a release green on the branch push's run before the tag's own run existed, as one project's v0.4.0 cut did. The query is still run as `<query> <sha>`, so no query breaks on this upgrade. **Projects that declare `release.ci.query` must make their query read `${DEVBIN_RELEASE_TAG:-}` and answer for that tag's runs only, `none` until one exists**: that project's `tools/ci-state` in place of its `git tag --points-at`, and Utilz's `tools/ci-state`, which reads every run on the sha today. A query that does not read it keeps its old verdict, and devbin cannot tell the difference. Row 11 now reads `ci.query answers green for <tag> (<sha>): ...`. devbin's own cut declares no `ci.query` and was not affected.
- **An unsealed option or command says what became of `--purge`, `--purge-only` and `--allow-empty` (issue `0122`).** Those flags act on a seal, and an option with a `run:` and no `log:` has none, so they reached its tool as arguments without a word: `check bare --purge`, over `run: echo bare-ran`, printed `bare-ran --purge`. Inside `all` they are now dropped for such an option, since they were typed for the sealed options beside it; named directly, the option or command still passes them on, because its tool may own the word, as git commit owns `--allow-empty`. Either way stderr says which.
- **`shell-init` writes a project's declared `install.prefix` into `dvb` as its machine-install fallback (issue `0125`).** The config reference always promised this and it never happened: shell-init read a config cache the dispatcher does not hand to a handler, so every project answered empty whatever it declared, and `dvb` had no fallback unless `DEVBIN_INSTALL_PREFIX` was exported. shell-init now reads its own project's config, and one it cannot read still emits `dvb`, without the fallback, and says why on stderr.
- **`infra check` and `infra init` ask again when a domain's nameserver lookup comes back empty, and say what they observed instead of blaming nameservers they never asked (issue `0142`).** An empty answer from the machine's resolver was final, so for one infra user six runs each listed live domains as not measured that answered moments later. The lookup is now asked up to three times, a second apart (`DEVBIN_INFRA_DNS_RETRY_PAUSE`), and a domain still unmeasured names what each attempt got and says devbin asked no authoritative nameserver. The three DNS knobs are refused, exit 1, before anything is measured, unless each is a whole number below 100000.
- **An infra profile can declare a sender's several DKIM records, DMARC `sp=` and a zone's wildcard A, AAAA and TXT, and `infra check` reads each (issue `0143`).** MailerSend signs with two rotating keys, `ms1` and `ms2`, and a profile could declare only one, so a missing second key read as held. Each labelled record is now read and judged alone, `sp=` is compared with the live record (or with `p=` where it has none), and a wildcard's absence is verified. A declared value is compared with the whole set of records at its name rather than found as a substring of the first one listed, and a declared policy against a record with no `p=` is drift. `infra init` records an `sp=` that differs from its own `p=` for review. Every profile in the consuming projects prints the same result before and after.

## Fixed -- devbin's own tree

- **`fleet`'s census frame is a tracked file, `bin/.devbin/fleet.roots`, and every census looks for installs outside it (issue `0116`).** The frame was the directory that holds the projects, a default in code justified by an earlier search; a second directory of projects appeared later, and a consuming project's checkout ran devbin 0.1.1 inside it, unseen by every sweep from 0.1.2 to 0.1.7. The file names both directories, `DEVBIN_FLEET_ROOTS` still overrides it for one run, and a missing or empty frame is refused rather than read as none. `fleet audit`, `fleet doc` and `fleet upgrade` each name any install outside the frame, and a walk that could not read everything fails `audit`, refuses the doc, and shows as a NOT KNOWN row in `upgrade`.
- **The test that every `@builtin` catalogue row has something implementing it can fail again (issue `0138`).** It read each row one column short from the day the catalogue gained its group column, so no row matched and it could not fail for seven weeks. It now reads all six columns and fails when the rows it checked and a second count of `@builtin` rows disagree; on today's catalogue it passes, 27 of 27, so nothing was hiding behind it.

## Known limitations

- **No devbin issue is open.** All 38 filed since 0.1.7, `0113` to `0150`, closed before this cut, since 0.1.8 carries every one.
- **The `MIX_ENV=prod` refusal does not reach a project's own `db` handler (issue `0132`).** A handler, a file at `bin/.devbin/cmd/db` or one mapped with `commands.db.handler`, replaces devbin's `db` entirely and is the one way past the refusal. When 0132 was filed, every Elixir project with a database ran its own -- five of them -- so the refusal covers none of them.
- **The `fleet` census does not look inside `~/Library`, `~/.Trash` or anything reached only through a symlink (issue `0116`)**, so it cannot find an install under `~/Library/CloudStorage`, where Dropbox and Google Drive keep their folders; each report says so beside its count. Walking CloudStorage as well is an open choice, against a walk that already took `fleet audit` from 17 s to 52 s.
- **The shipped pages are checked for prettier stability only where prettier is installed.** CI does not install it while devbin is private, so a CI run skips the check and says why; it is made by the `test all` gate a cut runs, on the machine the sweep runs from.
- **`infra` checks DNS and mail records only.** The Fly runtime and `infra mail dmarc check` are devbin's ST0006, which is not built, and Workspace routing is not machine-checkable; every `infra check` report says so.
- **Nothing the macOS runner supplies is exercised between releases**: its image, Homebrew, and the Intent formula `check critic` installs are met at a tag. `gh workflow run tests.yml --ref main` asks for the full set on demand.
- **A cut produces two runs of the tests workflow and only the tag's is the whole verdict**, and an intermediate pushed commit can have no verdict at all, because a newer push cancels it or a board-only push starts nothing.
- **A directory whose ACL denies search, its mode bits allowing it, is not detected as unsearchable (issue `0145`).** The walk asks the mode bits; probing each directory's ACL would cost a process per directory.
- **`fullcycle`'s artefact check does not read a cross-compiled profile, `target/<triple>/release` (issue `0148`)**, and a writer beside the cycle that recreates `release/` after the clean is not seen. For a crate in a subdirectory, the shared `<root>/target` that `check targetdir` accepts is not a tree `clean` removes, so a cycle reads it as kept; unset `CARGO_TARGET_DIR` there.
- **cargo is asked from each crate's own directory (issue `0150`)**, so a build line that runs cargo from elsewhere, or passes `--target-dir` or `--config` itself, is not followed; and where a carrier is present, a `Cargo.toml` cargo cannot parse, such as a template's, is refused by name.
- **Intent and one other project still release with their own orchestrators.**
- **The release core's reads before the first push are not time-limited**, nor is `release status`.
- **A cut under `object: ci` depends on the project's workflow running.** If CI does not start a job, the tag and the pushes stand and the object step fails at `object_wait`.
