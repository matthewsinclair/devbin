## Fixed

- **`release` no longer stops at step 1, saying nothing, when the tag git lists last matches the template but names no version (issue `0106`).** `release_versions` ended its loop with `is_semver "$v" && printf`, so the loop took its status from the last tag listed, and under `pipefail` a last tag like `v1.0.0-rc1`, or Utilz's old `v2.6.1` under its `{version}` template, failed step 1 with an empty detail, for a relative target and an explicit one alike. git lists tags in byte order, so which tag comes last is an accident of spelling. The test is now an `if`, and every way `release_versions` can fail now warns, naming what failed. Found by Utilz, the first project to cut with the core after devbin.
- **`version` and `infra`, with every `infra` subcommand, name `bin/devbin` in their usage lines and `try:` hints, as every other built-in does (issue `0107`).** They printed the project's name, which named a command only while each project had a launcher of that name. Those launchers are retired, so in a project named `demo` the usage read `usage: demo version ...`, a command that does not exist. The project's name stays the prefix on devbin's own messages. ST0003's AC-1.9 is restated to match.

## Known limitations

- **Intent and one other project still release with their own orchestrators, and Utilz has declared the release core but not yet cut with it.** Utilz's first cut through the core waits for this release to reach it. The adoption continues in each project's own work.
- **`fullcycle`'s overhead is measured across the whole cycle, not per phase.**
- **The release core's reads before the first push are not time-limited**, nor is `release status`.
- **A cut under `object: ci` depends on the project's workflow running.** If CI does not start a job, the tag and the pushes stand and the object step fails at `object_wait`; the workflow's run for the tag has to be re-run before the cut can finish.
