**Released 2026-09-16 as `v0.1.1`.** This note was written while the series was open, from 2026-09-07. It was completed at release against `git log`, and the entries that had never been written are now in it.

**What the `v0.1.0` tag does not carry.** `v0.1.0` was cut on 2026-09-01. Its note was then edited on 2026-09-06 to describe 26 commits made after the tag -- the machine install and most of issues `0045` to `0058` among them -- and re-dated to match. So the 0.1.0 note describes work that no tag carried until this one. **The tag stays where it is**, because a tag that moves is worse than a note that overreached. Some of those 26 commits appear in neither note, and they are written up below with everything else this release adds.

**Why the series moved at all.** 0.1.0 vendored straight out of the tree devbin is edited in, so the tree's state at any moment was every consumer's state. `install`/`upgrade` publishing to a machine install broke that coupling, and the version number is what makes the break legible: the dev tree can move while the consumers hold, and `devbin --version` in two directories now answers differently on purpose.

```
Consumer   devbin 0.1.0 (<sha>...)
Devbin     devbin 0.1.1 (<sha>... +dirty)
```

## Changed

- **`status:` in a release note is now read, and required.** It was written into the 0.1.0 note and consumed by nothing for the whole of that release -- a field that looked like a control and controlled nothing. It is now `released` or `unreleased`, and **absent is an error rather than a default**: defaulting it would rebuild the same hole one layer down, since a note that meant `unreleased` and forgot the field is exactly the mistake the field exists to catch.

- **`install.prefix` has NO DEFAULT, and publishing refuses without it.** `lib/install` carried `$HOME/Devel/opt/devbin` as the fallback -- one operator's directory layout, written into the runtime that fourteen projects vendor. Every consumer carried it, and a publish from any of them would have gone to a path named after somebody else's home directory and **would have succeeded**, because a publish to the wrong place is indistinguishable from a publish to the right one. devbin's rule already said the location is configuration; a default does not soften that rule, it relocates the decision from a key somebody wrote to the absence of one. `install`, `upgrade` and `fleet upgrade` now refuse by name through one shared message, and `--prefix <dir>` supplies it for a single run. It is the same rule `fleet` follows, which removed a hardcoded machine root for the same reason.
- **`shell-init` no longer emits a path invented from `$HOME`.** A consumer project has no reason to know where the machine install lives, so `dvb` generated there now carries no machine-install fallback rather than one aimed at a directory named after somebody else. Removing the default made the empty case reachable, which exposed a second defect: an unguarded `-x $prefix/bin/devbin` with an empty prefix tests `/bin/devbin` -- a real path on the system PATH that the function would have RUN. Guarded, and the message now says the prefix is unconfigured instead of naming a location it does not have. The bootstrap example in its usage named one machine's checkout; it names `/path/to/devbin`.
- **`docs/infrastructure.md` is deleted.** Half of it was one project's vendor snapshot -- MX forms, SPF includes, DMARC phases -- carried in a tool other projects vendor, which is the rule above applied to documentation. The machinery half survives in two places that reach a reader: the schema at `lib/infra.reference.yaml` (vendored) and the command's argument at `bin/.devbin/help/infra.md`. **The guard moved with it rather than being retired quietly**: the old arm read `[ -f "$doc" ] || skip`, so deleting the document would have made a guard stop guarding with nothing reporting the change. ST0003's design records the one thing this costs -- `infra init`'s STANDARD proposal source now has no home, and WP-03 carries that as an open dependency rather than inheriting a broken pointer.

## Added

- **`infra`: an estate's DNS and mail configuration, declared in a profile and checked against the live records** (ST0003). `infra check` reads authoritative nameservers only -- a recursive resolver reports the remaining TTL, not the configured one -- and sorts every assertion into four channels: ok, drift, COULD NOT MEASURE, and blind spot. It exits 2 when anything could not be measured, ahead of 1 for drift, because an unmeasured domain is what a scripted caller would count as covered. With no vendor table, `mail:` is checked for consistency across the estate, and an estate of one domain is reported as a blind spot rather than a pass. `infra profiles <dir>` checks that no domain is claimed by two profiles. `infra init` measures live domains and prints a profile to start from: a value reaches the target only through the RFC layer or a strict majority of the estate above two domains, and everything else goes to `unreviewed:`, which `check` refuses to run past. A domain naming a sender must describe its SPF and DKIM pair, and a profile that does not is refused when it is parsed. The schema is `lib/infra.reference.yaml`.
- **`infra mail dmarc parse` and `report`: DMARC aggregate reports, read in the containers reporters actually send.** Measured on 17 real reports from three reporters, none arrived as bare XML, so `parse` reads `.zip` and `.xml.gz` and decides the kind from the file's bytes, never its name. A zip that does not hold exactly one member is refused. `parse` takes a directory and accounts for every file on stderr -- parsed, not a report, or FAILED -- keeping stdout as JSON Lines, and an empty directory is an error. `report` summarises them; over those 17 reports the pipeline surfaced 10 records carrying no DKIM result at all, which is the forgery signature the subsystem exists to find.
- **`dormancy`: how many tests a Rust project does not run.** It runs the declared suite and the same suite with `--all-features`, and reports the difference, since tests behind a feature the declared invocation never enables compile, sit in the tree and are never reported. It is a verb rather than a `check` arm because it costs two full builds.
- **`fleet upgrade`: the sweep of every consuming project, dry-run by default.** It distributes the machine install's bytes to every project that vendors devbin and needs `--apply` to write. A project counts as `level` only when its recorded provenance matches the install, and an upgrade that holds back an edited or released file is reported by name, counted as `HELD BACK` and exits 1 (issue `0074`, and the `0069` entry below).
- **`clean --dry-run`** (issue `0042`). The scan used to be reachable only through the confirmation prompt, so in CI, a script or cron the only two outcomes were refusing and deleting.
- **The run log names the machine that produced it** (issue `0052`). A seal was a true record of one OS's run and said nothing about which, so a local `824 tests, 0 failures` read as a fact about devbin while CI was red on Ubuntu. Every sealed log now carries a `platform:` line, and run-log stamps read UTC (issue `0055`).
- **`--version` names the bytes it is running.** On a dirty tree the commit alone names no bytes, which is exactly when an identity matters, so the line also carries a digest of the runtime: `devbin 0.1.1 (<sha> +dirty, runtime <digest>)`.
- **An unreleased release note.** `CHANGELOG.md` and `RELEASES.md` render `Unreleased` in place of a date, per Keep a Changelog, so an open series can accumulate notes without either view claiming it shipped. An unreleased note carrying a `date:` is **refused rather than ignored** -- an ignored date survives the flip to `released` and ships as a claim nobody re-checked.

## Fixed

- **`release check` could not go red on the question it is asked.** It compared the two generated views against `RELEASES/*.md` and reported `release views are current`, which was true and narrow: nothing in the command had ever read `VERSION`, so **no state of the version file could turn any of the seventeen arms in `tests/unit/release.bats` red**. Bumping to 0.1.1 with no `RELEASES/0.1.1.md` was green. It now reads the version file and refuses. Found by walking into it while preparing this release, not by review.
- **A refusal in the release tooling could not refuse.** `note_status` dies on a note with no `status:`, and the message was printed -- twice -- while `release notes` went on to write both views and exit 0, with the date rendered as though the note were released. **Command substitution does not inherit `errexit` unless `shopt -s inherit_errexit` is set, and that shopt appeared nowhere in the repository**, so a `die` two substitution levels deep killed only its own subshell. The guard written to catch a false green was hiding one inside itself. Fixed in `bin/.devbin/cmd/release`; the general case is issue `0060`, deliberately NOT fixed runtime-wide in this release because the one-line dispatcher form would be in force in every project that vendors devbin the moment it landed.
- **`infra` told the reader to type a command the project does not have.** `lib/cmd/infra` hardcoded the literal `devbin` in its usage block and its unknown-verb refusal, inside a QUOTED heredoc, while the same command's own children rendered `$DEVBIN_NAME` correctly. In a project whose dispatcher is not named `devbin`, the top level printed `usage: devbin infra` and `devbin` resolved to nothing. **It was invisible from inside this repository**, where `$DEVBIN_NAME` IS `devbin` and the two forms are byte-identical -- only a consuming project can tell them apart, and the first run of `infra` in one is what found it. The obvious fix carries a second defect: unquoting the heredoc also expands the unset `$DEVBIN_INFRA_PROFILE`, dropping a resolution step from the text that documents resolution, so the variable is escaped. Three arms cover it, all of them run under a name that is NOT `devbin` because no assertion made under the real one could separate the two.
- **A refusal named a verb that did not exist yet.** `infra check`'s unreviewed gate said each deviation "was proposed by `init`" while `infra` accepted only `show|check`. It was reworded to describe the deviation without naming an unbuilt command; `infra init` has since shipped (see Added). The same line carried the last outstanding `SC2016` breach in the tree, which is what made anyone read the sentence.
- **`check lint` was red at HEAD and nothing had reported it.** Two deliberate backtick-in-single-quote messages landed with `infra`'s profile validator on 2026-09-06 and CI could not have caught them: CI runs on push, and nothing had been pushed since 2026-09-03. Suppressed at the function with the rationale, matching what `release`'s renderers already do. `check all` is rc 0 again.
- **The version bump had a sidecar that does not move by itself, and one instrument said it did.** `bin/.devbin/config.yaml` declares `devbin_version` as a CONSTRAINT and it still read `"^0.1.0"` after `VERSION` moved to 0.1.1. **`devbin version check` reported `version: 0.1.1, every sidecar agrees`** -- true, because a constraint is not a sidecar and it never looked. The suite is what caught it: `documentation.bats` asserts devbin's own version is a literal in exactly one file, and with nothing carrying `0.1.1` the extractor found no site at all. Now `"^0.1.1"`, and `doctor` reads `0.1.1 satisfies ^0.1.1`. **The constraint stays a hand-written literal on purpose** -- deriving it from `VERSION` would make `doctor`'s check unfailable, which is the whole reason it is written twice.
- **THE MACHINE INSTALL COULD NOT DO THE ONE THING IT EXISTS FOR.** `bin/devbin` refused to run from an install tree at all, `install` included -- so a project with no devbin yet could not be seeded from the install, which is precisely what a distribution point is for. Reported from a real onboarding attempt. **The two routes that did work were each wrong in a different direction**: from the development checkout you get whatever that tree is mid-release (0.1.1 while every consumer runs 0.1.0) and the project records a working tree as its `source`; from another consumer you get the right bytes and a `source_commit` that is THAT consumer's git HEAD -- a hash which does not exist in devbin's history. Installing from the install is the only route that gets bytes and provenance both right, and it was the blocked one. `install` is now exempt, matching the exemption the wrong-tree guard has always had for the same verb.
- **And the refusal named a command the reader could not run.** It said `cd <your project> && bin/devbin upgrade --from <install>`, addressed to someone whose project has no `bin/devbin` in it. That is this repository's own "the remediation names a command that EXISTS" defect, in the one message read by people who have nothing installed yet. It now names `install --into` first.
- **Installing into a devbin SOURCE tree is refused, whatever the source.** The guard compared the target to the source, so it only caught a tree installed into itself. Installing from the machine install into the development checkout has a different source and an identical consequence -- and while testing the exemption above it happened: `bin/.devbin/lib/` and a manifest landed in devbin's own tree, where a vendored copy sits ahead of `lib/` in the dispatcher's search order and every edit stops taking effect with the suite still green against the copy. **A first attempt at this guard required `--into` instead and was wrong**: `--into` defaults to the cwd, and that default is correct for the documented `DEVBIN_SOURCE` bootstrap, which runs `install` from inside the new project on purpose. Guarding the harm beats guarding one route to it.
- **`dvb` outside every project was a flat error, and that stopped being the right answer the moment a machine install existed.** All four of `dvb version`, `dvb --version`, `dvb devbin version`, `dvb devbin --version` failed from `$HOME`. The emitted shell function now falls back to the machine install when the walk finds nothing and `DEVBIN_SOURCE` is unset -- **last in the order**, so a project's own launcher and an explicit `DEVBIN_SOURCE` both still outrank it and the fallback can never shadow the tree you are standing in. The prefix travels as a placeholder substituted after generation rather than by unquoting the heredoc, because unquoting would expand `$PWD`, `$@` and `${^tried[@]}` at generation time -- emitting a `dvb` that always ran against one frozen directory, with no error anywhere. That is the same trap `lib/cmd/infra` fell into on the same day, and there is an arm holding it down.
- **An install now answers questions about DEVBIN, and still refuses questions about a project.** All four spellings report the installed version and commit, read from the manifest -- answered by the dispatcher rather than routed to `lib/cmd/version`, which reads a project's `VERSION` file and declared sidecars and would report `unknown` from a tree whose manifest records the answer exactly.
- **The wrong-tree guard no longer fires inside an install tree.** With `dvb` falling back to the install, running a project verb from outside any project reaches one by design, and the answer was `refusing to run -- this is not your current project`, naming the install as the project it belongs to: confusing, and false. The install-tree refusal says what is true and names `install --into` and `upgrade --from`.
- **Every consuming project's tracked manifest named the operator's home directory, and a scrub never survived the next upgrade (issue `0069`).** `# source:` recorded the install path absolute, so `bin/.devbin/manifest.sha256` carried `<home>/...` -- and with it a login name -- in every project that vendors devbin, several of them public, rewritten on each `install` and `upgrade`. **A source under `$HOME` is now recorded as `~/<rest>`**, and every reader goes through `manifest_source`, which expands it, so `upgrade` with no `--from`, `vendor`, `doctor`, the update notice and `fleet` all still see the absolute path they always saw. A manifest written before this change reads back as it is. **The same leak was in the census document `fleet doc` generates**, which this repository tracks: its roots list printed absolute, and its project column stripped `$HOME/` by hand and so printed every path absolute under a HOME ending in a slash. **Four copies of the `~` conversion became one pair**, `home_relative` and `home_expand` in `lib/helpers`: the config reader for `install.prefix` had its own, and it turned `~/opt/devbin` into `/opt/devbin` under an empty HOME -- a real directory a publish would have written into. The pair guards that edge, a HOME that is only a string prefix of the path, and a trailing slash, once for every caller. **A sweep that only compared paths would have left the leak in place**: an absolute source reads back equal to the prefix, so every pre-0069 project looked level, and a project's first upgrade pass runs the runtime it already has, which writes the absolute form while installing the new one. `fleet upgrade` now treats the recorded form as part of `level`, and takes its second pass when the first leaves the form behind. **What this does not do**: remove the line from history already committed and pushed in those repositories; and a tracked `~/...` names a path relative to whoever runs devbin, which is the point, so a collaborator with a devbin at that path upgrades from theirs. A project rolled back to a pre-0069 runtime cannot expand the `~` form: its update notice goes quiet and `upgrade` with no `--from` refuses by name until it is given one.
- **`fullcycle` told the operator the build trees had not been rebuilt, after the build had rebuilt them (issue `0068`).** When `test rust` failed, the run printed `THE BUILD TREES WERE ALREADY REMOVED AND HAVE NOT BEEN REBUILT`, called everything on PATH through `target/release/` dangling, and named a rebuild as the first thing to do -- in Intent, two minutes after `build all` had passed and the new binary was already running. The branch asked whether the clean had passed and never whether a build had passed since, so on the one failure that can follow a passing build it was false every time, which teaches a reader to discount it on the day it is true. **It now fires only when the clean passed and no build has since.** After a passing build it states the build's exit code and the failing phase, and says the run makes no claim that `release/` came back: the artefact check runs only on a green cycle, and a first cut of this fix that called the failure "not in the rebuild" overclaimed the other way, contradicting the link check on the same screen. **Not changed here, filed instead**: a declared `commands.fullcycle.restore` is skipped silently after a test failure (`0070`); a failed build with a dark watched link gets a dev-profile cause and a second remedy (`0071`); a clean that fails partway reports nothing about the links it darkened (`0072`).
- **A failed build got two causes and two remedies from `fullcycle` (issue `0071`).** With a watched PATH link dark, a `build all` that failed after a passing clean drew the loop's `THE BUILD TREES WERE ALREADY REMOVED` and `bin/devbin build all`, and then the link check, which is not gated on the run's exit code, added that "a dev-profile build does not" repopulate release/ and prescribed a RELEASE profile. The build had not run at a dev profile; it had failed. **The link check still names every dark link**, and gives the dev-profile cause and its remedy only when a build passed; otherwise it points at the remedy already printed.
- **A clean that failed partway left `fullcycle` silent about the PATH links it had darkened (issue `0072`).** `clean` removes trees one at a time and dies on the first it cannot remove, but the link check ran only after a clean that passed -- so a failed clean that had already removed a tree behind a watched link reported `STOPPING: clean rust failed` and nothing else, which reads as nothing having been touched. **The link check now runs whatever the phases did**, and after a failed clean names the dark links, says the clean may have removed what they resolved through, and gives the one rebuild remedy. The loop adds no alarm of its own on a failed clean, because the commonest one -- the no-tty refusal a cycle without `--force` meets -- removes nothing; it points at `clean`'s own `removed` lines, and at the tree it died on, which may be partly gone.
- **A witness run's deliberate failure reached its parent's run summary (ported from a consuming project).** `RUNLOG_WITNESS_RUN=1` marks a run that is not the gate's current verdict, and it already kept such a run from re-pointing `LATEST_*`. But `run_all` exports its seal ledger, so a nested witness `bin/devbin` inherited it and appended its red row: in that project the summary under `FAILED: mix credo` named a `test rust` seal the rust gate never produced, and it was chased as real. **The ledger now records the run id that owns it, and a row from any other run is not written** -- the witness child is a different run by the rule below. A first cut keyed on the witness flag, and because the flag is inherited it emptied a witness `all`'s own ledger, a false green; it never shipped. A witness started inside a witness run is part of that run and its rows are kept -- the declared limit in the next entry.
- **A witness run started by a non-witness run mints its own run id; every other child devbin inherits its parent's.** `lib/runlog` said the id was not exported while `bin/devbin` exported it and the suite held a child to its parent's id, and one consuming project patched its copy to stop exporting it. Inheritance is the rule -- a `fullcycle` is one run, witness or not -- except at a witness boundary, where sharing the parent's id made `grep -l "run: <id>"` count a gate's nested witness runs as that gate. `DEVBIN_RUN_WITNESS` carries whether the parent was a witness, because the flag alone cannot tell. **Declared limit:** inside a witness run, a child started as a witness on purpose cannot be told from one that inherited the flag, so it is part of that run, its id and its ledger rows alike.
- **`fleet upgrade --apply` counted a project whose upgrade held back edited files as upgraded (issue `0074`).** The sweep discarded each project's upgrade output and judged it by exit code and recorded provenance, and an upgrade that skips a file edited in place exits 0 and still stamps the new commit. In the 0069 sweep that read `16 upgraded ... 0 FAILED` while one project had kept two patched files. **Every pass of each project's upgrade is now read**: a project with `skipped` or `released` files is reported in its own table with the files named, left out of the upgraded count, and counted as `HELD BACK` on the summary line, and the sweep exits 1, because a held project is not level. Every pass, because a `released` file leaves the manifest on the pass that releases it and a second pass never mentions it. Each kind gets its own remedy -- `--force` replaces an edited file and cannot reach a released one -- and when a pass counts more skipped files than it names, the difference is reported. A FAILED project now says how it failed (the upgrade's exit code, provenance that did not converge, or no scratch file to read the output into) and keeps its held files; a `skipped` or `released` line in wording the sweep does not recognise is reported as unrecognised rather than counted as named, where every FAILED row used to say the provenance had not converged.
- **Publishing the machine install named a `fleet` command that refuses to run (issue `0073`).** `install` and `upgrade` in devbin's own tree ended with `bin/devbin fleet upgrade --dry-run`, and `fleet upgrade` has no `--dry-run`: its dry run is the default, so the line died with `unknown argument '--dry-run'` at the moment the projects were behind. Both now print `bin/devbin fleet upgrade` from one helper, and the tests run the printed line through the real `fleet` parser rather than comparing strings.
- **`version check` said every sidecar agreed when there were none to agree** (issue `0061`). Zero sidecars and two agreeing ones printed byte-identical output at rc 0. It now names the count, and still exits 0 at zero, because most projects correctly declare no sidecar.
- **A refusal for an undeclared language named neither list it read nor the file it lives in** (issue `0062`). `project.languages` in `bin/.devbin/config.yaml` scopes devbin's gates, and Intent's language list is a separate fact by design, so "does not declare the 'rust' language" sent Utilz to change a correct declaration. Both refusals now say `in project.languages (<file>)`, and the option-level one checks that the language really is undeclared before saying so. `doctor` states which languages arm the built-ins and notes when none do.
- **A project could not decline the log wrapper** (issue `0065`). `log: "-"` sealed a gate named `-`. `-`, `false`, `no` and `0` now mean no seal, resolved once for both the option and the command path.
- **`check critic` was red for a week with a sentence blaming the runner** (issue `0075`). Intent 3.0.3 takes one path per `--files`, and the gate passed the whole corpus after one flag. It now passes one flag per path, and a runner that refuses the call is reported with its exit code and its own words.
- **`release notes --help` regenerated both views, and `release check --help` ran the check** (issue `0067`). The command read only its first argument, so asking a verb for help ran the verb, and a hand edit to `CHANGELOG.md` -- the state `check` exists to catch -- was silently discarded. `--help` in any position now prints usage, and a word after either verb is refused before anything is written.
- **`fullcycle` skipped a declared restore, without saying so, when the tests failed after a passing build** (issue `0070`). The restore was gated on the whole cycle passing, so the toolchain was left dark in exactly the projects that declared a restore to prevent it. It now runs after any build that passed since the clean. The failing phase's exit code stays the run's verdict: a failed restore or a dark link no longer overwrites it.
- **`infra profiles` and `infra mail` read a forgotten argument as success.** Both exited 0 with usage text when called with no argument. Asking for help still exits 0, and a missing argument is now a refusal.
- **The upgrade notice warned it would REVERT the runtime when the commits differed and the bytes did not** (issue `0053`), and **the `fullcycle` preview printed a weaker `clean` than the run executed** (issue `0054`).

### Found in a consuming project, and three of the four were real

- **The flagship profile example did not parse, and it was somewhere no consuming project could read it.** It used flow collections (`dmarc: { policy: none }`), flow sequences, and a `domains:` map keyed by FQDN rather than by handle -- three forms this parser rejects, in the first thing a new reader copies. It also named eleven real domains of a live estate. Fixed and genericised; then moved, because the deeper defect was its address: it lived in `docs/infrastructure.md`, and `docs/` is devbin's own repository. **The fourteen projects that RUN `infra` vendor `bin/devbin` and `lib/` and nothing else**, so the only documentation of the profile schema sat in the one tree where `infra` is never pointed at a real estate. It is now **`lib/infra.reference.yaml`**, vendored to `bin/.devbin/lib/infra.reference.yaml` in every project exactly as `config.reference.yaml` is, and **parsed by the suite on every run** -- the only assertion that cannot rot, since a test grepping for forbidden punctuation would pass the day somebody invented a fourth way to write it wrong. It is a profile outright, so there is no extraction step left to break.
- **Cross-profile domain uniqueness had no owner: `infra profiles <dir>`.** One-entry-per-domain was enforced WITHIN a file for a stated reason, and that reason does not stop at the file boundary -- an estate laid out as `profiles/<name>/infra.yaml` can have two profiles claiming one domain with the identical consequence and nothing reporting it. A directory holding no profiles is an **error**, not a clean report. An unparseable profile stops the comparison rather than being skipped, because a skipped profile is a domain that vanishes from the population and makes a real collision read as clean.
- **Recorded for WP-02, not built:** a DMARC store must key on `report_id`, not on the reporter's filename. Measured on real data -- two reports sharing reporter, domain AND window, differing only in `report_id`. A store keyed on `reporter!domain!begin!end` would overwrite one with the other and say nothing.
