version: 0.1.20
date: 2026-11-05
headline: every open issue fixed in one release: a formula rendered in assets mode passes brew style; a Rust CLI's lock sync, notarisation, binary signing and formula publish move into the core; the release core's edge cases are closed; and devbin's own release takes the core's standard shape.
status: released

**Why this release exists.** It carries every issue that was open on devbin, fixed, as one release. A formula that `formula render` or `formula publish` wrote in assets mode had its install manifest's header on one Ruby line, longer than brew style's limit, so a tap whose CI runs `brew style` or `brew audit --strict` went red on it (issue `0322`). The ship that Rust CLI projects each carried as commands of their own (the lock sync after the version stamp, the macOS signing and notarisation, and the formula publish after the release) moves into the core as config (issue `0323`). The rest close edge cases in the release core, the helpers and the test harness. It also carries devbin's own release in the core's standard shape (issue `0320`) and its workroom, public with the product. It keeps a 0.1 number, as 0.1.8 to 0.1.19 did, because every consuming project pins a `^0.1` caret.

## Added

- **The stamp step brings a `Cargo.lock` in step with the version it stamps (issue `0323`).** Where `version_from` is a `Cargo.toml` with a `Cargo.lock` beside it, the stamp step runs `cargo metadata` and compares the lock with what it was, setting aside the version line of each package with no source. Any other change puts the lock back byte for byte and refuses, naming the lock and what moved, and the lock joins the release commit as a written path. Pre-flight refuses a cut whose stamp is due, whose lock needs syncing and whose host has no `cargo` on PATH, and the dry run's stamp row names the sync. A project's own `derived:` lock sync still runs after it and finds nothing left to change.
- **The built-in `macos` signs, notarises and packs a project's command-line binaries, a `.app` beside them included (issue `0323`).** A project declares them under `macos.binaries`, one entry a label: each binary's name in `macos.bin_dir` (default `target/release`), the identifier it is signed as, and an entitlements file or a designated requirement where it needs one, the requirement defaulting to the Developer ID form from its identifier and the team. `macos.pack.files` names files packed beside them. Four verbs mirror the app's. `bin-sign` signs each binary at the release commit with the Developer ID identity, the hardened runtime and a secure timestamp, and reads it back. `bin-notarize` submits them to Apple in one archive under the notary profile and, once Accepted, has Gatekeeper assess each; nothing is stapled, since a bare binary cannot carry a ticket. `bin-publish`, once the tag is cut, packs them as `<project>-<version>-<host triple>.tar.gz`, a `.app` at its root and every other binary under `bin/`, and attaches it with SHA256SUMS. `bin-verify` reads the stage back and changes nothing. Where the release object is `local`, the cut's macOS stage, now `macos leg`, signs and notarises the binaries at the release commit as it does the app, so a notary refusal stops the cut with nothing tagged or pushed, and pre-flight refuses a `macos.bin_dir` git does not ignore. The object step runs `bin-publish` once the object and its attach are made, before the formula step. A re-run finds the archive there and packs nothing; a release that carries it without SHA256SUMS agreeing stops the cut at its confirm step, before anything is packed; and a re-run past the tag must be on a Mac, since the archive's name carries the host's triple.
- **`release.formula: true` makes the formula publish and the tap pull a step of the cut (issue `0323`).** The formula step runs `formula publish --pull` under the cut's one yes, between the object step and `after:`, and only once the object step has succeeded, its attach and the binaries' archive included, so a formula never names an asset the release does not have. A failure stops the cut at that step, exit 1, with the release standing and `after:` not run, and the same command finishes it once the cause is fixed. Pre-flight refuses the key where no `formula` command is active. A project without the key sees one new row, `formula skipped`, in the cut, the dry run and `release status`.
- **`formula publish --pull` updates this machine's clone of the tap once the formula is published (issue `0323`)**, at `<brew --repository>/Library/Taps/<owner>/homebrew-<name>`, by a fast-forward pull. No brew, or no clone there, is said and is not a failure. A clone that will not fast-forward is.

## Changed -- a script or a config may get a different result

- **Every notarisation submits under one `notarytool` keychain profile, and `macos.keychain` is retired (issue `0323`).** `macos app-notarize` runs `xcrun notarytool submit --keychain-profile <profile> --wait`, the profile named by `macos.notary_profile` (default `devbin`), and no longer reads the three login-keychain items under `macos.keychain`'s prefix. A config that still declares `macos.keychain` is refused as an unknown key, naming what replaced it. `macos store-creds` now runs `xcrun notarytool store-credentials <profile>`, which prompts for the Apple ID, the team id and an app-specific password and checks them with Apple before it saves, and `macos doctor` reads the profile PRESENT or NOT USABLE. Before a project's next cut on 0.1.20: delete `macos.keychain` from its config, and run `bin/devbin macos store-creds` once on each Mac that cuts. The old keychain items are left where they are.
- **`macos.team` picks the Developer ID identity, and a keychain with more than one and no team is refused (issue `0323`).** `app-sign` stops before it builds, naming the teams it found and the key, and `macos doctor` reports the identity REFUSED. One identity in the keychain, or a declared team, signs as before.
- **Pre-flight refuses a declared macOS stage whose app, or whose declared build root, lies in the tree where git does not ignore it (issue `0313`)**, naming each path, its key and the line to add to `.gitignore`, before anything is stamped. The stage and the local gates share the tree at the release commit, so such a path failed the leg that read it, blamed on the wrong leg. A path outside the tree is passed over.
- **The candidate's remote pick refuses a push url whose host cannot be read (issue `0310`)**, naming its remote and never the url, whose user part may hold a password. Such a url (an `@` in its user part not written `%40`) was passed over, so a mirror on another host could take the candidate. Pre-flight refuses on it, before anything is stamped.
- **Under `release.publish.url`, pre-flight and `release attach` refuse an assets workflow that the snapshot list leaves out (issue `0314`)**, naming the list and the line to add. Both checked the release commit's tree, so a list that left the workflow out passed, and the attach then waited out `assets.wait` for a run that could not exist.
- **`git_head_sha` stops on a form it does not know (issue `0298`)**, naming itself and the two forms it knows, `short` and the full name, as `is_commit_sha` does. It read any other form as `short`, silently.
- **`worktrees` names each of git's local variables it clears, with the repository it acts on (issue `0305`)**, as the release verbs do, and stops on a failure to clear them, saying which. It cleared them silently before `remove-landed` wrote.
- **An install's dirty source stamp names why it is dirty (issue `0318`)**: `<sha> +dirty (<answer>) -- THESE BYTES MATCH NO COMMIT`, the answer one of DIRTY, not tracked, not watched or UNREADABLE. Every reader in devbin matches ` +dirty` or cuts the commit at the first space, so a manifest written before reads as one written after. A script of a project's own that parses the stamp sees the new parenthesis.
- **The update notice stays quiet between two installs of one release (issue `0319`).** Commits that differ while no vendored byte would change read `matches`: quiet in the notice and the upgrade offer, and a pass in `doctor` that still names both commits and why they differ. Switching a machine between an opt install and Homebrew's for one release no longer makes every project's notice speak. Bytes that cannot be compared still read as they did.
- **`ci-state` words a failed listing of a commit's runs as the attach always has (issue `0312`)**, naming the workflow and the full sha, and the attach's rows no longer carry what `gh` writes on stderr as it succeeds. Both read one lister of a commit's workflow runs.

## Fixed -- reaches every project

- **A formula rendered in assets mode passes `brew style` (issue `0322`).** The install manifest's header, the `lines = [...]` list the install body writes, was one line, 131 columns in one tap's render against brew style's `Layout/LineLength` limit of 118. It is now written one element a line, with the trailing comma brew's style asks for. The manifest a keg writes is byte for byte what it was, so nothing installed reads differently. In both modes, every line a render writes of its own passes `brew style`, and a test holds every file a render writes to that where brew is installed. A tap that published an assets-mode formula with an earlier devbin passes once it publishes again with this one.
- **A cut's exit notes reach its RELEASE log when the signal that ends it takes the tee (issue `0307`)**: the gates it stopped, and the candidate it pushed with the command that deletes it. With no person at a terminal, as for a CI job or a cancelled booking, those lines reached no log before.
- **`macos`'s commit-stamp check takes a sha256 repository's 64-character stamp (issue `0299`).** `is_commit_sha` has a stamp form, eight or more lowercase hex characters up to a whole name of either object format, and the check reads through it.
- **`macos`'s `drop_check_copy` puts every signal it was asked about back (issue `0311`).** A caller that saved one handler had the other signals left ignored. `traps_restore` resets each named signal the saved text does not name before restoring the saved handlers, and the gate runner restores through the same helper.

## Changed -- devbin's own tree

- **devbin releases from its public repository in the core's standard shape (issue `0320`).** Its config declares no `release.publish` or `release.snapshot`, and `release.remotes` names `local` then `upstream`. The cut pushes the release commit itself to `candidate/<tag>` on `upstream`, reads CI green there beside the local gates and the kovacs leg, then tags and pushes the commit and the tag to both remotes. The tag names the release commit, so the formula's revision is read from the tag in the checkout that cut it. `docs/releasing.md` says the same. The core's snapshot shape stays for any project that declares `release.publish.url`.
- **devbin's workroom is public with the product**: its `intent/` record, its own project commands under `bin/.devbin/`, and its agent instructions. None of it is in the set a project vendors. Comments, test titles and a CI step's name now give the reasons that hold since (issue `0321`).
- **`DEVBIN_JOBS` is a shared desk's one cap (issue `0303`).** devbin's own test runner takes it as `DEVBIN_TEST_JOBS`'s default, and `DEVBIN_TEST_JOBS` still wins where both are set. `docs/authoring-commands.md` names it in the environment a declared command inherits, so a project's command can bound its own tools, such as cargo's `CARGO_BUILD_JOBS` or xcodebuild's `-jobs`, with no flag.
- **The test harness refuses a commit with no identity on every host (issue `0302`).** Its global git config sets `user.useConfigOnly`, so an arm that leaned on an identity git guessed from the host's name goes red where it is written, not only on a host without a domain. The release fixtures' redundant `-c` identity pairs go.
- **The release fixtures' builders return each step's failure (issue `0301`)**, so a project half made never reads as made, and the arm that built two projects in one directory clears the first.
- **The gate scans read a `run_gate` call only where a command starts (issue `0316`)**, so a name that ends in `run_gate`, or `declare -F run_gate`, is no longer read as a call.
- **Code that was written twice in the release core is written once (issues `0308`, `0309`, `0312`)**: a repository's host and OWNER/NAME split, the candidate ref's delete and read-back, and the lister of a commit's workflow runs. No behaviour changes but what `0312`'s entry above says.

## Known limitations

- **Every limitation 0.1.19's note names still stands**, except where an entry above says otherwise.
- **A Rust CLI whose release object is CI's draft (`object: ci`) keeps its own finalize step.** The core signs and notarises binaries a project builds itself (`object: local`). Signing archives that CI built into a draft release stays a project's own command.
- **The `build:` block does not export `DEVBIN_JOBS` to a build (issue `0303`)**, since the core runs no build through the block yet. The first runner exports it.
- **Under `derived:`, `--fires` is given none of the stamp's files**, so a project with `derived:` whose test workflow's push has a positive `paths:` filter is refused at pre-flight, never passed wrongly, with the three exits the refusal names.
