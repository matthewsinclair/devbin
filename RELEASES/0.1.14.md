version: 0.1.14
date: 2026-10-24
headline: devbin conforms to the dev, opt and brew contract -- `devbin use` switches one link between a maintainer's dev checkout, opt install and the Homebrew keg, the machine pointer is retired, and `--version` names the tree it runs from -- the README installs from brew first, the licence is MIT, the shipped tree carries no workroom text and a guard keeps it out, every remote call runs through one no-prompt runner, the release core names its steps instead of numbering them, and the changelog carries the sections every note since 0.1.7 left out.
status: released

**Why this release exists.** It carries everything since 0.1.13: devbin's conformance to the dev, opt and brew contract (`docs/dev-opt-brew.md`, new in this release), which Molt, Utilz, Intent and devbin share for every tool released through Homebrew, and issues `0207` to `0219`. Most of it prepares devbin's first public release: the README's user route is the brew install, dev and opt are written for the maintainer of a dev checkout alone, the licence is MIT, and the shipped files carry no text written for the development workroom. This release is still cut from the private repository. It keeps a 0.1 number, as 0.1.8 to 0.1.13 did, because every consuming project pins a `^0.1` caret.

## Added -- new commands, checks and routes

- **`devbin use [dev|opt|brew]` switches which devbin a login shell runs, through one link, `~/.local/bin/devbin` (issue `0213`).** `use dev` and `use opt` point the link at the maintainer's dev checkout or opt install, and run from the dev checkout only; `use brew` removes a link into devbin's own trees and nothing else, so no link means brew; a bare `use` reports which tree the link names. It runs from an install, the keg on `PATH` included. No other verb writes the link. `use` belongs to devbin's own trees: a project with devbin vendored into it does not offer it, its `bin/devbin` refuses `use` with exit 6 naming `devbin use`, and its help leaves the command out. A project that owns a `use` command of its own still runs it.
- **`--version` and `version` name the tree they run from (issue `0213`).** From an install and from devbin's own checkout the line is `devbin <version> (<tree>, <sha12>[+dirty]) at <root>`, where the tree is `brew`, `opt`, `dev` or `unknown`; a dev tree's `+dirty` reads only the runtime set, `bin/devbin` and `lib/`. A consuming project keeps its own line.
- **`docs/dev-opt-brew.md`, the dev, opt and brew contract.** The trees, the publish, the manifest, tree identity and the version line, the `use` switch and its link set, upgrading by tree, tests in dev only, the formula, the install vendored projects read, and the proof. The README's documentation table has a row for it, and `documentation.bats` holds that the table has a row for every doc under `docs/`.
- **A project's own commands get three library forms in `lib/helpers` that devbin's own callers already used (issue `0218`).** `git_local_env_clear` clears git's repository-local variables from the current shell and fails when nothing can be cleared; `url_host_path <url>` reads a remote url as `HOST<TAB>OWNER/NAME`, taking the userinfo from the authority alone, with a status of its own for each failure; `text_shown <text>` leaves out the userinfo of every url in any text. `git_readonly`, `release_repo` and `release_text_shown` are rebuilt on them.
- **`git_remote` is the one runner for a call that reaches a remote, and a project's own commands can call it (issue `0217`).** It sets `GIT_TERMINAL_PROMPT=0`, empties `GIT_ASKPASS` and `SSH_ASKPASS`, passes `-c core.askPass=`, sets `SSH_ASKPASS_REQUIRE=never`, keeps ssh's `BatchMode=yes`, asks a credential helper not to prompt (`credential.interactive=never`, `GCM_INTERACTIVE=never`), and reads stdin from `/dev/null`. `release_git_remote` runs through it.

## Changed -- a script or a config may get a different result

- **The machine pointer is retired, and which install a project vendors from follows the switch (issue `0213`).** The install devbin reads is `DEVBIN_INSTALL_PREFIX`, else the `~/.local/bin/devbin` link followed by its own path, else Homebrew's opt link. `--point` is gone from `install` and `upgrade`, and nothing reads `~/.local/share/devbin/home` any more; doctor names one left on disk as a note. `DEVBIN_SOURCE` places nothing any more: it is `dvb`'s fallback alone. Under `use dev` a project upgrades from the checkout and records `checkout`, `+dirty` when dirty.
- **`install --force` is the one way to re-publish an opt install (issue `0213`).** It replaces an opt install devbin wrote. `upgrade` run in devbin's checkout publishes nothing and names `install --force`. An opt prefix with no manifest is refused, naming the remedy, where 0.1.13 replaced it unchecked; a manifest with no rows still says devbin wrote it, and is still replaced unchecked.
- **An install's manifest records `tool: devbin`, its version, and `managed_by` (`devbin` or `brew`) (issue `0213`).** An opt install in the older form fails doctor, naming `install --force`; an older keg, and a keg with no manifest under Homebrew's opt link, is brew, and doctor notes it, naming `brew upgrade devbin`. doctor gains a tree row in devbin's checkout and a switch row: a link shadowed on `PATH`, a link that cannot be followed, an older manifest, and a leftover pointer.
- **`fleet` sweeps from the switch's install, and refuses a switch that names the checkout or nothing (issue `0213`).**
- **The release core names its steps and rows, and its status table prints no number column (issue `0209`).** A row is `  <step>  <state>  <detail>`, its name and state columns as wide as the longest step name and state, and the stop line reads `stopped at the <step> step`. A script reading the table by column shifts. The core's messages, docs, pages and tests name each step, so adding a step no longer renumbers every later one.
- **`release check`'s declaration table sizes each column from what it prints (issue `0207`).** `assets.workflow` and `release.verbs`' default overran columns of a width written into the code, printing those rows' source out of line.
- **`release_repo` reads a url with no scheme by git's own rule, and reads the host from the authority alone (issue `0218`).** An ssh alias's form, `alias:owner/name`, now resolves to the repository git pushes to, where it was refused. A url that names an empty host, such as `file:///x/y`, is refused as naming no host. A url whose path holds an @, such as `https://evil.example/x@github.com/o/n`, is read as the host it names, `evil.example`, and refused as not `HOST/OWNER/NAME`, where 0.1.13 read it as github.com's `o/n`. `release_text_shown` now also leaves out a credential in text that belongs to no configured remote.
- **The changelog carries every note's sections, and a note it would render empty is refused (issue `0212`).** A `## ` heading is a section's when its first word is the section's name, so `## Fixed -- reaches every project` goes under `### Fixed`, its qualifier kept beneath it. Every note from 0.1.7 to 0.1.13 qualified its headings, and the reader matched them whole, so those releases had empty changelog entries; `CHANGELOG.md` is regenerated and carries them. The cut's pre-flight and `release check` refuse a note none of whose headings is a section's, unless its header says `changelog: none`.
- **The README's user route is the brew install (issue `0210`).** `## Install` opens with the tap, the full-name install and `devbin install --into`, and `dvb` is emitted from the brew install. Dev and opt are documented once, under "For the maintainer of a dev checkout", with placeholder paths. The install, upgrade, doctor, shell-init and use pages say the same, and `dvb`'s remedy when it finds no devbin is to install it with Homebrew.
- **devbin is MIT-licensed.** `LICENSE` and `lib/LICENSE.md`, held byte-identical by test, carry the MIT text, holder unchanged; `bin/devbin`'s header, the formula's `license "MIT"` and the README say the same.

## Fixed -- reaches every project

- **A manifest that cannot be read is named by devbin alone (issue `0215`).** `install --force` over such an install refused correctly, but its output also carried bash's own `Permission denied` from a redirect. The manifest is now tested readable before it is opened, and a read that still fails is failed and named.
- **The shipped files carry no text written for the development workroom, and a guard keeps it out (issue `0216`).** Comments, test titles, fixture identities, help pages and docs drop who said or found a thing and when, and pointers into the private tracking tree; each comment keeps its technical reason. Two output strings change wording: `fullcycle`'s note on a guarded release path, and `check`'s note on fork size. `tests/shipped.paths` is the one list of what ships, and `workroom.bats` reads every text file on it for collaborator handles, review credits, words for who settled a question, and pointers into the tracking tree. An entry the list includes must name a tracked file; an exclusion may name nothing, so the guard passes in a tree built from the list.

## Fixed -- devbin's own tree

- **The `fullcycle` arm for a refused cycle runs its tree check (issue `0211`).** A line carried two statements, so the check was passed to the assertion as arguments and never ran. A syntax-tree scan of the tests finds the shape nowhere else.
- **devbin's docs and help pages write no count down (issue `0208`),** and the comments naming the run log's extraction grammars no longer count them (issue `0219`), where copies already disagreed.
- **The DMARC fixtures carry documentation addresses (RFC 5737), and the harness arm reads a product file (issue `0214`)**, so the suite runs on a tree without the private tracking files.

## Known limitations

- **The tree's other written counts, and names that refer to an item by its place in a list, are still in comments and test titles (issue `0220`)**, for the next release.
- **The contract's proof has run in devbin's own trees only (issue `0213`).** Intent's leg waits on Intent vendoring this release, and the Linux VM's leg on its `brew upgrade` to it.
- **The Homebrew tap is private while devbin's repository is, and the formula's url is `ssh://` (ST0009)**, so `brew install` needs a GitHub ssh key on every machine.
- **ST0008 is not finished, and devbin does not run natively on Windows.** AC-2.1's clause on WSL 2 behind a VPN is not yet measured, and waits on a real Windows machine. AC-6.4, an adopting project running the smoke list on one of its own repositories inside WSL, is not yet received. The WSL leg is a CI runner's WSL 2, not a developer's machine, and the smoke list's server is a stub that writes a marker and sleeps, not a real application server.
- **The smoke list asserts the critic gate on the fixture carrying `intent/` by `check all`'s exit alone (ST0008 WP-06).** The gate is active there by construction, but its own lines stay in the job's `smoke.log` inside WSL and are not readable from CI.
- **A project's name has no shape, so no test holds the vendored set to naming none (issue `0202`)**; review holds it. The domain arm reads only the vendored reference yamls.
- **`text_shown` prints a url whose password holds a raw `/` (issue `0218`)**, a malformed url, as it stands.
- **No arm runs a `fleet` sweep with `--apply` end to end on a brew machine.**
- **An interceptor that forges AA is read as the zone's own answer, and the interception probe proves only what reaches TEST-NET-2 (issue `0193`)**, so a path that intercepts only some addresses leaves its replies without AA unexplained, though every read still says what came back.
- **`infra` follows no CNAME (issue `0196`).** A CNAME inside the zone whose target has no record of the type asked reads NOT MEASURED rather than as the absence it is, and for a chain of CNAMEs the line names the first hop, not the end of the chain.
- **Each remote has its own read-back in the push step, so two remotes that do not answer hold a cut for about 135 s each (issue `0194`)**, and a failure to make the read-back's scratch directory reads as a read-back that waited.
- **Install's line-ending block gives a project's newline-less last line a newline, since the block cannot follow it otherwise, and converts no file already carrying CR bytes (ST0008 WP-01).** doctor names each such file, and the fix is the operator's: `dos2unix`, or `upgrade --force` for a vendored one. Intent writes its own block for its hooks; devbin writes none for it.
- **A Windows shim with no extension, found where the Linux tool is missing, is not modelled by the Windows PATH arms (ST0008 WP-04)**; the runtime runs no such tool, and a missing Linux tool is already reported by `require` and the hints.
- **Some of devbin's own test files still build their fixtures per test (issue `0192`):** `upgradeoffer.bats`'s publish history and `releasecut.bats`'s project and remote carry each test's own directory in committed config, so a copy would not be the state a fresh build gives. Every file builds both caches in `setup_file`, including the ones that never install.
- **`fullcycle.bats`'s slow-y arm reads a charged wait green when the time before the prompt and after the gate passes about 3 s (issue `0199`)**, which load can cause, so on such a run it misses a regression of `0096` rather than reporting a false one.
- **`fullcycle`'s artefact check reads a `release/` it cannot list as holding no binary (issue `0177`).** Where a build tree cannot be listed and neither can its `release/`, the tree's warning and the summary's line for a tree listed while its own `release/` held no binary both say that `release/` holds no binary, which the check cannot know; the warning that it cannot be listed prints beside them. A tree that comes back between the check's tests reads as one it cannot search, or as one behind a link that cannot be followed exactly. Both fail closed, at rc 1.
- **Where git cannot say, whether a repository is there is read from the filesystem, and some cases read otherwise than git would (issues `0179`, `0185`).** A `.git` past a filesystem boundary still counts, where git's discovery stops; so does a `.git` git passes over, an empty `.git` directory or a dangling `.git` link; `GIT_CEILING_DIRECTORIES` is read only to its first newline, so a ceiling listed after one is not honoured; and a bare repository counts as none. So `fleet` reads a root whose only `.git` sits above it, past a filesystem boundary or past a ceiling listed after a newline, as `not its own checkout`. With no git on `PATH`, a gate's log directory in a repository gets no ignore file, and the run says git could not say whether it is tracked, with no line from git.
- **`vendor` does not refuse a devbin that is no checkout and has no manifest, so it names no variable there (issue `0178`)**; `upgrade` refuses one, naming `DEVBIN_INSTALL_PREFIX` where the variable placed it.
- **One frozen name freezes two projects where the same path sits under two roots (issue `0182`)**, since both carry one label.
- **A check `check lint` runs again alone is not always alone, and nothing times a check out (issue `0184`).** A check whose worker was killed can still be running when its file's second run starts; the second runs go one at a time; and a check that never returns holds the gate, in the second run as in the parallel run. The parallel run is still sized by CPUs, never by free memory. A lint gate killed outright leaves its scratch, and its workers finish into it; nothing in devbin kills the gate.
- **The release pre-flight still refuses a `tmp/` committed as a link to a directory outside the tree, and an untracked link on that path inside the tree (issue `0186`).** A `tmp/` that is a submodule passes until `tmp/release/` holds a `.gitignore` of its own, as after a run has written there, and is then refused, with git's `is in submodule` line. `--version` prints the bare commit over a tree whose status answered after skipping a directory it could not open.
- **devbin's own `docs/authoring-commands.md` still recommends `postgresql://user:$PGPASSWORD@host/db`, and arms in `gendoc.bats` and `neutral.bats` plant the shape (issue `0187`)**, so a secret scanner over devbin's own repository can find them; a project that vendors devbin carries only the vendored set, which is clean.
- **A dry run's `no step failed` speaks for the steps it reaches (issue `0181`)**; the NOT REACHED list above it names what it could not predict.
- **`release` leaves out of a url only what it can read as a userinfo (issues `0188`, `0189`).** A url it cannot read that way reaches its refusals and git's words whole, as one holding a raw `/` in its userinfo does where the url has no scheme, where no `:` stands ahead of that `/`, or where the password runs only digits up to it. Where a raw `/` follows a raw @ in the password, the userinfo ends at that @, as git reads it, and the rest of the password reaches them as the host and the path. A `://` anywhere in a url is read as its scheme's, and a secret elsewhere in a url, as in its query, is not looked for. In the scp form an @ in the path's first segment ends the userinfo, and so does an @ in the path of a url whose password holds a raw `/`, so the host, and the path ahead of that @, are left out too. A remote call killed at its bound prints none of what git said and leaves git's words in a file under `TMPDIR`. ssh's refusal names its user.
- **A manifest written before 0.1.9 keeps its recorded path through that project's first upgrade from a runtime older than 0.1.9 (issue `0153`)**, which runs that older runtime and records the path again; the upgrade after it, run by the new runtime, writes the kind of source, and `fleet upgrade --apply` makes both passes itself. Both old forms still resolve meanwhile.
- **The machine's frozen list for `fleet` is declared nowhere yet (issue `0154`).** devbin's built-in list is empty, so a sweep plans an upgrade for every project the roots reach, archived ones included, until the machine declares `DEVBIN_FLEET_FROZEN`.
- **A project's own `.gitignore` in a gate's log directory is left as it is, even one that ignores nothing (issue `0157`)**, so that directory can still dirty the tree: where it is `tmp/release` the release pre-flight still refuses, and elsewhere the cut fails at the commit step once a gate writes there. Where git cannot say what a repository tracks, as of one it refuses to read, no ignore file is written and the run says so; one is written only where no `.git` sits at the project root or above it, as far up as git's own discovery looks (issue `0179`).
- **The cargo config order `check targetdir` and `fullcycle` read is cargo 1.99.0's as measured (issue `0164`)**: with both `.cargo/config` and `.cargo/config.toml` in one directory, cargo reads `config`. A build line run from outside the workspace does not read the workspace's config, so `fullcycle`'s offered `build.target-dir = "target"` does not reach it.
- **A `CARGO_TARGET_DIR` that resolves to `/` through `.`, `..` or a link reads "resolves to /, outside the project" rather than "is the filesystem root" (issue `0166`)**, and is refused all the same.
- **`check targetdir` does not see a cargo config inside a directory `find` cannot read at all, or deeper inside one it can search but not list (issue `0163`)**, nor a directory whose ACL denies only search (issue `0145`). A workspace below the project root whose own config pins `target-dir = "target"` fails over an unreadable directory beneath it (at the project root that target is the shared tree, and it passes), since only what the directory hides tells a member from a second workspace; the failure says to make it readable or move it out of the workspace. Where `find` meets a directory it cannot read, `check targetdir` walks a second time, about 1.8 times one walk.
- **`clean` still never removes `<root>/target` for a nested crate with no root `Cargo.toml` (issue `0167`)**; `check targetdir` does not endorse that tree instead, since removing it would mean running cargo inside `clean`.
- **`fullcycle`'s artefact check does not see a release lost while another was built, the tree's own or a target triple's, and does not read custom profiles (issue `0168`).** A per-session directory built with `CARGO_CACHE_RUSTC_INFO=0`, or under a `build.build-dir` set to another directory, carries no `.rustc_info.json` and is read as a target triple.
- **cargo is asked from each crate's own directory (issue `0150`)**, so a build line that runs cargo from elsewhere, or passes `--target-dir` or `--config` itself, is not followed.
- **The lint arm skips where shellcheck is not installed, and reaches a change only in a run that includes `contract.bats` (issue `0155`).** An explicit empty `senders.*.dkim.type` is now refused, and no test holds that (issue `0161`).
- **A commented key in the reference config with prose directly above and below it reads as prose, so the schema check does not see it (issue `0173`).** None is written that way today.
- **Outside the `fleet` roots, an install whose `bin/.devbin/lib` cannot be searched passes the audit (issue `0175`)**, since that walk digests nothing; under the roots the audit still fails it.
- **The neutrality tests do not read a citation or a count split across two lines, other than a line ending in "issue" or one opening with an issue-shaped number, nor a line opening with `#` inside a heredoc or a multi-line string, nor a bare four-digit number, nor a count of machines (issue `0172`).** Each would be indistinguishable from innocent text in the tree; the test file declares them.
- **The `MIX_ENV=prod` refusal does not reach a project's own `db` handler (issue `0132`).**
- **The `fleet` census does not look inside `~/Library`, `~/.Trash` or anything reached only through a symlink (issue `0116`).**
- **The shipped pages are checked for prettier stability only where prettier is installed.**
- **`infra` checks DNS and mail records only.** The Fly runtime and `infra mail dmarc check` are devbin's ST0006, which is not built.
- **Intent and one other project still release with their own orchestrators.** Intent runs devbin's `release check` and `release attach` beside its own.
- **The vendored-set scans fold case in ASCII letters only (issue `0205`)**: under C, GNU grep's `-i` does not fold the dotless i (U+0131) to `i` or the long s (U+017F) to `s`, so a lookalike of a name in those letters would pass the case-insensitive scans. The vendored set holds no byte outside ASCII today, and nothing refuses one.
- **The arm that holds a runtime to one digest under every locale runs where the runner has an en_US UTF-8 locale (issue `0204`)**: on CI's Ubuntu and macOS legs, and not on the WSL 2 leg, which has none and says so in its skip.
- **Assets reach a release after it is published (ST0008 WP-08).** That works while immutable releases are off, as they are on devbin's and Intent's repositories, as measured; a repository that turns them on needs its release object made as a draft first, which the core does not do.
- **`release status` and `release attach` read a release's assets as consistent, not as complete (ST0008 WP-08).** The object row reads `already` when `SHA256SUMS` names exactly the release's other assets and each of its lines equals the digest GitHub reports for that asset, and an attach that reads the same stops there, reading no run. Neither reads the run's artifacts to decide it, so an asset taken off both the release and `SHA256SUMS` is not seen, and running the attach again does not put it back. The attach writes `SHA256SUMS` last, so one that stopped part-way reads `pending`.
- **An attach reads its assets from the run's artifacts, which GitHub keeps for 90 days unless the workflow or the repository says otherwise (ST0008 WP-08).** A release whose attach finished needs no artifact: running the attach again reads `already` however long ago they expired. If the earliest successful run's artifacts expire before its release's attach has finished, the attach cannot finish: it ships that run's files only, so a run started later cannot stand in, and whether a rerun of that run (`gh run rerun <id>`) gives them back is not measured.
- **Each call the attach makes to GitHub is cut off at 120 seconds, and its reads of the release object, its `SHA256SUMS` and the run list at the time its wait has left, never below 15 seconds (ST0008 WP-08)**, so an asset larger than one upload or download can move in that time is out of reach.
- **The earliest successful run is chosen by its creation time (ST0008 WP-08).** A failed run rerun to success keeps its id and, as GitHub's re-run attempts are understood, its creation time, so it can become the earliest after another run's files shipped. An attach that has finished reads no run and stays `already`; one that has not refuses that run's other bytes, never replacing what shipped. Not measured.
- **The release core's reads before the first push are not time-limited**, nor is `release status`.
- **A cut under `object: ci` depends on the project's workflow running.** If CI does not start a job, the tag and the pushes stand and the object step fails at `object_wait`.
