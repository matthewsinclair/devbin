# devbin 0.1.0

**The first release of devbin.** Everything below has been running in production on thirteen projects for weeks; the tag records a state that was already true rather than announcing a change.

Devbin is a dev launcher you **declare** rather than write. Most projects grow a `bin/<project>` script -- a dispatcher, a helpers library beside it, and a help text that has to be updated by hand every time either changes. Devbin is that script, extracted once.

It came out of four real projects whose launchers had independently converged on the same shape and then drifted. Between them they carried four copies of one helpers library (50-80% identical), four hand-maintained help heredocs totalling roughly 95 KB, and eight hand-written `test_all` / `check_all` functions. A hardening learned in one of them had reached none of the others, and could not, while there were four copies. Devbin is the one copy.

## Added

- **A declarative dispatcher.** `bin/devbin` plus a vendored runtime under `bin/.devbin/lib/`, driven by a project-owned `bin/.devbin/config.yaml`. The commands a project offers follow from what it declares.
- **Built-in commands** -- `test`, `check`, `fmt`, `clean`, `build`, `version`, `docs`, `new`, and the surfaces (`server`, `iex`, `cli`, `repl`) -- scoped to the languages the project declares, so an Elixir project never sees `cargo` gates and a shell project never sees `mix`.
- **Sealed gates.** A gate's verdict is a **file**, not terminal output: `test all` writes `tmp/test/<stamp>.<SUFFIX>.{out,errors}` per option, and the `.errors` companion is empty exactly when a completed run was green. CI reads the file; a human reads the scroll.
- **A toolchain gate that reads the deploy image.** `check toolchain` proves the running versions match the `.tool-versions` pin and, where a Dockerfile builds the deploy image, that the image's pinned `ARG` versions agree with the same file. A project with a `fly.toml` and no Dockerfile fails rather than passes: a deploy nobody can check is a breach, not a gap.
- **A free `all`.** Any command with more than one option gets `all` synthesised from the option list, so adding an option puts it in `all` in the same edit.
- **Generated help.** `devbin help` is derived from what actually resolves, so it can neither list a command that does not exist nor omit one that does.
- **Project commands, first class.** An executable dropped in `bin/.devbin/cmd/` is registered with no config edit and no help edit. A project handler shadows a built-in of the same name, totally and by design, and `doctor` announces every such shadowing rather than leaving it silent.
- **`install`, `upgrade`, `vendor` and `doctor`.** Devbin vendors itself into a project; the devbin doing the installing is whatever you are running, so a fresh clone and an already-installed project seed the next one by the same path. `upgrade` re-syncs the vendored runtime, refuses to overwrite files the project has edited, and records what it refused. `vendor` compares the vendored runtime against the source it came from -- a different question from `doctor`'s tree-vs-manifest, and the two are deliberately not merged.
- **A checksum manifest** at `bin/.devbin/manifest.sha256`, checksummed against the TARGET rather than the source, so a copy that silently failed cannot verify clean. It carries the devbin version, the source path and the source commit.
- **`shell-init`**, emitting a shell function that finds the nearest `bin/devbin` by walking up from `$PWD`, with a `DEVBIN_SOURCE` fallback so the function can bootstrap a project that has no devbin yet.
- **`fleet`**, auditing every devbin install on the machine and generating a report of the installs from what it finds.
- **`fullcycle`** -- from a total clean: remove the cargo trees, rebuild, test. **Destructive by design and it says so.** It snapshots the PATH symlinks resolving into the tree *before* it removes anything, re-checks them after, and goes red naming any it darkened and did not restore. Read `## Known limitations` before relying on it.

`0035` is parked deliberately rather than open by neglect.

**What this section said until 2026-09-06, because the correction is the finding.** It read *"Eleven issues are open. Two are `high` and both concern `fullcycle`; read them before using that verb."* Every issue it named as urgent -- `0045`, `0046`, `0047`, `0048`, `0050`, including both `high` ones -- has since been closed, and `0056` was filed after it and never added. So it warned a reader away from two defects that no longer existed while omitting one that did, in the section whose entire purpose is honesty about what is known.

**It also named nine issues while claiming eleven**, which is the only reason the drift was visible at all. A number beside its list is what makes a stale list arguable; a list alone just reads as true.

**`fullcycle` is still the verb to read about before relying on it**, but for a different reason than the one this section used to give: it is destructive by design, not defective. `0057` and `0058` were both found in it on 2026-09-06 and both are fixed, and both were the same class -- behaviour determined by the operator's environment, invisible to every environment lacking one.

### The machine install (2026-09-06)

A project used to vendor straight out of the tree devbin is edited in, and that tree can be dirty: **five of thirteen projects were running bytes stamped `+dirty -- THESE BYTES MATCH NO COMMIT`**, two of them vendored ten minutes apart from the same dirty tree and carrying byte-identical provenance over three differing files. Publishing is now gated on a clean checkout, and the install is a project-shaped tree with the project half missing -- so `bin/devbin` refuses to start in it and it can only be vendored FROM.

Homebrew was considered and dropped: a tap would have made devbin easier to obtain while leaving untouched the thing that was actually wrong, which is what the source could be.

**Known gap, stated rather than discovered:** the warning that a source is BEHIND you -- the one that stops an upgrade silently reverting your runtime -- computes ancestry with `git merge-base` in the source. An install has no history, so that answer is `unknown` and `unknown` is silent. It is the ordinary case for every project swept onto the install. `devbin vendor` still shows exactly what would change, before it changes.

## Requirements

- **bash >= 5.** The dispatcher checks its own interpreter and refuses anything older with a `brew install bash` remediation. macOS ships `/bin/bash` 3.2.57, so a stock Mac needs Homebrew's bash. That refusal is deliberate: devbin targeted 3.2 until 2026-08-24, when the floor was inverted to point at what the projects using it actually run.
- The guard block itself stays parseable by bash 3.2, so the refusal arrives as a message rather than as a syntax error that explains nothing.

## Installing

Devbin publishes itself to a **machine install**, and projects vendor from that rather than from the working tree devbin is edited in:

```
cd <the devbin checkout>
bin/devbin install                 # publish -- REFUSES on a dirty tree, no --force
bin/devbin upgrade                 # replace an existing install
```

Seed a project from it, or upgrade one:

```
devbin install [--into <dir>] [--name <n>] [--alias <a>] [--lang <l>] [--force]
cd <project> && bin/devbin upgrade
```

And bring every project on this machine forward at once. Dry run by default; `--apply` writes:

```
cd <the devbin checkout> && bin/devbin fleet upgrade
```

Confirm what you are running:

```
bin/devbin devbin version      # the framework, and the commit it was vendored from
bin/devbin version             # this project, and the tree it is standing in
```

## Why 0.1.0 and not 1.0.0

Devbin makes no stability promise yet. The `devbin_version` constraint a project declares uses a caret, and a caret on a `0.x` version admits the next minor here -- deliberately not what semver's own text says, because the strict reading pins every project to a patch series and makes `upgrade` a lie. The seam between what devbin owns and what a project owns is stable in practice and has not been declared frozen.

**And two `high` issues are open against a destructive verb.** That is compatible with a `0.x` release which names them; it would not be compatible with a `1.0.0` claiming stability.
