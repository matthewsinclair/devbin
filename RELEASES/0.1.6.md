version: 0.1.6
date: 2026-09-22
headline: CI runs macOS on a release tag and on demand, cancels superseded pushes, and starts no run for a push that only moves a board.
status: released

## Fixed

- **The macOS job runs on a release tag and on demand, never on a push, and a superseded run is cancelled (issue `0108`).** A private repository bills a macOS minute at ten times a Linux one, and devbin's macOS job on every push was about 80% of the account's weighted Actions minutes in September 2026: 740 macOS minutes, 7400 weighted, of 9149. Nothing cancelled a run a newer push had overtaken. The job is now gated on `github.ref_type == 'tag' || github.event_name == 'workflow_dispatch'`, which asks the ref's TYPE and never a tag's spelling, and `on.push.tags` carries both release forms (`v1.2.3` and `1.2.3`) so one filter serves every project that copies the workflow. `Test Summary` takes its inputs through `env` rather than inline expressions, so it is a script a test can RUN on a given combination of results: it accepts a skipped macOS leg exactly where the workflow did not ask for one, refuses a skip on a tag or a dispatch, refuses a result it does not recognise rather than defaulting to the permissive branch, and refuses an empty result on any event. The concurrency group carries the event as well as the ref, because a push and a dispatch on `main` share a ref and would otherwise cancel each other. `release.yml` is untouched: each tag is its own ref, and cancelling a release run mid-publish is the one place this rule should not be applied mechanically.
- **Nothing devbin vendors is shaped like a home directory path (issue `0109`).** The fix for issue 0069 wrote an example of what an empty `HOME` would record into a comment in `lib/helpers`, and that example was a home-shaped path. It shipped in v0.1.1 to v0.1.5 and every consuming project vendored it. One consuming project's release-archive guard refuses any tracked file matching `/Users/<name>` or `/home/<name>`, and cannot tell prose from a path -- which is not a thing a pattern can be asked to do -- so a consumer's CI went red on devbin's bytes and stayed red for four days. The comment describes the example rather than writing it out, and a new arm runs the consumer's own predicate over `vendored_paths`, with a control proving the probe can still match both halves of it.
- **Every action runs on a Node 24 major, and a push that only moves coordination state starts no run (issue `0110`).** `actions/checkout@v4` runs on Node 20, which GitHub has deprecated, so every job carried a warning; both workflows are at v7. `on.push` ignores paths under `intent/whiteboard/**` and `intent/.canon/**`, justified by what no job READS: nothing in the workflow opens either tree, so a push touching only those has nothing to verify. **CORRECTED AFTER RELEASE, on the day of the cut, and the tag's copy of this file still carries the wrong version** -- what shipped listed `intent/whiteboard/**` alone and justified it with "board-only commits were 47% of this repository's commits over the preceding 30 days". That figure was wrong two ways at once, and either alone reads as a perfectly reasonable number. **Wrong unit**: GitHub decides per PUSH, not per commit -- "When all the path names match patterns in `paths-ignore`, the workflow will not run", against "a two-dot diff between the head and base SHAs" -- so one code commit carries a whole push past the filter however many board commits ride with it, and 47% of commits is 13% of pushes. **Wrong era**: the thirty-day window straddled the move from hand-authored boards to generated views, and a generated board write emits a canon event outside the ignored path, so 13% of pushes is 0% in the fortnight before the cut. Re-measured at the push, using this workflow's own run head SHAs as the real push boundaries: **the line as shipped suppressed nothing, and had suppressed nothing since 2026-09-03**; with `intent/.canon/**` beside it, 6 of the last 32 pushes. The justification is now the mechanism rather than a rate, because a rate decays silently and does not transfer between projects -- measured the same day, the same pair is worth 13% of pushes at devbin and 4% at Utilz. Path filters are not evaluated for pushes of tags, so a release run is never suppressed by either line.

## Known limitations

- **The workflow tests hold what the YAML SAYS, and the experiment this release was has now been READ.** The arms pin the triggers, the condition, the concurrency key and the summary's decision; what GitHub does with them rested on documentation alone until the cut. It no longer does. Cutting this release pushed the commit and the tag, and the two runs landed one second apart: on `main` `Test Summary` printed `test-macos = 'skipped'`, `macos required = 'false'`, `All required checks passed.`; on the tag it printed `test-macos = 'success'`, `macos required = 'true'`, the same verdict, after a macOS leg that ran 21m17s with its tests, its gates and its bash-3.2 refusal control all green. So **`github.ref_type` does resolve to the ref's type on both events, a tag push does start a run, `paths-ignore` did not suppress it, and neither run cancelled the other** -- measured facts now, not documented ones. **The limit that REMAINS, and it is the half worth keeping**: two of the summary's four branches have been driven in production and both were the ACCEPTING ones. `required=true` with a skipped leg, and an unrecognised or empty result, are still held by arms alone. A script that has only ever been asked to say yes has not been observed saying no, and promoting the accepting branches to measured fact is not permission to promote the refusing ones with them.
- **Nothing the macOS runner supplies is exercised between releases**: its image, Homebrew, and the Intent formula `check critic` installs are met at a tag. `gh workflow run tests.yml --ref main` asks for the full set on demand, and `docs/releasing.md` says to use it when that side has been quiet.
- **A cut now produces two runs of the tests workflow and only the tag's is the whole verdict**, and an intermediate pushed commit can have no verdict at all, because a newer push cancels it or a board-only push starts nothing.
- **Intent and one other project still release with their own orchestrators, and Utilz has declared the release core but not yet cut with it.**
- **`fullcycle`'s overhead is measured across the whole cycle, not per phase.**
- **The release core's reads before the first push are not time-limited**, nor is `release status`.
- **A cut under `object: ci` depends on the project's workflow running.** If CI does not start a job -- a billing block stops jobs before they start -- the tag and the pushes stand and the object step fails at `object_wait`.
