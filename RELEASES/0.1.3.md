## Fixed

- **A devbin read no longer writes the git index it reads, and a project's `project.referent` runs without git's optional lock by default (issue `0094`).** A plain `git status` on a stale index takes git's optional index lock and rewrites `.git/index`, so a command meant only to read could fail a concurrent commit with `index.lock exists`. The dispatcher evaluates `project.referent` on every devbin invocation, and three projects declare one that runs `git status`, so every devbin command there could write into `.git`; a read-only `doctor` sweep of the projects on 0.1.2 found it. A referent now runs with `GIT_OPTIONAL_LOCKS=0`, set for the referent alone and never for a gate; a referent that wants the lock sets `GIT_OPTIONAL_LOCKS=1` itself. devbin's own reads had the same defect and are fixed with it: `--version`, `fullcycle`'s header and the release core's dirty-tree check, which the read-only `release check` runs. The release check skips the lock and nothing else, so it still reads the same repository the release writes to under an inherited `GIT_DIR`. `git_readonly` now lives in `lib/helpers` alone, where `lib/install` and `fleet` reach it.
- **The overhead line says how many of the suites it counted reported zero time (issue `0095`).** cargo prints a `finished in` line for every test binary and doc-test pass, empty ones included, so `across 4 suite(s)` could describe one suite that ran and three that were empty. The count stays -- cargo rounds to two places, so a binary running a few fast tests also reads zero, and dropping those would undercount -- and the line adds `, K of them reporting zero time` when K is more than zero. The line is unchanged when no suite reads zero.
- **`fullcycle` asks before its gate opens, so a person's time at the prompt is no longer counted as overhead, and the log records what was agreed and how long the answer took (issue `0096`).** The prompt ran inside the gate, after its clock had started, so the time a person spent deciding was reported as apparatus overhead: measured in one consuming project, about 86 seconds of one run. The notice, the preview of what would be removed and the question now come before the gate's header, and an `n` or a missing terminal stops before any log exists. The gated run's first line records the consent and the wait, eg `devbin: confirmed y to clean rust --force-blocked --force at the prompt after 42s -- before this gate's wall began`, or that `--force` was given and nothing was asked. The overhead line is unchanged. The rule that says whether a person is at the terminal moves into one helper, `stdin_tty_flag`, which the gate and the prompt both use.

## Known limitations

- **Utilz, another project and Intent still release with their own orchestrators.** Utilz is adopting the release core now, through its own ST0019; the other project and Intent follow (ST0007 WP-08).
- **`fullcycle`'s overhead is measured across the whole cycle, not per phase.** A cycle's wall covers its clean, build and test phases together.
- **The release core's reads before the first push are not time-limited**, nor is `release status`: a remote that hangs there holds the run, but nothing has been published and nothing is written.
- **A cut under `object: ci` depends on the project's workflow running.** If CI does not start a job, the tag and the pushes stand and the object step fails at `object_wait`; the workflow's run for the tag has to be re-run before the cut can finish.
