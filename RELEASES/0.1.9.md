version: 0.1.9
date: 2026-10-07
headline: devbin ships its owner's licence and names no one who uses it, a gate's logs stop dirtying a project's tree, `check critic` steps aside outside Intent projects, and `check targetdir` and `fullcycle` read cargo's build trees as cargo builds them.
status: released

**Why this release exists.** Every open item is fixed forward as an issue and bundled into one release, and every open issue closes before that release is cut. So it closes every issue filed since 0.1.8, `0151` to `0176`. It opens with `0152`: devbin is vendored into projects its owner delivers to clients, so the runtime now carries its owner's licence and names no one who uses it, and `0172` takes the last description of the operator's own projects and devbin's tracker out of what a consuming project receives. It keeps a 0.1 number, as 0.1.8 did, because every consuming project pins a `^0.1` caret.

## Licence

- **devbin carries its owner's licence, and the runtime it vendors names no one who uses it (issue `0152`).** `bin/devbin` and everything under `bin/.devbin/lib/` now ship `LICENSE.md`: Geodica Ltd (geodica.com), all rights reserved. A client that receives a project carrying a vendored devbin as part of an engagement may use, copy and run that copy as part of that project, and takes no ownership. The repository's root `LICENSE` is the same text, byte for byte, and replaces the MIT licence it carried. Every comment, page and example in the vendored runtime keeps its reasoning and drops who, where and when: it names no project that uses devbin, no person or session, no other repository's commit, issue or CI run, and no path on one machine, and its examples use a project called `demo`. A test refuses each of those by its shape, and keeps no list of who uses devbin; a name in prose is review's to hold, and the test says so.

## Changed -- a script or a config may get a different result

- **A project's manifest records the kind of devbin it was vendored from -- `install`, `checkout` or `project` -- and never where that is on the machine (issue `0153`).** `install` and `upgrade` wrote `# source: <path>` into `bin/.devbin/manifest.sha256`, which every project that vendors devbin tracks; written home-relative since issue 0069, it carried no login name but still carried the operator's directory layout into every repository that vendors devbin, those delivered to a client included. Now the machine says where. An install is placed through `DEVBIN_INSTALL_PREFIX`, or else a one-line pointer kept outside every repository, `$XDG_DATA_HOME/devbin/home` (its XDG default under the home directory when that variable is unset or not absolute), which a publish to `install.prefix` writes and the install's own upgrade rewrites; a checkout is placed through `DEVBIN_SOURCE`, and a project through nothing, so a bare `upgrade` from one asks for `--from`. A pointer that is empty, a link to nothing, relative, or names a tree that is no install or whose manifest cannot be read is named as such, never read as absent, and `upgrade`'s refusal of a tree `DEVBIN_INSTALL_PREFIX` names that is no devbin says the variable named it. A source devbin cannot classify is refused before `install` or `upgrade` writes anything, and `upgrade` and `vendor` refuse a source this machine cannot place with the reason and "name one with --from <dir>", where they said "no source recorded". A manifest written before this release, home-relative or absolute, still resolves, and keeps its recorded path through that project's first upgrade to 0.1.9, which runs the project's older runtime and records the path again; the upgrade after it, run by 0.1.9's runtime, writes the kind, and `fleet upgrade --apply` makes both passes itself. `fleet upgrade` refuses to sweep unless the machine names the install it distributes, says what names another and what would change that, and plans every recorded path as a repoint to the kind, even one that names the prefix.
- **`check critic` and `docs agents` are inactive in a project with no `intent/` directory, so `check all` passes in a project that is not an Intent project (issue `0156`).** devbin activated Intent's critic in every project and ran it in `all`, so in a project that does not use Intent, `check critic` died naming Intent's own remedy and `check all` failed with it; the page offered disabling it as a workaround, the starter config did not apply it, and `docs agents` had the same shape. Now `check critic` exits 2 there naming `intent/`, `all` counts it inactive, and `help --why` says why, naming the declaration that runs it anyway: a declared `commands.check.options.critic` still runs. Without `intent/`, `docs`, which ships only `agents`, is unavailable, and every surface says what its option needs in one sentence. The test is the directory, never Intent's config, so an Intent project that has lost its config still fails loudly, naming the config; a directory or a link counts, a link to nothing included, a file named `intent` does not, and the question is asked of the project root, never of the current directory.
- **A gate's log directory ignores itself, so a project's tree stays clean after its first `check` and `--version` stops reporting `+dirty` (issue `0157`).** Every sealed gate writes its logs under `tmp/<command>/`, and nothing in devbin arranged for that directory to be ignored, so in a project whose `.gitignore` did not cover `tmp/` the first `check` left `?? tmp/` in `git status`, and from then on `--version` and `fullcycle`'s header called the tree `+dirty`; only the release pre-flight knew, and it probed `tmp/release` alone. Now `*` is written into `tmp/<command>/.gitignore` before the first log lands -- devbin's own output directory, never the project's `.gitignore` -- and only in a directory strictly inside `tmp/`, resolved physically: never `tmp/` itself, never at or above the project root, never through a link out of the tree, never where a `.gitignore` already is, and never in a directory git tracks, or where git finds a repository but cannot list what it tracks. The file is created and written in one exclusive open, so another writer's file is never overwritten, and a write that fails is said and the run goes on. The release pre-flight asks the same rule without writing, so a dry run and a cut reach the same verdict at step 2.
- **An infra profile's `senders.*.dkim.type` takes only `CNAME` or `TXT`, and any other value is refused by name when the profile is read, before any query (issue `0161`).** The key took any value, so `cname`, `Cname`, `txt` and `bogus` were accepted, and `infra check` passed the value as written to the DNS reader, which keeps only answers whose type equals it exactly; dig prints types in capitals, so `cname` kept nothing and the check reported a HALF PAIR over a zone carrying the record, at rc 1. The suite's fake dig refused `cname` outright, which is why the suite could not see it. Both rows now carry the two words, the validator names the key and the words, and the infra page and the reference profile's comment state them. An absent type still defaults to `CNAME`; an explicit empty one is now refused.
- **`check targetdir` fails a cargo config that forks a crate beneath a directory it cannot read, and stops failing a config over such a directory that moves nothing (issue `0163`).** It cleared a `.cargo/config` as harmless when every crate cargo answered for beneath it built into its own target, so a config sending a second workspace beneath an unreadable directory into its own `target` -- a fork -- printed that no cargo config was in play, at rc 0, and failed only once the directory was made readable. Now, over each such hole, cargo is asked where a throwaway crate that is its own workspace would build, from the hole's parent or from inside a hole it can search but not list, reading every config that applies there, nearest first, and the walk is in play unless the answer is the probe's own target, the shared tree or the machine's tree. A hole no config applies at puts nothing in play, a config that moves nothing over a hole is no longer failed, a config above the project that the project's own config overrides does not fail it, and a config inside a directory the walk can search but not list is read and judged. A workspace's own `target-dir = "target"` beside a docker volume stays green, and one below the project root over a hole beneath it, which 0.1.8 passed, now fails, since only what the hole hides tells a member from a second workspace; at the project root that target is the shared tree, and it passes. Where a probe's answer put the walk in play, the failure names the tree a crate there would build into and says to make the directory readable to the user running the check or move it out of the workspace; where the probe cannot answer or the machine's tree cannot be measured, it says which.
- **`check targetdir` reports, rather than fails, the machine's cargo config over a crate it cannot see, and `fullcycle` names that config and offers a remedy `check targetdir` passes (issue `0164`).** The machine's own cargo config was judged three ways: `fullcycle` refused a tree only that config sent outside the project without naming the file, and pointed at `check targetdir`, which passed the same tree; and `check targetdir` failed a machine config over a hole where no crate was answered, an `include` that moves nothing among them, while the same config over a visible crate was only reported, at exit 0. Both commands now read it one way. In a config directory they read the file cargo reads, `config` where it can be opened, else `config.toml`, which is cargo 1.99.0's order as measured (with both there, cargo reads `config` and warns, even when `config` names nothing), where `check targetdir` read `config.toml` first. A tree is attributed to the project root's config first, then the machine's, else to no named cause, so `fullcycle` no longer refuses as the machine's a tree the project's config names. Wherever no crate here builds with the machine's config, `check targetdir` reports it as cargo reads it -- where it moves the tree, that it moves none, or that it could not be measured, because cargo failed, in cargo's words, cargo is not on PATH, or a config at or above `TMPDIR` clouds the probe -- so a dotted key, a trailing comment or an `include` is reported too, and the passing line no longer says there is no override in a config that sets one. `fullcycle`'s refusal of a tree only the machine's config sends outside the project names that file, and offers `build.target-dir = "target"` in the workspace's own `.cargo/config`, or `.cargo/config.toml` where it has none, which cargo reads before the machine's and `check targetdir` passes as the workspace's own target; setting `CARGO_TARGET_DIR` inside the project, the remedy the issue first prescribed, would have turned a passing `check targetdir` into a failing one for every value but the shared tree.
- **`check targetdir` endorses `<root>/target` as the shared tree only with a `Cargo.toml` beside it, the tree `clean` removes, so it no longer passes what `fullcycle` then fails (issue `0167`).** For a crate in a subdirectory, such as `native/cli` with no root `Cargo.toml`, check called `<root>/target` the shared tree, though `clean` removes a tree only with a `Cargo.toml` beside it: with the variable unset it said cargo builds into the shared tree while cargo answered `native/cli/target`, `CARGO_TARGET_DIR=<root>/target` "points at the shared tree" at rc 0, and a config naming `../../target` built "into the shared tree", after which `fullcycle` failed at rc 1. `clean`, `fullcycle` and `check targetdir` now ask one test, so the three cannot disagree. With no root `Cargo.toml`, the passing line says cargo builds each crate into its own workspace target; `CARGO_TARGET_DIR=<root>/target` fails, saying `clean` never removes it and `fullcycle` fails a cycle built there, and to unset it; a config naming `<root>/target`, from a crate or from the root, fails as a fork; an empty `CARGO_TARGET_DIR` is told only to unset it; and over an unreadable directory `<root>/target` no longer clears a config. With a root `Cargo.toml` nothing changes.
- **`fullcycle`'s artefact check reads a cross-compiled profile under `target/<triple>/` beside the tree's own (issue `0168`).** It read only a tree's own `debug/` and `release/`, so `--release --target <triple>` beside a host debug build read as RELEASE ARTEFACTS lost at rc 1, and a debug build under a triple whose release was lost read INCONCLUSIVE at rc 0. A profile now counts as built when the tree's own `debug/` or `release/` holds a binary or a triple's does, a triple's directory being one in the tree, not a link, holding cargo's lock file, `.cargo-lock`, in its `debug/` or `release/`, and no `.rustc_info.json`, as cargo writes it with or without `build.build-dir` (measured on cargo 1.99.0). The first setup passes and the second fails as lost; the read after the clean names a triple's release kept through it and does not compare that tree; a per-node directory inside the tree stays apart, its release never standing for the tree's. What the check cannot read is named rather than read as lost -- a profile directory it cannot list, a directory in the tree it cannot search, which may be a triple's, and a tree it can search but not list whose own `release/` holds no binary -- each on its own line, and the cycle fails as INCOMPLETE. A directory in a shared tree that the check cannot search now fails the cycle as incomplete, a per-session directory another user owns included; the page says so.

## Fixed -- reaches every project

- **`gate_exec` runs a tool the way a gate does -- stdin from `/dev/null`, and `DEVBIN_GATE_TTY` saying whether a person is there -- and a project's own handler can call it (issue `0158`).** `run_gate` wrote that rule inline, so a project's own handler that ran a gate tool directly got neither half: a prompting tool blocked at a terminal while an agent read EOF. A project measured four such gates in its own tree and asked for one named function. `gate_exec <command>...` now lives in `lib/helpers`, which a scaffolded handler sources, and `run_gate` and the release cut's `version set` and `after:` lines all call it; the authoring guide and the handler template say to. Inside a gate the flag the gate read is kept for the tools it runs, so a release's `after:` line still sees the person the cut's gate saw, while a devbin started inside a gate reads its own stdin, as issue 0088 has every gate do. An empty command is refused with a warning.
- **A manifest that records no files vouches for none: `doctor` fails it by name, and `upgrade` and `vendor` refuse it as they refuse a missing one (issue `0159`).** `doctor` counted the manifest's lines with a status it threw away, so a manifest cut to its `#` header passed as `0 vendored files intact`, every file under `bin/.devbin/lib/` was listed as unowned with the advice to delete it, and the run ended `0 failed`; over the same manifest, `upgrade --from` overwrote an edited file at exit 0, issue 0146's hazard arriving through a manifest that is there. Now `doctor` fails it by name and never counts its files intact or unowned, `upgrade` refuses it unless forced, with the remedies it gives for a missing manifest, and `--force` says every file is replaced unchecked without sending the reader to `vendor`, which refuses it too. `doctor` reports an install whose manifest names no version as running `unknown`, and `devbin --version` refuses it; neither reports the project's own `VERSION`. `doctor`'s counts no longer have a status to lose, and a catalogue row it cannot read fails its shadowing check by name, where the row's shadow was dropped and the check passed.
- **`<command> all` over a command-level `run:` with no words says the line holds no words, rather than sending the reader to the bare command (issue `0160`).** An empty or blank `run:` was refused twice, and `<command> all` said "'bin/devbin <command>' runs it", after which the bare command refused the empty line itself. Both exited 1, so there was no false green; the pointer to a command that cannot run was the defect. `all` now refuses with the bare command's own sentence, that `commands.<command>.run` holds no words; a `run:` with words keeps its pointer, and the exit status and the count line are unchanged.
- **A release's scratch directory is refused inside the project however the project root is spelled, a leading `//` included (issue `0162`).** `release_scratch` resolved the project root and `TMPDIR` with its own copies of the physical-directory step, which keep a leading `//`, pass no `--`, read CDPATH for a relative path and drop a trailing newline from a name, so `release_scratch //<project>` with `TMPDIR` inside the project returned 0 and made its scratch there; the dispatcher does produce such a root, run from a directory entered as `//`. Both paths now go through `physical_dir`, the one turn of a directory into its physical path, which spells a leading `//` as `/`, and a scan holds that step to `physical_dir` in `lib/`.
- **A `CARGO_TARGET_DIR` of `/`, under any number of slashes, is judged the filesystem root wherever devbin asks, never "outside the project" (issue `0166`).** The helper that judges whether a build tree lies outside the project had its own guard, which knew only "not absolute", and tidied `/` to an empty string whose status nothing read, so `/`, `//` and `///` all came out "is outside the project". No command reached it, since every caller judged the value first and refused `/` by name, so the wrong answer was latent. The helper now judges the value first in those callers' words, so `/` reads "is the filesystem root, which the artefact check cannot examine as a build tree", a relative value reads "is relative", as every caller already said, and a status it does not expect is named by its number rather than walked to "outside the project".
- **The helper that lists a project's crates and build trees no longer demands a roots array its caller never reads (issue `0169`).** `fullcycle` named a third array it never read, held there by a lint disable, because a call naming two died on an unbound variable, and an empty third name drew an error from bash on stderr while the call ran on. The roots array is optional now, named as nothing or as an empty name, and is never left behind in a global; `fullcycle` names two arrays and its disable is gone, and `check targetdir`, the other caller, still names the roots array, one of five since `0163` added one for the holes.
- **The `clean` page's `CARGO_CACHE_RUSTC_INFO` sentence says what it means, and names a `build.build-dir` set to another directory beside it (issue `0171`).** "Nor does a target directory cargo built under `CARGO_CACHE_RUSTC_INFO=0`" followed no negative and read as a fragment. It now says that such a target directory, or one built with `build.build-dir` set to another directory, which takes that file there, holds no `.rustc_info.json`, so it is not listed and raises no warning. The `build.build-dir` clause is new, from a measurement on cargo 1.99.0; a build-dir naming the target directory itself leaves the file there, hence "to another directory".
- **`check targetdir` reads the project root's cargo config as cargo does, `.cargo/config` before `.cargo/config.toml`, and names the file it read (issue `0176`).** It took the first of `.cargo/config.toml` and `.cargo/config` that named a target-dir, where cargo, with both there, reads `config` and ignores `config.toml`. Now only the file cargo reads is taken: with both there, a fork `.cargo/config` makes is named as its own, ".cargo/config sets build.target-dir = ...", where its cause went unnamed, and `fullcycle`'s refusal names it too; with no crate, a `config.toml` cargo ignores is no longer reported; and the passing line names the file read, or `.cargo/config.toml` when there is none, where it named `.cargo/config.toml` whatever it read.
- **The runtime every consuming project vendors no longer describes the operator's own projects, and nothing a user reads cites devbin's tracker (issue `0172`).** `0152` took names out of the vendored runtime, but its prose still described the operator's projects without naming them -- the word fleet on 42 lines in 17 shipped files, comments counting those projects and the ones devbin was folded from, and a quotation about one person's directory layout -- and printed lines, the help pages, the two reference yamls and the handler template `new` writes cited devbin's issues, threads, design records and decision dates. Each such comment now keeps its reasoning and drops who, where and how many, and what a user reads says what the rule is, not which issue or decision made it; comments for maintainers that cite devbin's own issues stay. Publishing the machine install and its publish-upgrade now print `cd <your project> && bin/devbin upgrade --from <install>` in place of a `fleet upgrade` hint only devbin's own tree could run; `bin/devbin`'s refusal to run from an install already printed that line, and now prints it through the same function. Two tests hold both rules over every vendored file.

## Fixed -- devbin's own tree

- **Two arms that passed under macOS's tools and failed on every Ubuntu run hold on both (issue `0151`).** `fullcycle.bats`'s `Cargo.lock` arm read the file's modification time as `stat -f %m` or else `stat -c %Y`, and GNU's `stat -f` prints the filesystem's status, free-block counts included, so two reads of one unchanged file differed; it now takes each spelling alone and accepts only a number. `dispatch.bats`'s exec arm refuted a bare `bin/devbin` among the parent processes, which a CI checkout's own path contains; it now refutes the dispatcher's own line with its verb. Both were test-only, and they are why v0.1.8's tag read red on CI.
- **`fleet` finds an install that has lost its manifest and gives it a NO MANIFEST row, where the census dropped it at exit 0 (issue `0154`).** Both of `fleet`'s walks found installs by their manifest alone, so an install that kept its launcher and vendored runtime but lost `bin/.devbin/manifest.sha256` -- the install issue 0146 made `upgrade` refuse unless forced, because no edit in it can be named -- had no row and no message anywhere. An install is now a directory carrying that manifest or, without one, `bin/devbin` beside a `bin/.devbin/lib` directory or a link to one, a definition both walks share. Such an install is a NO MANIFEST row in `audit` and `doc` and a line in the walk outside the roots; its seam is still digested, and the census still exits 0, because it reports and never judges. `fleet upgrade` names it in its not-swept table with the command that forces it, `./bin/devbin upgrade --from <prefix> --force` in it, or a re-install, and `--apply` neither runs its launcher nor writes to it. An install two overlapping roots reach has one row, where it had two, and a census whose list of installs could not be finished fails by name. Riding with it, since devbin keeps no list of who uses it: `fleet`'s built-in frozen list is empty, the machine declares its own in `DEVBIN_FLEET_FROZEN`, the plan prints `frozen: none declared` when nothing is, and a `*` in the list no longer globs. Measured on this machine's census, two passes each way, the walk took 40.5 s to 41.1 s before and 40.0 s to 41.4 s after, and the table of installs under the roots was byte-identical.
- **The suite runs the lint gate `check lint` runs, so shellcheck reaches a change before it lands rather than at the cut, and the gate lints in parallel (issue `0155`).** At the 0.1.8 cut, six patches had passed review, their targeted runs and the whole suite on the landing tree, and the cut's `check all` lint then found SC2034 in `lib/cmd/fullcycle` and SC2004 in `lib/runlog`, fixed mid-cut: no test ran the lint gate, the pre-commit hook runs Intent's gate, and `check all` runs at the cut and on CI, after landing. `contract.bats` now runs `bin/.devbin/cmd/.lib/shell-gate lint` over the tree under test and holds a clean verdict over at least 40 files, printing the count; a two-file probe tree with a planted SC2034 is its positive control, and without shellcheck the arm skips and says the lint gate was not run. `gate_lint` runs `shellcheck -x` in parallel, jobs from nproc or getconf capped at 8, each file's output and status read back in corpus order; a worker that dies is named as a file with no verdict and counted a breach, the summary still prints, and the scratch is removed. The arm adds about 12.5 s to a targeted run that includes `contract.bats` (12.6 s and 12.4 s, two runs on 16 CPUs), and `gate_lint` over the tree's 48 files takes 12.8 s and 12.4 s in parallel against 76.6 s and 77.2 s in series.
- **The test that `fullcycle` runs no cargo of its own says what it holds and sees cargo in any command position (issue `0165`).** The arm was titled "the shipped fullcycle contains NO cargo invocation", though the cycle runs `cargo metadata` from `lib/helpers`, and its pattern missed a command behind an environment prefix, the form `lib/helpers` writes, so a planted `CARGO_TERM_COLOR=never cargo build --release` left it green. It now says `lib/cmd/fullcycle` runs no cargo command, the cycle building and testing only through its build and test commands, and its matcher, one for both arms, reads `cargo` behind any number of `NAME=value` prefixes and behind `if`, `then`, `!`, `{`, `env`, `command`, `exec` and the other words that put a command there, drops comment lines, and of the rest only lines whose command is printf or echo, and fails on a grep error rather than reading it as no hits. The prefixed plant, `if cargo`, `! cargo` and `env ... cargo` each turn it red. A second arm holds that the only cargo command `lib/helpers` runs is `metadata --offline --no-deps`.
- **The test pinning `clean`'s cargo markers reads code, never comments, and pins `clean`'s own walk markers too (issue `0170`).** The arm grepped the whole of `lib/helpers`, where comment lines alone satisfied `CACHEDIR.TAG`, `.rustc_info.json` and `debug/.fingerprint`, so deleting their code left it green, and nothing pinned `clean`'s walk markers once 0148 moved the marker test. Each function is now read as `declare -f` prints it, without comments, and each marker's whole test, such as `[ -f "$1/.rustc_info.json" ]`, is looked for as a fixed string in the function that tests it, so a half-deleted test goes red too; the walk markers are pinned the same way in `_clean_roots`, with `lib/cmd/clean` sourced over a stub that runs no gate.
- **Every key the annotated reference config documents only in a comment is held to the schema (issue `0173`).** `lib/config.reference.yaml` documents some keys only as comments, because declaring them would change what a project does, and its tests ran over live keys and from the schema to the file, never from a commented key to the schema, so a commented key the schema does not know, or one a rename left behind, passed. A new arm reads every commented key at the dotted path its nesting gives it and requires each to be a path the schema knows, a list key with its index; a key it cannot place, or one spelled as no key is, is named rather than left unread, and an extraction that finds fewer than eight keys fails. The configuration page's arm asks the same question through the same helper.
- **Two release notes name the owner's projects without their local directories (issue `0174`).** 0.1.1's version table listed a project by its path on the operator's machine, and 0.1.8's census-frame entry quoted the frame's old default directory. 0.1.1's table now names each project, and 0.1.8's entry says "the directory that holds the projects" and "a second directory of projects". `CHANGELOG.md` and `RELEASES.md` regenerate unchanged, since neither carries those lines, and `release check` reads both views current.
- **`fleet`'s census no longer names an install whose `bin/.devbin/lib` cannot be searched as a hole where installs may be missing (issue `0175`).** An install whose lib had lost its x bit drew `could not read all of <root> -- installs beneath it may be missing from this scan` in the walk under the roots, and `could not read all of <home> -- installs outside the roots may be missing from this list` in the walk outside them, though nothing beneath a vendored runtime is an install. Under the roots the audit already failed on that install through its digest, so the verdict was right and the message wrong; outside them the false hole was the audit's only failure. The walk now marks and prunes a `bin/.devbin/lib` before it asks whether it can search it. Under the roots the audit still exits non-zero, naming the seam it could not digest; outside the roots, where the walk digests nothing, the install is listed and the audit passes. Every other directory the walk cannot search is still a hole and still fails the audit, a project's own `lib/` and a `.devbin/lib` outside `bin/` among them. A sweep is no longer refused whole for one such install: it is planned, and `--apply` names it FAILED when its own launcher cannot run, and sweeps the rest.

## Known limitations

- **No devbin issue is open.** All 26 filed since 0.1.8, `0151` to `0176`, closed before this cut, since 0.1.9 carries every one.
- **This release has no CI run and no GitHub release object.** GitHub Actions refuses devbin's jobs for billing, and the release was cut without them: the cut stops at the object step, and the tag, the pushes and the machine install carry the release. The suite ran in full on every landing tree on macOS, and the GNU-tool runs were made locally.
- **No verb writes the machine's install pointer alone (issue `0153`).** A publish to `install.prefix` writes it, and so does the publish-upgrade that rolls this release out; a `fleet` sweep refuses until one has, unless an exported `DEVBIN_INSTALL_PREFIX` names `install.prefix`, in which case it runs and warns that a shell without the variable will not find the install.
- **A manifest written before 0.1.9 keeps its recorded path through that project's first upgrade to 0.1.9 (issue `0153`)**, which runs the project's older runtime and records the path again; the upgrade after it, run by 0.1.9's runtime, writes the kind of source, and `fleet upgrade --apply` makes both passes itself. Both old forms still resolve meanwhile. The `upgrade` help page still says the next upgrade writes the kind, and that a refusal of a source `DEVBIN_INSTALL_PREFIX` places says the variable named it, which holds only where that tree is no devbin.
- **The machine's frozen list for `fleet` is declared nowhere yet (issue `0154`).** devbin's built-in list is now empty, so a sweep's plan names every install the roots reach, archived ones included, until the machine declares `DEVBIN_FLEET_FROZEN`.
- **A project's own `.gitignore` in a gate's log directory is left as it is, even one that ignores nothing (issue `0157`)**, so that directory can still dirty the tree: where it is `tmp/release` the release pre-flight still refuses, and elsewhere the cut fails at step 5 once a gate writes there. Where git finds a repository but cannot say what it tracks, no ignore file is written and the run says so; where there is no repository to ask, one is written.
- **The cargo config order `check targetdir` and `fullcycle` read is cargo 1.99.0's as measured (issue `0164`)**: with both `.cargo/config` and `.cargo/config.toml` in one directory, cargo reads `config`. A build line run from outside the workspace does not read the workspace's config, so `fullcycle`'s offered `build.target-dir = "target"` does not reach it.
