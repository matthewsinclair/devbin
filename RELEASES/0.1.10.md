headline: a passing release dry run ends on its verdict and plans the push the cut makes, `release` leaves a remote's password, where it can read one, out of its refusals and out of git's words about the remote, `check lint` checks a killed check again before counting it, a repository git cannot read is named as one, and `fleet`'s frozen list names a project as the plan does.
status: released

**Why this release exists.** Everything open closes for the next release, so 0.1.10 closes the issues filed since 0.1.9, `0177` to `0191`, all but `0192`, which moves to the next release. Most came out of reading 0.1.9 as it shipped: its note before the cut, its CI after the push, its first dry run, and its rollout's sweep plan. The last three, `0190` to `0192`, came from a profile of devbin's own suite, which ran its 2282 tests one at a time, each fixture paying for a real install, in about 40 minutes on a 16-core Mac and on CI alike. The cut was held to land them, since a dry run and a cut each run the suite, and `0192` then moved to the next release once `0190`'s two lanes had brought the suite to about ten minutes. It keeps a 0.1 number, as 0.1.8 and 0.1.9 did, because every consuming project pins a `^0.1` caret.

## Changed -- a script or a config may get a different result

- **`fleet upgrade`'s frozen list names a project as the plan's row does, its path below the run's roots, and a frozen name that labels no project stops `--apply` before it writes anything (issue `0182`).** A name in `DEVBIN_FLEET_FROZEN` was compared with each project's basename, while every row of the plan names a project by its path below the scan root. So the name a row printed froze nothing: a project labelled `GroupA/Child` and declared as `GroupA/Child` was planned `upgrade + repoint` beside a header naming `GroupA/Child` as frozen and a summary reading `0 frozen`, and `--apply` swept it. A basename froze every project it ended, `Child` freezing `GroupA/Child` and `GroupB/Child` together, and a name that matched no project was echoed in the header and never reported. Now a name matches a project's label, so `GroupA/Child` freezes that project alone, and a bare `Child` freezes only a project of that name at a root's top level, where the label and the basename are one. A label is the path below the run's own roots, which `DEVBIN_FLEET_ROOTS` changes. Each declared name that labels no project the run could sweep, as one that labels only a worktree or a dependency checkout does, is named in the plan's header as `matches none`, the dry run stops offering `--apply`, and `--apply` refuses while one is declared, after the incomplete-scan refusal. The `fleet` help page says the same. **A list that froze a nested project by its basename no longer freezes it.** Where no project at a root's top level has that name, the name matches none and stops `--apply`; where one does, the name freezes that project alone, and the nested one is swept with nothing said. Run the plan without `--apply`, and copy each name from its project's row.
- **`DEVBIN_HEARTBEAT_SECS` takes a decimal fraction of a second from 0.1 up, and the heartbeat reads its quiet and elapsed times off the clock (issue `0191`).** 0.1.9 took whole seconds only, so a value such as `0.2` switched the heartbeat off without a word, as a malformed value does, and its times were the interval counted once per beat. Now a whole number or a decimal fraction of 0.1 or more, such as `30`, `0.2` or `.5`, sets the interval, and both times are read from the clock and printed in whole seconds, rounded down: a gate silent at `0.2` prints five lines a second, the first four saying `quiet for 0s, 0s elapsed`. Anything else, `1e3` included, and anything under 0.1, zero however it is written included, still switches the beat off without a word. A value that `sleep` refuses, as BSD's refuses one above 2147483647, now ends the beat without a word, where 0.1.9's beat spun, printing `sleep`'s complaint and a beat on every pass. The beat still prints only under a terminal, on stderr, never into a gate's log. It reads the wall clock, so a step of the system clock moves both times.

## Fixed -- reaches every project

- **A gate's log directory gets no `.gitignore` in a repository git refuses to read, and the run says why in git's own words (issue `0179`).** A gate writes `*` into `tmp/<command>/.gitignore` before its first log lands, and never into a directory the project tracks. It asked git whether the directory was tracked and, when git could not say, whether there was a repository at all. A repository git refuses to read, as it refuses one owned by another user unless `safe.directory` names it, failed both questions and was taken for no repository, so the file landed even in a directory the project tracks, at rc 0 and without a word, and its `*` hid every file the project added there afterwards. Now, when git cannot say, whether a repository is there is read from the filesystem: with a `.git` (a directory, a gitfile or a link) at the project root or above it, as far up as git's own discovery looks, with the exceptions under Known limitations (issue `0185`), the directory gets no ignore file, and the run says that git could not say what is tracked, with git's own first line, which for a refused repository names the dubious ownership. When git cannot answer, only a tree with no `.git` above it gets the file unannounced.
- **`upgrade`'s refusal of a tree `DEVBIN_INSTALL_PREFIX` places that cannot say what kind of tree it is says the variable named it, and the `upgrade` page says when a recorded path gives way to the kind (issue `0178`).** 0.1.9's note named both under its known limitations. The page said that every refusal of a source the variable places names the variable, where only the refusal of a tree that is no devbin did; the bare `upgrade`'s refusal of one that is no checkout and has no manifest to say what it is now says it too. The page also said that a manifest written before 0.1.9 keeps its path until the project's next upgrade writes the kind. An upgrade is run by the project's own runtime, and one older than 0.1.9 records the path again, so the page now says that the kind replaces a recorded path only at an upgrade the new runtime runs, and that a project upgraded from an older runtime needs a second upgrade. `fleet upgrade --apply` makes both itself.
- **`fullcycle`'s ARTEFACT CHECK INCOMPLETE summary lists every cause a build tree can be partial for, one to a line (issue `0177`).** It named three: a tree that could not be reached or searched, a `debug/` or `release/` in it that could not be listed, and a directory in it, which may be a target triple's, that could not be searched. So a tree the check could search but not list, whose own `release/` held no binary, and a tree behind a link that could not be followed exactly, a loop or a chain longer than the kernel follows, read in the summary as trees that could not be reached or searched. The verdict was right, at rc 1, and the warning above the summary named each tree and its cause. Now the summary lists all five, whichever held, and the `fullcycle` page names the link too.
- **A devbin checkout git cannot read is named as one, never as no repository: vendoring from it says so in the consumer's manifest, publishing from it refuses in git's own words, and `fullcycle`'s header says so (issue `0185`).** In 0.1.9 each of these readers took a failed git call for no repository. So vendoring from a checkout git refuses to read, most often one another user owns, which git refuses unless `safe.directory` names it, wrote `# source_commit: not a git checkout -- these bytes name no commit` into the consumer's tracked manifest beside `# source: checkout`, at rc 0; `install` and `upgrade` refused to publish from it as `is not a git repository`; and `fullcycle`'s header said `dirty: not a checkout`. Now whether a failed call had a repository behind it is read once, from the filesystem: none only when no `.git` sits at the directory or above it, as far up as git's own discovery looks, `GIT_CEILING_DIRECTORIES` honoured, with the exceptions under Known limitations; anything else is a checkout git could not read. The manifest line reads `a checkout git could not read -- these bytes name no commit`, the publish refusal says `git cannot read the repository at <path>` with git's own first line (the dubious ownership for another user's repository, `index file smaller than expected` for a corrupt index), and the header says `dirty: a checkout git could not read`. A source with no repository is still refused as `is not a git repository`. `fullcycle` in a project that is not a git checkout, under a `GIT_DIR` inherited from another repository, no longer exits with git's 128 before its dirty line; it says `dirty: not a checkout`. The `install` and `fullcycle` pages, and the `fleet` help page's audit, say what each reader now says. `release` is unchanged: a cut or a dry run in such a repository stops at step 1 in git's own words.
- **A release dry run that passes ends on its verdict and names the cut as the command that releases, and where step 4 would make the release commit, it names that commit and plans its push (issue `0181`).** A dry run that passed ended on its NOT REACHED list, and was read as one that failed. Its header said `resume with`. Where step 4 would make the release commit, rows 6, 7 and 11 named HEAD's sha, which the cut never tags, and step 6 read a remote at HEAD, the usual case when main is pushed before a cut, as already holding the release commit, so rows 6 and 8 planned `tag` where the cut pushes `commit tag`. Now a passing dry run's last line is its verdict, `release: dry run of <tag> -- no step failed; the cut stops to ask at step 6`, whose tail says instead, given `--yes`, that the cut does not stop to ask, and for a release with nothing left, that the cut has nothing left to ask about; given `--yes`, row 6 says `--yes given:` in the cut's own words, and step 6's confirmation is no longer listed as unpredicted. The header says `cut with: bin/devbin release v<version>`, and a cut still says `resume with`. Where step 4 would commit, rows 6, 7 and 11 name `the release commit step 4 makes`, a remote at HEAD is planned `commit tag`, and a remote that moves past HEAD after pre-flight is refused at step 6, as pre-flight refuses one, where 0.1.9's dry run passed. A dry run that fails still stops at its FAILED row, exit 1, with no verdict, its header naming the cut; a cut and a resume are unchanged. `docs/releasing.md`, the `release` page and `docs/configuration.md` say how a dry run ends and what it names.
- **A repository whose index git cannot read is said to be one, never read as a clean tree, as nothing staged, or as a log directory that is not ignored (issue `0186`).** Over an index git cannot read, as a truncated `.git/index` is, git still names the commit, while `status`, `diff --cached`, `ls-files` and `check-ignore` fail. In 0.1.9 four readers took that failure for an answer: `--version` printed the bare commit at rc 0, over a tree whose state nobody had read; `fullcycle --dry-run` printed the same bare `HEAD:` line and then exited with git's 128, in git's words alone; `check critic`'s builtin warned that nothing was staged and ran Intent's critic, which then failed on the same git call; and the release pre-flight, beside its `git status failed` refusal, told a log directory that ignores itself to `add tmp/ to .gitignore`. Now `--version` and `fullcycle`'s header mark the commit `+unreadable`; the header says `dirty: a checkout git could not read -- these bytes are not compared to anything` with git's own first line, and the run goes on; `check critic` stops before the critic runs and says git could not say what is staged, with git's line, read from the index the call read, a commit hook's `GIT_INDEX_FILE` included; and the pre-flight says `git could not say whether tmp/release/ is ignored`, with git's line, and offers no remedy. It says the same where `git check-ignore` fails over a readable index, as it does on a `tmp/` committed as a link to a directory outside the tree, where 0.1.9 offered `add tmp/ to .gitignore`, which does not clear that refusal; both versions refuse such a link. `check critic` in a project that is not a git checkout now stops, saying so, before the critic runs, where 0.1.9 warned that nothing was staged and ran Intent's critic, which fails outside a repository. A status that answers but warns, as of a directory it could not open, now prints its warning under `fullcycle`'s count, on stdout, where 0.1.9 let git's warning through to stderr. The `check`, `version` and `fullcycle` pages say so.
- **`generated_doc_write`'s refusal advises env indirection by naming the variable, never with an example URI that a secret scanner reads as a credential (issue `0187`).** When a `--deny-env` variable's value appears in a generated block, 0.1.9's refusal advised `Use env indirection in the producer's output (postgresql://user:$<VAR>@host) rather than the value.` Its source line, `postgresql://user:\$$v@host`, is vendored, so it sat in every consuming project's `bin/.devbin/lib/helpers`, and a secret scanner reads it as a Postgres connection string carrying a password: Kingfisher 2.11.0 flagged it as the one false positive in another project's repository, so every consuming project that scans its tree had to excuse a line of devbin's. The refusal now reads `Use env indirection in the producer's output -- write the literal text $<VAR> where the value would go -- rather than the value.`, and Kingfisher finds nothing in the vendored set. A `neutral.bats` arm refuses a URI that carries a password, whatever stands for it, anywhere in the vendored set.
- **`release`'s refusals of a remote url it cannot read a repository from print the url with its userinfo left out, and a url holding more than one @ ahead of its host is refused (issue `0188`).** Where `release.repo` is not declared, the repository is read from the remote's url, and a url that named no host or was not HOST/OWNER/NAME was refused with the url printed as configured. So a url carrying a token, in the URL form or the scp form, put the token on the terminal, in the cut's sealed log under `tmp/release/` and in CI's job log, through pre-flight's `gh` check, step 6's object read, `release status`'s row 9 and the object's content read. And since the userinfo was read to its first @, a password holding a raw @ made the rest of the password the host, which `gh` was told in `--repo` and pre-flight printed. Now both refusals print the url with its userinfo left out, with the exceptions under Known limitations, and a url holding more than one @ ahead of its host is refused, naming `%40` as the way to write an @ in a userinfo. A url with no userinfo reads as before, and so does every url 0.1.9 read a repository from but one holding more than one @ ahead of its host. `docs/configuration.md` says what is left out, what is refused and what is printed regardless.
- **git's own words about a remote, and a `release.remotes` entry that is a url, are printed with every part of their userinfo left out, a password holding a raw @ or `/` included (issue `0189`).** When a call to a remote failed, the release core printed git's own words, in the UNREADABLE answer that pre-flight's refusal, step 6, step 8's read after its push and `release status` print, and in step 8's pushes. git leaves a well-formed userinfo out of its message, but not a malformed one: with a raw @ in the password it printed the rest of the password as part of the host, and with a raw `/` it printed the url whole, or handed ssh the userinfo up to that `/` as the host, which ssh named when it could not resolve it. A `release.remotes` entry that is a url rather than a remote's name was printed whole by pre-flight's refusal, and by the warning that it has no url, which pre-flight's `gh` check and `release status`'s object row print where it is the first entry and `release.repo` is not declared; and `release status` read it without pre-flight's check and printed it in its push row, with git's words about it. Now git's words are printed once git exits, with every part of every remote's userinfo they carry left out, where it can be read as one, with the exceptions under Known limitations; where a url has a scheme and a `:` that is no port's stands ahead of a raw `/` in its password, its userinfo is read past that `/` to the url's last @; pre-flight's refusal and the no-url warning name such an entry with its userinfo left out; and `release status` reads it as `UNREADABLE` without asking git. ssh's refusal still names its user, which is no credential. `docs/configuration.md` says what is left out and what is not.

## Fixed -- devbin's own tree

- **`check lint` reads its statuses back only once every worker has finished, on any xargs, and the two arms that held 0.1.9's Ubuntu CI red pass there (issue `0180`).** The lint gate ran its checks through xargs and read their statuses back when xargs exited. GNU xargs 4.9.0, the Ubuntu runner's, exits as soon as a worker is killed by a signal, without waiting for the workers still running, so a file nothing was wrong with lost its verdict and counted as a breach, and its worker wrote into the gate's scratch after the gate had removed it. Now xargs's output goes through `cat` to `/dev/null`, which ends only when every worker holding that pipe has exited. `contract.bats`'s dying-worker arm asserts xargs's own report of the death; a new arm kills xargs itself, and is red without the fix on macOS as well as on Ubuntu; and `helpers.bats`'s `gate_exec` arm guards its terminal half with `require_pty`, where it required `expect`, which the Ubuntu runner does not carry. In both of 0.1.9's failures the gate failed closed.
- **`check lint` checks a file again, alone, before counting it a breach, when its check exited above 128 in the parallel run (killed, or out of memory), was left with no verdict, or never started (issue `0184`).** The gate runs up to eight checks at once, sized by CPUs and never by memory, and `shellcheck -x` peaks at over 2 GB on `bin/devbin`, so a host with many CPUs and too little free memory had checks killed, each a breach with no defect behind it; and in 0.1.9 a file xargs never started after a worker died was named `lint: no verdict for <f>`, a breach. Now each such file is checked by itself once every worker of the parallel run has exited, that verdict is the one that counts, and a line on stderr gives both, eg `devbin: lint: lib/x exited 137 in the parallel run; checked again alone: ok`. A check that fails on its own terms, a status from 1 to 128, is never run again.
- **`fleet`'s census answers through 0185's reading.** A project whose `.git` is a dangling link reads `UNREADABLE` and fails the audit, where 0.1.9 called it `not a checkout`. A project whose only `.git` is above it, in a repository git refuses to read, reads `not its own checkout` and no longer fails the scan, where 0.1.9 read it `UNREADABLE`. With no git on `PATH`, a project with no `.git` reads `not a checkout`, where 0.1.9 read every project `UNREADABLE`. A project below an empty `.git` reads `not its own checkout`, where 0.1.9 read `not a checkout`; both pass the scan.
- **The comment on `targetdir.bats`'s arm for a workspace's own `target-dir = "target"` over an unreadable directory says the case fails, where 0.1.8 cleared the config, not that it stays failed (issue `0183`).** 0.1.9's note was corrected the same way before its cut.
- **`test all` runs devbin's own suite in two lanes where GNU parallel is installed: the tests not tagged `serial`, N at a time under `bats --jobs N`, then the tests tagged `serial`, one at a time (issue `0190`).** The suite ran one test at a time: its 2282 tests took 40.6 minutes on a 16-core Mac and 39.5 on CI's Ubuntu runner. N is half the CPUs and never fewer than two, and `DEVBIN_TEST_JOBS` sets it; the run's first line names N and the GNU parallel it found. The two lanes write one seal and give one verdict, which fails when either lane fails, or when the lanes did not run every test `bats --count` counts, each exactly once. Without GNU parallel, or with `DEVBIN_TEST_JOBS=1`, the suite runs one test at a time, as before, and the first line says why; a run handed paths or bats flags runs exactly those, in one lane. On this Mac the 2295 tests of 0.1.10's landing suite ran in 9 minutes 29 seconds, 8 at a time. CI installs GNU parallel on both legs, and the `test` help page says when to tag a test `serial` and how.
- **The Ubuntu CI job lints the tree once, and two tests stop waiting on what they need not (issue `0191`).** The job's `test all` runs the suite's full-tree lint test (issue `0155`), which runs the gate `check lint` runs, and its Run gates step then ran `check lint` again, so the tree was linted twice in a row, about two minutes each time. Run gates now runs every gate but `critic` and `lint`, and the lint test, which skipped where shellcheck was missing, fails there under CI, as `check lint` does, so a runner without shellcheck still turns the job red. `ci-workflow.bats` holds the list to `check`'s options less those two, and holds that the job runs `test all`. `heartbeat.bats` beats at a fraction of a second and takes 12.2 s where it took 21.7 s on this Mac, and `releasecut.bats`'s test of a hung `ci.query` sets `DEVBIN_RELEASE_ASK_FLOOR_SECONDS=2`, as its siblings do, so it waits 2 s rather than the default 15: 6.8 s where it took 17.9. CI's Shell Script Analysis job now writes its list of files to a file under `set -euo pipefail` and reads that, so a `find` that fails stops the job, naming the directory; it sent `find`'s errors to `/dev/null` and read the list from a process substitution, whose status nothing read, so a directory `find` could not read would have left the job green over a shorter list. And a comment in `contract.bats` whose line opened with the word `shellcheck`, which ShellCheck parses as a directive, so that it checked nothing in the file, is rewrapped.

## Known limitations

- **One devbin issue is open, `0192`, and it moves to the next release.** The other 15 filed since 0.1.9, `0177` to `0191`, closed before this cut. `0192` installs devbin once per test file and copies that install for each test, where every fixture in devbin's own suite still pays for a real install; it moved to the next release once `0190`'s lanes had cut the suite from 40 minutes to about ten.
- **`fullcycle`'s artefact check reads a `release/` it cannot list as holding no binary (issue `0177`).** Where a build tree cannot be listed and neither can its `release/`, the tree's warning and the summary's line for a tree listed while its own `release/` held no binary both say that `release/` holds no binary, which the check cannot know; the warning that it cannot be listed prints beside them. A tree that comes back between the check's tests reads as one it cannot search, or as one behind a link that cannot be followed exactly. Both fail closed, at rc 1.
- **Where git cannot say, whether a repository is there is read from the filesystem, and four cases read otherwise than git would (issues `0179`, `0185`).** A `.git` past a filesystem boundary still counts, where git's discovery stops; so does a `.git` git passes over, an empty `.git` directory or a dangling `.git` link; `GIT_CEILING_DIRECTORIES` is read only to its first newline, so a ceiling listed after one is not honoured; and a bare repository counts as none. So `fleet` reads a root whose only `.git` sits above it, past a filesystem boundary or past a ceiling listed after a newline, as `not its own checkout`, where 0.1.9 said `not a checkout`. With no git on `PATH`, a gate's log directory in a repository gets no ignore file, and the run says git could not say whether it is tracked, with no line from git; 0.1.9 wrote the file there unannounced.
- **`vendor` does not refuse a devbin that is no checkout and has no manifest, so it names no variable there (issue `0178`)**, as in 0.1.9; `upgrade` refuses one, naming `DEVBIN_INSTALL_PREFIX` where the variable placed it.
- **One frozen name freezes two projects where the same path sits under two roots (issue `0182`)**, since both carry one label. 0.1.9 froze by basename, so a bare name froze every project of that name.
- **A check `check lint` runs again alone is not always alone, and nothing times a check out (issue `0184`).** A check whose worker was killed can still be running when its file's second run starts; the second runs go one at a time; and a check that never returns holds the gate, in the second run as in the parallel run. That holds on every xargs now, where on GNU xargs 4.9.0 0.1.9 stopped waiting once a worker was killed by a signal (issue `0180`). The parallel run is still sized by CPUs, never by free memory. A lint gate killed outright leaves its scratch, and its workers finish into it; nothing in devbin kills the gate.
- **The release pre-flight still refuses a `tmp/` committed as a link to a directory outside the tree, as 0.1.9 did, and an untracked link on that path inside the tree (issue `0186`).** A `tmp/` that is a submodule passes until `tmp/release/` holds a `.gitignore` of its own, as after a run has written there, and is then refused, with git's `is in submodule` line, where 0.1.9 said `add tmp/ to .gitignore`. `--version` prints the bare commit over a tree whose status answered after skipping a directory it could not open, as 0.1.9 did.
- **devbin's own `docs/authoring-commands.md` still recommends `postgresql://user:$PGPASSWORD@host/db`, and arms in `gendoc.bats` and `neutral.bats` plant the shape (issue `0187`)**, so a secret scanner over devbin's own repository can find them; a project that vendors devbin carries only the vendored set, which is clean.
- **A dry run's `no step failed` speaks for the steps it reaches (issue `0181`)**; the NOT REACHED list above it names what it could not predict.
- **`release` leaves out of a url only what it can read as a userinfo (issues `0188`, `0189`).** A url it cannot read that way reaches its refusals and git's words whole, as one holding a raw `/` in its userinfo does where the url has no scheme, where no `:` stands ahead of that `/`, or where the password runs only digits up to it. Where a raw `/` follows a raw @ in the password, the userinfo ends at that @, as git reads it, and the rest of the password reaches them as the host and the path. A `://` anywhere in a url is read as its scheme's, and a secret elsewhere in a url, as in its query, is not looked for. In the scp form an @ in the path's first segment ends the userinfo, and so does an @ in the path of a url whose password holds a raw `/`, so the host, and the path ahead of that @, are left out too. A remote call killed at its bound prints none of what git said and leaves git's words in a file under `TMPDIR`. ssh's refusal names its user.
- **No verb writes the machine's install pointer alone (issue `0153`).** A publish to `install.prefix` writes it, and so does the publish-upgrade that rolls this release out; a `fleet` sweep refuses until one has, unless an exported `DEVBIN_INSTALL_PREFIX` names `install.prefix`, in which case it runs and warns that a shell without the variable will not find the install.
- **A manifest written before 0.1.9 keeps its recorded path through that project's first upgrade from a runtime older than 0.1.9 (issue `0153`)**, which runs that older runtime and records the path again; the upgrade after it, run by the new runtime, writes the kind of source, and `fleet upgrade --apply` makes both passes itself. Both old forms still resolve meanwhile. The `upgrade` page now says a second upgrade is needed (issue `0178`).
- **The machine's frozen list for `fleet` is declared nowhere yet (issue `0154`).** devbin's built-in list is empty, so a sweep plans an upgrade for every project the roots reach, archived ones included, until the machine declares `DEVBIN_FLEET_FROZEN`.
- **A project's own `.gitignore` in a gate's log directory is left as it is, even one that ignores nothing (issue `0157`)**, so that directory can still dirty the tree: where it is `tmp/release` the release pre-flight still refuses, and elsewhere the cut fails at step 5 once a gate writes there. Where git cannot say what a repository tracks, as of one it refuses to read, no ignore file is written and the run says so; one is written only where no `.git` sits at the project root or above it, as far up as git's own discovery looks (issue `0179`).
- **The cargo config order `check targetdir` and `fullcycle` read is cargo 1.99.0's as measured (issue `0164`)**: with both `.cargo/config` and `.cargo/config.toml` in one directory, cargo reads `config`. A build line run from outside the workspace does not read the workspace's config, so `fullcycle`'s offered `build.target-dir = "target"` does not reach it.
- **A `CARGO_TARGET_DIR` that resolves to `/` through `.`, `..` or a link reads "resolves to /, outside the project" rather than "is the filesystem root" (issue `0166`)**, and is refused all the same.
- **`check targetdir` does not see a cargo config inside a directory `find` cannot read at all, or deeper inside one it can search but not list (issue `0163`)**, nor a directory whose ACL denies only search, as 0.1.8 already said of every walk (issue `0145`). A workspace below the project root whose own config pins `target-dir = "target"` fails over an unreadable directory beneath it (at the project root that target is the shared tree, and it passes), since only what the directory hides tells a member from a second workspace; the failure says to make it readable or move it out of the workspace. Where `find` meets a directory it cannot read, `check targetdir` walks a second time, about 1.8 times one walk.
- **`clean` still never removes `<root>/target` for a nested crate with no root `Cargo.toml` (issue `0167`)**; `check targetdir` does not endorse that tree instead, since removing it would mean running cargo inside `clean`.
