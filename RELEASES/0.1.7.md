version: 0.1.7
date: 2026-09-22
headline: A command with nothing to run says what would make it run, doctor stops vouching for a config it could not read, and the `fleet` sweep stops writing into worktrees.
status: released

**Why this release exists.** The consuming projects were re-vendored from a commit that was 0.1.6 plus the fixes below, and every manifest still said `0.1.6`. Two different sets of bytes carried one version number, and only a manifest's `source_commit` told them apart. This release makes the number name the bytes again.

## Fixed -- reaches every project

- **A command that resolves to nothing says what would make it run (issue `0111`).** `bin/devbin build` said it was "not built yet" and "gated on: the built-in command library (ST0001/WP-14)". ST0001 closed on 2026-08-10, and `build` was never WP-14's. `help --why` meanwhile said the true thing about the same command. Both refusal sites in the dispatcher now print a reason that comes from one function `help --why` shares, so the two cannot drift again. There are two cases, told apart by the catalogue. A name devbin ships with nothing behind it (`build`) says what the project declares: `commands.build.run`, or a handler. A command or option served by devbin's own handler that cannot be found in this install says so and names `doctor`. Exit 3 keeps its meaning. `not_yet` in `lib/helpers` is unchanged, because project handlers use it for their own genuine stubs.
- **`doctor` no longer reports "any runtime satisfies this project" for a config it could not read.** An empty version constraint means either "declares none" or "could not be read", and only the first may be said. `check_languages` already re-read the config to be entitled to say it; `check_devbin_version`, four lines below it, did not, so a project whose config does not parse got doctor's most permissive verdict printed directly beneath a FAIL naming that same file.
- **`bin/devbin devbin` names only paths that exist.** In the devbin checkout it pointed at `bin/.devbin/lib/config.reference.yaml` and `bin/.devbin/lib/tmpl/`, which exist in a consuming project and not in the checkout, where the runtime runs from `lib/` in place. The paths are now derived from where the runtime actually is, and a test holds that each one exists, in an install and in the checkout.
- **`manual:` is documented in the infra reference.** `infra` has always read `defaults.manual` and `domains.<handle>.manual`, and the annotated reference, the one guide an operator has and a file every consuming project vendors, never mentioned it. It is the namespace for records devbin cannot verify, named on every run so nobody takes it for a record of verification.

## Fixed -- devbin's own tree

- **Every verb devbin offers has an authored page (issue `0112`)**: build, docs, fmt, release, version, devbin and shell-init were falling through to the generated stub. The test that should have caught it listed five commands by hand; it now reads the list from `help` itself.
- **`fleet upgrade` no longer sweeps a git worktree, wherever it is kept.** It recognised worktrees only under `.worktrees/`, and upgraded `Intent/tmp/wt-0516`, a worktree in use in Intent. A linked worktree is now recognised by its `.git` file; a submodule's is still swept as a project. Every row in the sweep's tables is labelled by its path, not its basename, so twelve dependency copies of two libraries no longer read as the same two names.
- **Two documents disagreed with what they describe.** `RELEASES/0.1.0.md` carried a test count and date from a docs pass five days after that release, not the release's own; `docs/releasing.md` named one of the two path-filter lines that both have to be present for a board-only push to start no run.

## Known limitations

- **The authored help pages do not reach any consuming project.** Help is read only from a project's own `bin/.devbin/help/`, which is not vendored, so in every consuming project `bin/devbin help release` still prints the generated stub, as `help upgrade` already did. The pages also say things that are only true of devbin, so shipping them is a choice about what a shared page says and how a project extends it. It is open, and not decided by this release.
- **Nothing the macOS runner supplies is exercised between releases**: its image, Homebrew, and the Intent formula `check critic` installs are met at a tag. `gh workflow run tests.yml --ref main` asks for the full set on demand.
- **A cut produces two runs of the tests workflow and only the tag's is the whole verdict**, and an intermediate pushed commit can have no verdict at all, because a newer push cancels it or a board-only push starts nothing.
- **Intent and one other project still release with their own orchestrators, and Utilz has declared the release core but not yet cut with it.**
- **The release core's reads before the first push are not time-limited**, nor is `release status`.
- **A cut under `object: ci` depends on the project's workflow running.** If CI does not start a job, the tag and the pushes stand and the object step fails at `object_wait`.
