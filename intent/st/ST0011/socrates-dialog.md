**Socrates:** So for Devbin the suite ran twice, once here on one commit and once on GitHub on a different commit, and the two never overlapped. Now the general case. hv's question, verbatim: "Why don't we just remember the hash that worked and set the release tag to that hash?" Answer it directly. Why is the commit that was tested not the commit that is tagged?

**Plato:** Because the stamp comes after the testing, by a ruling. ST0007 D38 v0.3 and v0.4 (E ruling 2026-09-17) put the gates on the release commit, after the stamp and the commit, so that the examined commit is the tagged commit, in place rather than in a worktree so compiled estates do not rebuild from nothing. That is correct as far as it goes: the gates do run on the commit that is tagged. What it does not account for is everything that ran before the cut on the candidate: hv's hand `test all`, a dry run (which runs the gates for real on HEAD, `Devbin: docs/releasing.md:22`), a dispatched matrix, the kovacs order, a gyges run. All of those tested the candidate; the cut then stamps, and the stamped commit is a new sha nothing has tested, so the gates test it again, and the tag's CI run tests it a third time.

Can the tested candidate simply be tagged? No, and A section 3.2 lists why. `release.yml` refuses a tag whose name is not VERSION's content. `doctor` reads VERSION against the constraint, and it is a Devbin gate for exactly that reason. The snapshot's message reads the version from the commit's own file. The formula fills the tag and the revision, and its `test do` asserts `devbin --version` prints the tag's version, so a tag on an unstamped tree installs and then fails its own test. The pre-flight's tag-sanity rule and `release publish`'s refuse a tag whose commit's VERSION is not the target. Devbin's own suite is version-sensitive by design: `documentation.bats` asserts that no authored file but the config names the current version. And for Gtools the version is compiled into the binary and the formula's test asserts `gtools version` prints it (issue 0295). So the tested commit cannot be the tagged commit unless the tested commit already carries the version. hv's "remember the hash that worked" therefore has to be read as: make the hash that will ship first, test that once, remember that it passed, tag it. That is issue 0295's fix, "stamp first, test once, tag what passed".

**Socrates:** Then hv's question is answered by an ordering, not by memory. Good. Hold the memory question; we will come back to it, because "remember that it passed" is doing work in that sentence. First I want the whole decision space on the table.

So the no-publish shape adopts the publish shape's candidate mechanism, pointed at the project's upstream rather than a public snapshot. A section 4 says this in terms: "the candidate mechanism itself, pointed at the workroom's remote rather than a public snapshot."

For Devbin's own shape the candidate is the snapshot, which is a third sha: the release commit's tree filtered over `tests/shipped.paths` with a new identity and no parent (A section 2, the "snap" column). What changes is when it starts: `snapshot_build` needs the release commit's tree and the public tip, not the tag, so it can be made and pushed the moment the release commit exists (A section 5 point 5).

What a red costs under stamp first: nothing public. ## 1. Recommendation

The pipeline shape, as one command from the yes to the brew-installable artefact. Each step names where it runs and what it waits on.

1. **resolve, pre-flight** (this Mac; reads only). As today, minus the `ci.base` read, which the candidate run replaces. Pre-flight additionally refuses a test workflow whose matrix does not fire on `candidate/` refs (an extension of `release check`'s existing workflow read, B A1 step 1).
2. **confirm** (this Mac; a person at the terminal or `--yes`). The one yes, before anything runs, naming the tag, the release commit the stamp will make, every remote, the object, the assets, the tap, and its meaning: ship if every leg is green. `--yes` sets `DEVBIN_RELEASE_CONFIRMED` exactly as a typed yes does.
3. **stamp, commit** (this Mac; seconds: 4 seconds on v0.1.18, A section 0; 25 seconds with Gtools's `derived:` builds, D 4.3 timeline). Unchanged in content: version file, sidecars, `derived:` commands, note date, views; one commit through the project's hooks.
4. **legs, started together, one wait loop** (the loop polls as today, 15 seconds; its deadline is the longest declared wait; a red or a timeout in any leg stops the run with nothing public):
   - 4a. **candidate** (GitHub). No-publish shape: push the release commit to `candidate/<tag>` on the project's remote. Publish shape (Devbin): build the snapshot of the release commit's tree on the public tip and push it to the public `candidate/<tag>`, as the publish step does today (A section 1.4), the moment the release commit exists. The project's matrix starts; its verdict is read by `ci-state` on the candidate's sha.
   - 4b. **local gates** (this Mac, in place on the release commit). `check all`, `test all`, `doctor` as declared; each seal now records the commit it ran on; the step is `already` when a sealed green for every declared gate exists for this commit on this platform.
   - 4c. **remote legs** (each host `release.legs` names; kovacs). The core clones at the release commit's sha over ssh, runs the declared command, copies the seal pair back under `tmp/` with a platform-named stamp; the same reader as 4b reads it.
   - 4d. **macos stage** (this Mac, where `macos:` is declared). `app-sign` and `app-notarize` with the precondition "HEAD is the release commit" instead of "HEAD is the tag"; the staged, stapled copy waits for step 7.
5. **tag, push** (this Mac; seconds). On all legs green: the annotated tag at the release commit; the commit and tag to every remote in order; publish shape: fast-forward the public `main`, push the lightweight tag at the snapshot, delete the public candidate; no-publish shape: delete `candidate/<tag>`. Read back as today.
6. **object** (GitHub; `gh release create` under `object: local`, seconds; under `object: ci` the `release.yml` run, 0.1 minutes plus one 15-second poll, D 4.1).
7. **assets** (this Mac and GitHub, in parallel, disjoint files). `release attach` reads `assets.workflow`'s run by the release commit's sha (the candidate run) and uploads its artifacts; `macos publish` uploads the staged copy; `SHA256SUMS` is written last over everything. Skipped where nothing is declared.
8. **after: the tap** (this Mac). `formula publish` renders and pushes under the yes from step 2; source mode needs only the public tag and may run as soon as step 5 completes; assets mode waits for step 7's sums.
9. **end** (this Mac). The brew switch note is printed; `brew upgrade` and `use brew` on each machine remain the person's.

## 4. Key trade-offs accepted, and the fixed points

Trade-offs accepted:

- **The yes moves ahead of the runs.** It authorises "ship if green" rather than "ship this green thing". Accepted because lights-out requires it; the Mac's suite still precedes the tag.
