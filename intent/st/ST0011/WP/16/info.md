# WP-16: Build artefacts cached by the hash of their inputs: nothing rebuilt that a recorded input hash already built (D67)

## Objective

hv's direction (2026-10-31, D67): as CI, CD and assembly tools keep a registry or catalogue of built artefacts keyed on the commit they were built from, devbin's core caches build artefacts by the hash of their inputs, so that while nothing in the assembled dependencies has changed the artefact is pulled by its hash rather than rebuilt. Design first, then code: (1) measure, from the record, which builds repeat per release and what each one's inputs are (Gtools's twelve release-profile builds of gtools-rs, ten cold on runners; Intent's pair built at the tag and again by its pre-push hook's cold clone; Laksa's prod `mix release` twice; Conflab's three cargo builds and its xcodebuild), using each project's existing build-input scope where one exists (Intent's pre-push currency check, issue 0518); (2) shape the key as the tree hashes of the declared build-input paths at the commit (`git rev-parse <commit>:<path>` over `project.build_inputs`), never the commit alone; (3) shape the registry: a cache directory on the machine for local builds, the runner's cache or the release's own assets on CI, each entry the artefact plus the key and the toolchain it was built with; (4) `bin/devbin build` consults the registry before building and records after, and `release attach` may take an artefact from it; (5) one core mechanism with one `build_inputs` fact per project, nothing else per project (criterion b). Serves the thread's objective (nothing built twice); ACs to be minted with the design.
