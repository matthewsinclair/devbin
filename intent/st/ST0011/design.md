# ST0011 design: the release cycle, diagnosed and remediated

Diagnosis phase, 2026-10-31, by vc on hv's order. Evidence A to E, the Socrates brief and the full Socrates dialog are attached to this thread; every number below names its source there. No code was written in this phase. This document is the thread's design record: the diagnosis, the recommendation, the ranked options, the per-project remediations and the fix-phase work packages. The argument behind each is in `socrates-dialog.md`; this document does not repeat it.

## 1. The question and the rulings

A release of any project that vendors devbin's release core takes an hour or more, and the same suite runs several times per release. hv's rulings (the thread's objective): the target is the floor, one honest run per platform, run once, in parallel, nothing run twice; kovacs, the full CI matrix on the shipping commit and a local Mac suite each stay unless the evidence shows a run catches nothing another does not; notarisation stays on this Mac; every change reduces both complexity and time (criterion a) and lands in the core for every present and future project (criterion b); bespoke project machinery is in reach and retires into the core where the core can carry it.

## 3. Diagnosis: six repetitions, each with its mechanism

1. **The suite runs on the candidate and again on its stamped twin.** The core stamps, commits, then gates on the release commit (`lib/release.steps:94`; `lib/cmd/release:1034-1038`, "never already"); the release commit differs from the candidate by the version string, a date and two regenerated views (A s3.1; Gtools v0.8.3 `git show --stat`: 4 files, 4 lines). Every pre-cut run (hand `test all`, kovacs, gyges, a dispatched CI run, a dry run that runs the gates for real) is therefore a verdict on a tree that never ships, and the cut runs the suite again. The gates step records nothing, so a stopped cut re-runs it whole on resume (Gtools 0.8.0 and 0.8.1, C Gtools s1). Chosen by ST0007 D38 to avoid a cold rebuild in a worktree (E s4): a cost ruling, not a confidence one.
2. **Every tag push starts the same workflow twice on one sha.** The push step pushes the release commit to main and then the tag seconds apart (`lib/cmd/release:1155,1162`); each project's workflow keys concurrency on workflow, event and ref, so the push-to-main run and the tag run both live, and their Ubuntu legs are identical work: nine of nine releases in the record, Intent doubling two workflows (D fact 1 and 2). The macOS legs are not doubled inside the pair only because they are conditioned on the tag ref.
3. **Serial by step order, not by data.** A s5 names fourteen waits; the ones that cost minutes: the snapshot and candidate push wait for gates, confirm, tag and push though `snapshot_build` needs only the tag's commit and the public tip (so Devbin's 13-minute local suite and 47-minute matrix never overlap); `formula publish` waits for the object step's poll of a workflow that takes seconds though it needs only the public tag; the `ci` wait follows the `after` step; every GitHub wait is a 15 s poll with no overlap between waits; the `macos` built-in cannot start until HEAD is the tag.
4. **Devbin's own matrix is the outlier, by arithmetic.** 818 billed-equivalent minutes per candidate against 126 to 316 for a consumer's release and 14 for Conflab; its Ubuntu leg takes 32 to 42 min and its macOS leg 55 to 66 for a suite this Mac runs in 13 on 8 lanes (D fact 8). The cause: `bats-lanes` runs the parallel lane at half the CPUs and never below two (`bin/.devbin/cmd/.lib/bats-lanes:35-36,67`), which is 8 lanes on this 16-CPU Mac and 2 on `ubuntu-latest` (4 vCPU) and `macos-latest` (3 vCPU); the file's own header records 40.6 min serial here against 39.5 on CI's two-CPU runner (`:11`). One red leg costs a whole new version (v0.1.17 to v0.1.18, A s0).
5. **Hand-sequenced halves after the tag.** Intent: macOS assets, Linux assets and the tap are three independent halves run as five commands, 11 to 19 min (B B1). Devbin: `release publish --yes` always ends with the formula step FAILED because `--yes` is no person's yes for the tap (`lib/cmd/release:1484-1486`; A s7), then `brew upgrade` and `devbin use brew` by hand. Lights out is not possible on the current shape for any project.
6. **Bespoke machinery re-runs what it just required.** Intent's 1524-line driver gates on the candidate (the order 0295 asks the core for), yet re-runs the five cargo steps and bats it required a green kovacs run of on the same tree, in a private empty-target worktree (cold every cut), and its pre-push hook clones and cold-builds the workspace once per remote (B B5). Gtools builds gtools-rs in release profile 12 times per release, 10 cold on runners with no cargo cache (C Gtools s2). Laksa's deploy re-runs credo and the suite CI ran on the same commit and reads no CI verdict; the crate's tests run twice per `test all` (C Laksa s2). Conflab's own release pushes the bump and the tag before any gate, runs clippy at the commit and again in pre-flight, and keeps three formula writers (C Conflab s6 and s7). Utilz's `tools/ci-state` ignores `DEVBIN_RELEASE_TAG` and its 2.14.8 release log never sealed (B A7, E s2).

Common root: **no verdict is keyed on a sha, and no step reads one.** The seal records platform and run id, never the commit (`lib/runlog:402,406`); the only sha-keyed record is GitHub's run list, read by `ci-state`; kovacs's verdicts live in summary files the core never sees; so every step that wants confidence runs the suite itself. hv's "remember the hash that worked and tag it" is answered by an ordering plus that one memory: make the commit that ships first, test it once everywhere at the same time, record each verdict against its sha in the seal that already exists, tag it when all are green (dialog, phase 1 and phase 5).

## 5. The recommended shape

One command from the yes to the brew-installable artefact (dialog section 1 has each step's sources):

1. **resolve, pre-flight** (this Mac, reads only), minus the `ci.base` read; plus a refusal of a test workflow whose matrix does not fire on `candidate/` refs.
2. **confirm**: the one yes, before anything runs, naming the tag, the release commit the stamp will make, every remote, the object, the assets and the tap; its meaning is "ship if every leg is green"; `--yes` says it and sets the confirmed variable the `after:` commands read.
3. **stamp, commit** (seconds; unchanged in content).
4. **legs, started together, one wait loop**, a red or a timeout in any leg stopping with nothing public: (a) the candidate: the release commit pushed to `candidate/<tag>` on the project's remote, or for the publish shape the snapshot of its tree pushed to the public candidate, the moment the release commit exists; the matrix runs there; (b) the local gates in place on the release commit, each seal recording the commit, the step `already` when a sealed green exists for this commit on this platform; (c) remote legs the config names (kovacs): clone at the sha, run, copy the seal back, the same reader; (d) the macOS stage where declared: sign and notarise at the release commit, not the tag.
5. **tag, push** on all green; candidate ref deleted; publish shape fast-forwards the public main and pushes the lightweight tag at the snapshot.
6. **object** (`gh release create`, or `release.yml`'s run).
7. **assets**, in parallel over disjoint files: `attach` reads the assets workflow's run by the release commit's sha (the candidate run); `macos publish` uploads the staged copy; sums last.
8. **the tap**: `formula publish` under the yes from step 2; source mode as soon as the tag is public, assets mode after the sums.
9. **end**: the brew switch note; `brew upgrade` and `use brew` on each machine remain the person's.

Expected wall-clock from the yes to the tap, the longest leg plus a measured tail of about a minute (dialog section 1 table): **Devbin about 57 (today 71 to 78), Gtools about 15 (cut 23.8; candidate to release 82), Utilz about 15 (56), Intent about 21 (62), Conflab about 9 (5 today, with the tag pushed before any gate), Laksa's deploy stops re-running the suite and the prod compile.** Every figure is a measured leg plus a minute; the first release in the new shape is the measurement, which is why the RELEASE seal gains start and end clock lines (today no log carries one, A s8).

Its clock lines read `start: 2026-11-01T20:50:29Z` and `end: 2026-11-01T21:53:56Z`, with one line per leg: `candidate green 0b5e4fa0f540 3743s run 41348944891`, `local green e532a0f67250 1065s` and `legs.kovacs green e532a0f67250 3326s`. The yes fell between the prompt (20:50:29Z) and the release commit (20:50:40Z), and the tap's commit is 21:53:50Z: **about 63 minutes from the yes to the tap, against about 57 expected and 71 to 78 at v0.1.18.** The longest leg was CI's macOS job, 61.9 minutes (20:51:00Z to 21:52:54Z), its `test all` under 3 lanes taking 61.4 of them; v0.1.18's was 55.3. Ubuntu took 23.1 minutes under 4 lanes (31.8 at v0.1.18), and WSL 2 took 37.5 (59.1), red on one arm, filed as 0318, which blocks nothing by design. What it removes from the core: `release publish` as a separate command with its second pre-flight and confirm; `--expect`; the `ci` step and the `ci.tag` and `ci.base` keys; the gates step's "never already" rule; the dry run's real gates; the prompted-only confirmed variable; the tag-at-HEAD precondition in `macos`; the Candidate verdict job and the `tags:` trigger on the test workflow; three step names. What it adds: one `commit:` header line in the seal and one reader; the candidate push in the no-publish shape (the publish step's code on another remote); a `release.legs` key and its runner; the attach keyed on sha; a built-in `ci-state`; `after:` running under `--yes`; clock lines in the RELEASE seal. From the projects it removes Intent's driver, two preflight scripts, a hook's build path and five hand steps; Utilz's three tools; Gtools's reader and wait; Conflab's release handler, two formula writers and a workflow skipped since v0.5.7; Laksa's double suite run and local prod compile; three copies of one `ci-state` (dialog, phase 3 ledger).

### 5.1 vc's assessment of the recommendation

I adopt the dialog's recommendation with four notes.

1. **The one real addition is `release.legs`**, the core driving a run on another machine over ssh. The dialog flags it and names the degraded form (the desk runs the leg, the core reads the copied seal). I agree it passes criterion (a) on the estate's ledger: three bespoke copies of the same thing (Intent's `preflight-linux.sh` and `preflight.lib`, Devbin's K-orders, Gtools's hand run) retire for one shipped runner, and without it the kovacs fixed point and lights out contradict each other. It is hv's to accept (question 4).
2. **Lanes alone will not bring Devbin's macOS leg far.** Setting `DEVBIN_TEST_JOBS` to the runner's CPUs gives 4 lanes on `ubuntu-latest` and 3 on `macos-latest`, not 8; the scaling point on record is 2 lanes at 30 min against 8 at 13, so expect the leg to roughly halve, not quarter. The next lever is parallelism by job count: shard the bats suite across N runner jobs, each a subset of files, with one summary. That is a mechanism, bats-specific, and it belongs after the first measurement, not before. Larger runners are the third lever and cost money on a repository whose minutes are otherwise free.
3. **The dialog is right to keep CI macOS whole for the consumers** on the ground that it is not the longest leg under the parallel shape, and right that Devbin's cannot shrink because its CI tests the snapshot. I would add one line to the expected table: the Gtools and Utilz kovacs legs are not on record and may be the longest leg for those two; if so, the kovacs question (4) decides their floor.
4. **Decisions 32 and 81 stand unchanged** under this shape: release candidates run the whole matrix, and macOS and WSL run only on candidates, tags and dispatch. The shape makes the candidate ref the one place the matrix runs, which is what both rulings asked for.

## 11. The leg contract

vc's ruling, 2026-10-31; cc and dc build to it, and a question about it comes to vc rather than a second draft.

- **R** is the release commit the stamp step makes; every verdict is keyed on R's sha and a platform. The tested sha is R, pushed to `candidate/<tag>` on the project's GitHub remote, or under `publish.url` the snapshot S of R's tree; the RELEASE seal records R and S.
- **A leg yields one word, `ci-state`'s, verbatim**: `green`, `failed`, `pending`, `none` (no record, or not started), `unknown` (could not read, with its reason printed). The legs: `local` (the declared gates in place at R on this machine; its verdict is the seal pair with `commit: R` and `platform:` this one, `.errors` empty and not in flight); `candidate` (the matrix on `candidate/<tag>`, read by `ci.query`, whose default is the built-in reader, for the tested sha; Test Summary's verdict; WSL blocks nothing, D50); `legs.<name>` (a remote host runs the project's own declared gates at R in a worktree of a bare repo on that host; the seal pair is copied back under `tmp/release/legs/<name>/` and read by the same reader); `macos` (sign and notarise at R, where declared; its own seal).
- **Order**: resolve, pre-flight, confirm (the one yes, before anything runs; `--yes` answers it and sets the confirmed variable the `after:` commands read; the yes names the tag, R, every remote, the object, the assets and the tap), stamp, commit, then every leg starts in one step and one loop reads them all; tag and push only when every leg is green; then object, attach, after (the formula under the yes).
- **Already**: before a leg starts, its verdict for (sha, platform) is read; a recorded green is `already` and the leg is not started. The gates keep no other memory. A seal is remembered only when its commit line at open and at close agree and both are clean.
- **The loop**: poll every `ci.poll` seconds (15 today), deadline `ci.wait` (default 60m) from the loop's start, one GitHub read per poll, one line per state change with the clock. End: all green, tag; any `failed`, stop; the deadline, stop as a timeout. On a stop the local background runs are killed, remote legs are left to finish (their seals are records), the candidate ref is deleted and nothing is public; R stays in local history, the fix lands on top and the same version is cut again while no tag exists (Q3).
- **Interface**: the loop (cc, WP02b) calls `leg_start <leg>` and `leg_read <leg>` (one word plus a detail line) per leg; cc owns the loop and the `local` and `candidate` legs; dc owns `legs.<name>` (WP05) and `macos` (WP06) behind the same pair, in files of their own, with one-arm hook-ins landing after WP02b. Every verdict goes through the seal reader (WP01) or `ci.query`; nothing else reads one.
- **Clock**: the RELEASE seal gains `start:` and `end:` lines (UTC) and one line per leg: name, verdict, sha, duration.
- **Booking is outside the core**: the operator or the coordinating node books the box before the cut; the core never calls `intent estate`.
- **A failure of the mechanism** (ssh or `gh` unreachable) reads as `unknown` with its reason printed and counts as not green; at the deadline it is a timeout. No silent errors.

## 13. The artefact cache (WP16, D67, D68)

vc's design, 2026-10-31, on hv's direction. Design first: the core verbs land in Devbin after the fix-phase runs (dc's lane, after WP06a), and each consumer adopts in its WP10 to WP14 commit. Nothing here changes a fix-phase unit.

**What repeats today.** From the record (sections 3 and 6 of the dialog): Gtools builds gtools-rs at the release profile twelve times per release, ten of them cold on runners; Intent builds its pair at the tag and again in its pre-push hook's cold clone; Laksa compiles its prod `mix release` twice per deploy; Conflab runs three cargo builds and one xcodebuild. The inventories asked of the five consumer estates on 2026-10-31 (the pre-sweep brief, item 1) confirm each row with its trigger, its platform and whether it is cold before the verbs are cut. Devbin itself builds nothing: its suite is a gate, and D57's GATES seal is that gate's cache.

**The key.** An artefact's key is the sha256 of the sorted lines `<path>\t<object id>` over the declared input paths at a commit, the object id being `git rev-parse <commit>:<path>` (a tree id for a directory, a blob id for a file), plus three lines, `toolchain\t<id>`, `platform\t<word>` and `arch\t<word>`. Tree ids and not the commit, because a commit that changes only docs, the whiteboard or `intent/` leaves every input id as it was, so the key stands and the artefact is pulled: that is the whole saving on a re-cut after a red leg (the fix lands, R changes, the inputs mostly do not) and on Intent's cold clone, whose commit carries the same ids. Git's ids and not a content hash of the files, because git has hashed them already, `rev-parse <commit>:<path>` reads an object with no checkout, so R's key exists before any worktree is made for it, and the key is identical in every clone. The toolchain, because the same inputs under another compiler are another artefact; its id is the tool's own version line (`cargo --version`; from `elixir --version`, the Erlang/OTP release and its erts with Elixir's own line, leaving out the emulator's flags, which follow the host's CPU count and `ERL_FLAGS` and not what a build makes; `xcodebuild -version`; `swift --version`), read by the core from a built-in table keyed on the artefact's tool word, so no project writes a version anywhere, and asked where the build runs, cargo in `project.cargo_root`, where rustup reads a `rust-toolchain` file, and every other tool at the project root, so the key never depends on where the command was run. The platform, because a built artefact is for one, as this host's platform word, `macos` or `linux` (`platform_word` in lib/helpers, vc's decision 108); the seals' `platform:` line stays an identity of its own, the OS build and the bash a run stood on, and is not the key's word. The architecture, because one platform and one toolchain build another artefact for another CPU: x86_64 and arm64 runners would otherwise share a key, and an arm64 job would pull an x86_64 binary; the key names the word `uname -m` gives (`platform_arch` in lib/helpers, hv's decision 115). A dirty tree has no key: an input path with uncommitted changes is no commit's object, so the build runs and nothing is recorded, as `git_head_identity`'s `+dirty` refuses a confident sha. A key is printed whole in every record, never cut.

**The declaration**, one block per project in `bin/.devbin/config.yaml`, which is criterion (b):

```yaml
build:
  inputs:
    - Cargo.toml
    - Cargo.lock
    - src
    - crates
  artefacts:
    gtools:
      tool: cargo
      path: target/release/gtools
    gtools-app:
      tool: xcodebuild
      path: build/Release/Gtools.app
      inputs:
        - Cargo.toml
        - Cargo.lock
        - src
        - macos
```

In block form, since devbin's config parser refuses YAML's flow collections (`[...]` and `{...}`). `build.inputs` is the one fact; an artefact's own `inputs:` narrows it where that artefact reads fewer paths. `tool` names the toolchain table's row; `path` is what the project's `build` handler writes, read after a build and written back at a pull. lib/config's key schema carries the block's keys, as an arm of `_cfg_path_known` like the `worktrees:` block's, with the one reader of its input paths (`cfg_build_input_paths`), which the cache, doctor and validation share, so config validation refuses an unknown key, a tool word outside the table, an artefact's name that does not start with a letter or a digit (`is_artefact_name` in lib/helpers), a declared path that is empty, absolute, holds an empty, `.` or `..` segment, or lies in `.git` in any case of its letters (`cache_path_problem`), and an artefact's path that is, holds or lies in any input path the block declares, in any case of their letters (`cache_paths_overlap`), since a pull replaces what is at the path, so a pull never writes or removes anything outside the project or over it, nor an input's working tree, and one path never makes two keys; `get` refuses a path the repository tracks files at, in any case of its letters; and doctor fails an input path the block declares that HEAD does not hold.

**The registry** (hv's ruling, 2026-10-31 10:5xZ, D68). Its root is `DEVBIN_CACHE_HOME`, an environment variable, so the cache lives wherever a machine puts it; unset, the core uses `$(xdg_dir cache)/devbin`, and hv's fleet sets it to `/Users/matts/Devel/.cache` through Molt, a path no shipped file names. Under the root, one directory per project, and under that one per artefact keyed by the input hash: `<root>/<project>/<artefact>/<key>/`, holding the artefact (a file, or a tar of a directory's contents, so a pull writes them at the path the declaration names then), `manifest.yaml`, the artefact's provenance (project, artefact, the key and each of its lines, the commit the build ran at and its tree's cleanliness, the toolchain id, the platform, the architecture, the host, the clock in UTC, the size, the artefact's sha256), and `SHA256SUMS`. YAML because the core already reads it (`bin/.devbin/config.yaml`) and a person can read it too. One registry per machine, since an artefact is for its platform: kovacs and gyges keep their own, and the remote-leg runner (D62) copies seals back, never artefacts. On CI, the runner's cache under the same key string (`actions/cache` with `key: devbin-<project>-<artefact>-<key>`), restored before the build step and saved after it, so a run re-fired on an unchanged key pulls. For a release, the release's own assets are the registry's public face: `release attach` takes an artefact from the registry when its key is R's, and the asset's name carries the key's first twelve characters beside the version. Nothing is fetched from anywhere else: a pull reads the machine's registry or the runner's cache, both written by the same user.

**The verbs.** The core gains `bin/devbin cache`: `key <artefact> [--commit <sha>]` prints the key, or refuses (no `build:` block, an undeclared artefact, a dirty input, an unreadable commit, a line or a sha256 it cannot take, an argument it cannot read) with its reason, a key being held to its form, 64 hex digits, before any path is made from it; `get <artefact> [--commit <sha>]` exits 0 with the artefact at its `path` and the line `pulled <artefact> <key>`, 1 when absent, 7 when refused, the cache's own code in devbin's exit-code contract (2 and 3 stay the dispatcher's: an unknown command, and one nothing here implements); `put <artefact>` records the file at `path` under HEAD's key once the inputs are clean, and refuses a dirty tree with a line and exit 7, so a dirty build runs and leaves no record; `list [<artefact>]`; `rm <key>`; `gc [--keep <n>]` keeps the newest n per artefact (3 unless `--keep` says, `CACHE_GC_KEEP` in the code) and every key the newest RELEASE seal names on a `cache<TAB><artefact><TAB><key>` line, the line a cut writes for each artefact it used (WP02b-2 and WP08 write it; until a seal carries one, `gc` keeps the newest n alone and says no seal named a key), the newest by its time, as runlog's `newest_run_stems` reads every kept run, and refuses, removing nothing, when that seal cannot be read; it prints what went and the bytes freed, and acts only on a name of a key's form. A project's `build` handler calls `get` before its build and `put` after; the core's own `build` command does not change; a `derived:` command may do the same; where the handler is the core's own (WP08's formula, WP06's macOS stage), the core calls them itself. The words follow `ci-state`'s discipline: one line, one word, the reason on refusal, never a silent miss.

**What it removes**, per the record: Intent's pre-push cold clone-and-build pulls whenever the clone's inputs are the working tree's, the common case after a commit; Gtools's re-cut after a red leg and its macOS leg's second build on the same inputs pull; Laksa's second prod compile pulls; Conflab, measured by conflab-dc and checked by conflab-vc at ffdba212 (2026-10-31): its three cargo builds are three distinct artefacts (conflab, conflabd, conflab-stamp) plus Conflab.app, each built once per cut in `after:` 2 after the legs are green, and the stamp step writes VERSION into every one's inputs, so no cut can pull an earlier cut's artefact, and the one same-key repeat, conflab-stamp under `test swift` and again under the app build, is already a cargo no-op; the cache removes no build from Conflab's cut, Conflab declares no `build:` block in WP13, and AC-5.4 does not reach it. What a cache could still save there is the dev loop's cold `fullcycle` restore, on two conditions that are Conflab cc's: one declaration of each artefact's inputs (native/stamp/src/inputs.rs already holds it, so a `build:` block would be a second copy unless derived from it), and `conflab doctor`'s build-versus-HEAD rule moving onto the key, since the key ignores history and a pull after a rebase would read as needing a rebuild. The general lesson holds for every consumer: an artefact whose declared inputs carry a per-cut stamp never hits across cuts, by design; the cache's saving is inside one cut (a re-cut after a red leg, a second leg on the same inputs) and in the dev loop. Gtools's ten cold runner builds stay builds, one per platform per key, and a run re-fired on the same key, the re-cut, pulls from the runner's cache. The measure is WP15's builds-per-release column, before and after.

**An absent cache is a miss, never a failure** (hv's question, 2026-10-31 12:5xZ). `DEVBIN_CACHE_HOME` unset or empty means the default root, `$(xdg_dir cache)/devbin`; nothing has to be set for a build to run. A root that does not exist yet is an empty registry: `get` answers 1, absent, the build runs, and `put` makes the root and the entry (`mkdir -p`), so the first build on a machine fills the cache rather than tripping over it. A root that cannot be used (a relative or non-absolute value, a path that is a file or a link to nothing, one this user cannot write, one that cannot be made because the nearest path above it that exists is not a directory this user can write or is a link to nothing, a disk that is full) makes `get` and `put` say so, one line each on stderr naming the root and the reason, before the key asks the toolchain anything, exit 7, and the build handler goes on; a `put` that stops at any step leaves no temporary entry under the root, and a `get` that cannot write the artefact refuses rather than answer absent: the registry is a cache, its absence costs a build and nothing else, and the line is the whole of what No Silent Errors asks. A `put` that fails after a green build never unmakes the build's exit. On CI the same holds: a restore miss of the runner's cache is a build, and a save that fails is a line in the job's log. `bin/devbin doctor` reports the cache root it resolves, the default marked as such, and whether it can be written, as a note when it cannot, and fails an input path the block declares that HEAD does not hold, so a wrong value is read before a cut rather than in one. The one thing the cache never does is pull on a doubtful entry: a key, manifest or `SHA256SUMS` that does not verify is removed with a line and the build runs.

**Integrity.** A pull verifies `SHA256SUMS` and the manifest's key against the key asked; a mismatch removes the entry with a line and the build runs. A directory is restored by tar with its recorded mode bits and nothing else (no owner, no xattrs, no ACLs, no file flags); a file is copied with its mode and times and no file flags, as a directory's tar records none, since a flag such as uchg or uappnd on the registry's copy would leave an entry nothing could replace or remove. The registry is the user's own and is never shared between users or machines in this design; a fleet registry (one on yggdrasil, or GitHub Packages) is a later decision, taken only if WP15 shows the per-machine cache leaves a build worth removing.

**Not done here**: no remote artefact registry; no cross-platform transfer; no cache for a test suite (D57 is that); no claim of reproducible-build equality between machines; no per-project setup beyond the `build:` block.

**Declared limits** (hv's rulings on I8 and I9 of the critic-shell review of 0c70f300..4774c637, 2026-11-01, relayed by vc, decision 122). The `arch` line is the shell's own `uname -m`, so a build run from an emulated shell, an x86_64 bash under Rosetta on an arm64 Mac, is keyed with the shell's architecture whatever its toolchain builds for: on one machine that is a second key and a miss, never a wrong pull, and a wrong pull would need one registry shared between an emulated shell and a native one, which this design keeps per machine. Every tool but cargo is asked its version at the project root, so a toolchain pinned below it (swiftly's `.swift-version`, asdf's or mise's `.tool-versions`) is not the one the key names; every pin in the fleet sits at its repository's root (12 of 36 repositories carry one, none below it), and a per-artefact `dir:` comes with the first adoption that needs one.
