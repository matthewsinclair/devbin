## What happened

A consumer project with a linked worktree reported this (devbin 0.1.23 vendored; relayed by devbin-vc, 2026-11-13). `bin/devbin new <command>` was run at the project's root. The project has no bats suite of its own. A linked worktree (`git worktree add`) sits inside the root at `tmp/worktrees/<name>`, ignored by `/tmp/`, checked out at a commit from before the project's last devbin upgrade, so it holds a vendored runtime of its own. `new` wrote its handler and help as it should, then wrote the test stub to `tmp/worktrees/<name>/bin/.devbin/lib/tmpl/<command>.bats`, beside that runtime's `tmpl/test.bats`. It exited 0 with no warning. The page says that with no suite the stub is skipped. The reporter removed the stray file by hand.

Reproduced on a fixture with canon's checkout at main (2026-11-13). A project `demo` was set up with devbin vendored and committed, no suite, and a linked worktree at `tmp/worktrees/wt`. `bin/devbin new greet` printed `wrote  tmp/worktrees/wt/bin/.devbin/lib/tmpl/greet.bats` and exited 0. With a suite at `tests/unit/a.bats` and the worktree at `.worktrees/wt`, the stub went to `.worktrees/wt/bin/.devbin/lib/tmpl/greet.bats` instead. The bytewise sort put the worktree's runtime, and then the worktree's own `tests/unit/a.bats`, ahead of the project's `tests/unit/a.bats`.

## The walk

`test_dir` in lib/cmd/new (lines 143 and 144) runs one `find_walk` over the whole of `$PROJECT_ROOT` for `*.bats`, excluding only `"$DEVBIN_LIB/*"` and `*/.git/*`, sorts the hits with `LC_ALL=C sort`, and scaffolds beside the first. The `$DEVBIN_LIB` exclusion is the project's own runtime, by exact path, kept so that its `tmpl/test.bats` is never read as the suite. Nothing excludes another copy of the runtime, so a linked worktree's `bin/.devbin/lib/tmpl/test.bats` is a hit. Nor does the walk stop at another work tree, a directory holding a `.git` file, so that worktree's own suite counts as well. A worktree named under `tmp/`, or with a leading dot, sorts ahead of `tests/`.

## Why it matters

`new` writes a file into another work tree, into a vendored runtime that upgrade manages and nothing runs. It does so in silence, and in the reported case where the page promises no stub at all. Linked worktrees inside a project's root are a common layout, eg `tmp/worktrees/`, and one checked out before an upgrade always holds its own runtime.

## Not yet known

- Whether any other walk over a project's root, in devbin or in a gate, reads into a linked worktree the same way.

## Options, none chosen

- Leave out every vendored runtime, `*/bin/.devbin/lib/*`, not only the project's own.
- Prune every directory below the root that holds a `.git` file or directory, so another work tree or a nested repository is never read as the project's.
- Read the candidates from what git tracks (`git ls-files '*.bats'`), so ignored paths are never a suite; a project outside git needs the walk still.
