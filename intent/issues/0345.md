## What happens

A `test shell` run (or `test all`, or a project's own runner calling `"$DEVBIN_LIB/bats-lanes"`) prints bats's TAP, the lanes' own lines, and a verdict.

Its log holds no time for any file or test. The seal's own start and end stamps hold the whole run's time and nothing finer.

Nothing records the machine's load either. A run that took twice as long as the one before cannot be told apart, after the fact, from a run that met a busy machine. The suite can make that load itself: a parallel lane at twenty-four jobs reads a load of several hundred on a sixteen-CPU Mac.

## Why it matters

Every tuning decision about the suite so far was made without a per-file time: issue 0340's job count, the split between lanes, and which files to cut down.

devbin's suite on rhadamanth took anywhere from 1.6 to 6.7 times as long for the same commit, the same configuration and the same day. No seal could say why.

The same gap holds for every project whose suite runs through the lanes.

## Where

- lib/bats-lanes. bats runs the parallel lane's files under GNU parallel with `--keep-order`, and keeps no time of its own.
- `bats --timing` adds a time to each test's TAP line. That would change every line that the seal's counter and a project's own readers parse, and it gives no time for a file.

## Fix

bats-lanes takes the place of the parallel program that bats runs, through bats's own `BATS_PARALLEL_BINARY_NAME`.

- It hands GNU parallel each file's command behind a recorder, which writes the moment the file starts and the moment it ends.
- The run's results pass through untouched.
- Before its verdict, which stays the run's last line, the run prints:
  - each file of the parallel lane with its wall time, the slowest first, with its exit when that was not 0;
  - the serial lane's time;
  - the one-minute load average at the run's start and at its end, read from /proc/loadavg or vm.loadavg.

Every bats the runner supports, 1.12 and 1.14, starts each file as `bats-exec-file ... <file> <test list>` after parallel's `--`. A command of any other shape is run as it is, and the run says it has no times.

The recorder hands back the caller's own BATS_PARALLEL_BINARY_NAME to everything parallel starts. So a bats that a test runs never reaches it.

A file's wall time runs from its first start to its end. It includes any wait for a free job slot: the one-second wait issue 0340 describes shows up here, so the times show it too.

## Acceptance

- A run over a fixture suite names every file of its parallel lane once, with a wall time, the slowest first, then the serial lane's time and the load at the start and at the end, all before the verdict line.
- A file whose test failed is named with its exit.
- A bats run by a test inside the lane sees neither the recorder's variables nor a changed BATS_PARALLEL_BINARY_NAME.
- Every existing lanes arm in testhandler.bats, and builtins.bats's project-runner arm, stay green.
