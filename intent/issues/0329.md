The built-in macOS stage signs and notarises during the legs step (`macos leg`, lib/release.macos:96-111), before the tag. A project whose build stamps its kind from the tag (Intent's issue 0534) therefore ships binaries that say `dev`. Its publish ships one app zip, and bin-publish one tarball named `<project>-<version>-<triple>.tar.gz`. A project shipping several named assets (Intent's: two bare binaries, a support tarball and an app zip) cannot adopt either.

Asked: a stage step that runs after the tag, and a publish that ships the project's declared assets under their own names.

Raised by intent-dc through intent-vc, 2026-11-10. Not for the next release (0326 to 0328): Intent 3.3.0 publishes through its own `after:` command with release.formula false, so it needs nothing from this issue. For the release after next.

The stage stays before the tag. The issue asked for a stage step that runs after the tag; the macOS stage stays a leg before it instead, so a refusal or a notary rejection still stops the cut with nothing public. A stage after the tag would meet a rejection with the tag public and the release's macOS assets missing, a state only a resume past the tag repairs. What the issue needed from running after the tag, a build that stamps its kind from the release's tag, the stage now has before it: it is handed the release's target, as every other command of the project's own that a cut runs is.

- 0329-1: the cut's macOS stage is handed DEVBIN_RELEASE_VERSION and DEVBIN_RELEASE_TARGET_TAG through release_target_run (issue 0327), so a build that stamps its kind from the tag reads the tag the release commit is about to carry.
- 0329-2: bin-publish packs the binaries' archive under the project's declared name, macos.pack.name, a template of {project}, {version} and {triple} whose default is the name archives were packed under before, inside its declared top-level directory, macos.pack.root, by default none; and macos.pack.files takes a directory, each file git tracks under it packed at its path. A name or root bin-publish cannot pack is refused before the keychain is asked, and by the cut's pre-flight before anything is stamped.
- 0329-3: a cut's object step zips and attaches the app through macos publish, where macos.app is declared under object: local, after bin-publish and before the formula step, so the cask the formula step renders reads the zip in SHA256SUMS. The confirm step names the zip as work left until the release carries it, and a finished cut run again runs no publish.
- 0329-4: render refuses a formula template whose install runs a line before @@INSTALL@@, naming the line and T8, since no template lays its assets out by hand.
- So a project shipping several assets, as Intent's two binaries, its support tree and its app are, packs its binaries and support tree as one archive rooted at the install root under its own name (0329-2) and its app through the object step (0329-3), and its template lays out nothing by hand (0329-4).
- docs/configuration.md, docs/dev-opt-brew.md's T8, lib/config.reference.yaml and lib/pages/release.md, macos.md and formula.md say so.

Ten new arms: one in releasecut.bats for 0329-1 (a cut whose tag step is refused runs the stage once at the release commit, handed the version and tag, and tags nothing); five in macos.bats and one in releasecut.bats for 0329-2 (a pack under a declared name and root holding a support directory's tracked files at their paths and nothing it leaves untracked; bin/ alone packed inside a root; refusals of an unfilled placeholder, a root named bin and a directory with no tracked file, each uploading nothing; a cut's pre-flight refusing a root named bin before anything is stamped); two in releasecut.bats for 0329-3 (a cut under object: local names the zip at its confirm step and runs publish at the release commit before the formula reaches the tap; a finished cut run again runs no publish); and one in formula.bats for 0329-4 (a comment and a blank line before @@INSTALL@@ render, a line that installs an asset by hand there is refused and writes nothing).
