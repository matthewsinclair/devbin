## What is wrong

`bin/devbin release` runs each `after:` command in order. When one fails, it still runs the commands after it. The after step's loop (`lib/cmd/release:4225-4262`) adds a failure to `after_failed` and goes on to the next line. It does this for a command that exits non-zero and for a line that holds no words.

The contract says so in two places. The comment at `lib/cmd/release:4211-4215` says "a failure is reported and undoes nothing, and the next command still runs". `docs/configuration.md:431` says "One that fails does not stop the next." `tests/unit/releasecut.bats:3074` holds it as a rule.

The core's own steps stop at a failure: the formula step runs only once the object step has succeeded (`cut_formula_step`, `lib/cmd/release:4205-4209`). An `after:` list has an order too, and a later command can depend on an earlier one. The after step does not stop for that.

## What it costs

A later command acts on work that failed, after the tag is public:

- A tool whose `after:` publishes its distribution asset and then runs `formula publish` can push a formula or cask whose asset is not on its distribution repository. Every brew install of that release then fails, until a person fixes it by hand. gtools/dc found this in the rework of gtools#I17c1577. Gtools closes it there by reading the distribution release back before its formula publish.
- Intent declares `bin/devbin cut publish`, then `bin/devbin brew smoke --at-tag`. When the publish fails, the smoke test still runs, against a tap that does not carry the release.

The cut still exits 1 and names the failed command, so the release does not read green. But the later command has already run, and a tap push cannot be taken back.

## Fix outline

1. Stop the after step at the first command that fails or holds no words. Run no command after it.
2. The after row stays FAILED. It names the command that failed, its exit, and each command that did not run.
3. The closing lines keep "the release is published, and the tag and the release stand". The remedy names the failed command and each command after it, to run by hand in their order. It also says that a run of the cut again runs every `after:` command again, because nothing records that one ran.
4. Change the contract where it is stated: the comment at `lib/cmd/release:4211-4215`, `docs/configuration.md:431`, `lib/config.reference.yaml:662`, and `lib/pages/release.md` where it describes the after row.
5. Add no key that keeps the old behaviour. No project's `after:` list today has a command that must run past a failure before it.

- Consumers with more than one `after:` command: Intent today (`cut publish`, then `brew smoke --at-tag`), and Gtools after gtools#I17c1577 (a distribution publish, then `formula publish`). Molt, Pplr, Cldr, Ccusage, Gtools' main and devbin declare one command each.

## Done when

- A cut whose `after:` is `false`, then `touch two`, ends with the after row FAILED, exit 1 and the release published. `two` is not made, and `touch two` is named as not run. The arm is red at the base, where `two` is made.
- A line that holds no words stops the step the same way.
- The remedy names the failed command and each command not run.
- The contract text in the four places above says that the step stops at the first failure.
