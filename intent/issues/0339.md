From Intent's ST0093 (hv's word, relayed by intent-vc, 2026-11-11), half B item 2.

Serial bats is on the critical path of every leg Intent ran for 3.3.0. On CI, its macOS test job ran 7m21s of serial bats after the release build, and the same suite ran four times on the shipping commit.

What exists:
- The core's catalogue row for `test.shell` is `bats tests` (lib/builtins:126). It is serial, and lib/cmd/test (16 lines) adds nothing to it.
- devbin's own parallel runner is project-local: `bin/.devbin/cmd/.lib/bats-lanes`, called from devbin's own `bin/.devbin/cmd/test:139`. It runs a parallel lane with `bats --jobs N --filter-tags '!serial'` and then a serial lane for tests tagged `serial`. It checks the count against an untagged `bats --count`, and it falls back to one lane when GNU parallel is absent. No other project can reach it.
- Intent's `test shell` is its own `tests/run_tests.sh`, declared at Intent's `bin/.devbin/config.yaml:155-164`. It pipes every .bats file through `xargs -0 bats`, serially (`tests/run_tests.sh:98`).

Ownership: the runner belongs in the core, and adopting it belongs to each project. A project knows which of its tests cannot share a host (Intent's daemon-socket tests are one such set), and only the project can tag them `serial`.

Ask:
1. Move bats-lanes into the core, as one library under lib/, with devbin's own `test` calling the core copy. The catalogue's `test.shell` runs through it. Its sizing (`lanes_jobs`), the GNU parallel probe and the count check move unchanged.
2. Give a project with its own runner one call into the lanes runner, for a directory and the environment the project exports. Intent's runner, which exports BATS_LIB_PATH and INTENT_HOME, then calls that instead of `xargs bats`.
3. A leg host with no GNU parallel says so in its leg log and runs one lane, as today. Every leg host gets `parallel` (kovacs: `apt-get install parallel`). That install is hv's or the host sysadm's.

Proof: devbin's own suite through the core copy, once; that run is the cut's own `test`.

Size M for the core. Intent's adoption (serial tags on its daemon and socket files, and the runner change) is Intent's own package, sized there. No dependency on 0333 or 0334.

- Ask 1: the runner is lib/bats-lanes, moved by git mv from bin/.devbin/cmd/.lib/, so every install vendors it. Its sizing (lanes_jobs), the GNU parallel probe, the count check and its printed lines are unchanged. It no longer changes to PROJECT_ROOT, and reads its directory from where it is called. devbin's own test calls "$DEVBIN_LIB/bats-lanes" "$PROJECT_ROOT/tests/unit". The catalogue's test.shell row is @builtin: builtin_test_shell in lib/cmd/test runs "$DEVBIN_LIB/bats-lanes" "$PROJECT_ROOT/tests" when handed nothing, which is what all hands it, and `bats tests` with whatever it is handed otherwise, as the row ran before.
- Ask 2: a project's own runner calls "$DEVBIN_LIB/bats-lanes" <dir>. bin/devbin exports DEVBIN_LIB to every command it runs, so a runner on an option's run: line has it, and every variable the runner exports, such as Intent's BATS_LIB_PATH and INTENT_HOME, reaches bats in both lanes. The runner needs no PROJECT_ROOT, which Intent's unsets, so Intent's runner adopts with one line in place of its find and xargs -0 bats: "$DEVBIN_LIB/bats-lanes" "$SCRIPT_DIR/unit". Its serial tags and that line are Intent's own package.
- Ask 3: no code. Without GNU parallel the runner's first line says so, naming the brew and apt routes, and it runs one lane, as before; through test shell that line is in the gate's output, its seal and a leg's log. With GNU parallel, the parallel lane runs bats --jobs and --filter-tags, so it needs bats-core 1.8.0 or later, which added --filter-tags.
- lib/pages/test.md says what the lanes do, how a test that cannot share a host takes bats's serial tag (test_tags on the line before it, or file_tags for its whole file), what DEVBIN_TEST_JOBS and DEVBIN_JOBS set, and the call for a project's own runner.

Two new arms in builtins.bats: test shell runs a shell project's tests/ in two lanes from inside tests/, and a project's own runner, with PROJECT_ROOT unset, calls the lanes runner by DEVBIN_LIB, a test in each lane reading a variable it exported. Thirteen arms changed in testhandler.bats: the two handler arms want the core copy by its absolute path, and the eleven lanes arms run lib/bats-lanes. All fifteen were red at the base, the handler arms and the two new arms each on its own finding, the lanes arms because the base has no lib/bats-lanes. Nineteen arms were green at the fix: those fifteen, and four the change reaches (builtins.bats's arm over every @builtin row, its two end-to-end gate arms that run test shell, and dispatch.bats's catalogue --purge arm).
