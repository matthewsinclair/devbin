From Intent's ST0093 (hv's word, relayed by intent-vc, 2026-11-11), half B item 2.

Serial bats is on the critical path of every leg Intent ran for 3.3.0. On CI, its macOS test job ran 7m21s of serial bats after the release build, and the same suite ran four times on the shipping commit.

What exists:
- The core's catalogue row for `test.shell` is `bats tests` (lib/builtins:126). It is serial, and lib/cmd/test (16 lines) adds nothing to it.
- devbin's own parallel runner is project-local: `bin/.devbin/cmd/.lib/bats-lanes`, called from devbin's own `bin/.devbin/cmd/test:139`. It runs a parallel lane with `bats --jobs N --filter-tags '!serial'` and then a serial lane for tests tagged `serial`. It checks the count against an untagged `bats --count`, and it falls back to one lane when GNU parallel is absent. No other project can reach it.
- Intent's `test shell` is its own `tests/run_tests.sh`, declared at Intent's `bin/.devbin/config.yaml:155-164`. It pipes every .bats file through `xargs -0 bats`, serially (`tests/run_tests.sh:98`).

Ownership: the runner belongs in the core, and adopting it belongs to each project. A project knows which of its tests cannot share a host (Intent's daemon-socket tests are one such set), and only the project can tag them `serial`.

Ask:
1. Move bats-lanes into the core, as one library under lib/, with devbin's own `test` calling the core copy. The catalogue's `test.shell` runs through it. Its sizing (`lanes_jobs`), the GNU parallel probe and the count check move unchanged.
2. Give a project with its own runner one call into the lanes runner, for a directory and the environment the project exports. Intent's runner, which exports BATS_LIB_PATH and INTENT_HOME, then calls that instead of `xargs bats`.
3. A leg host with no GNU parallel says so in its leg log and runs one lane, as today. Every leg host gets `parallel` (kovacs: `apt-get install parallel`). That install is hv's or the host sysadm's.

Proof: devbin's own suite through the core copy, once; that run is the cut's own `test`.

Size M for the core. Intent's adoption (serial tags on its daemon and socket files, and the runner change) is Intent's own package, sized there. No dependency on 0333 or 0334.
