## What happened

A consumer project reported this (relayed by devbin-vc, 2026-11-13). In an interactive zsh that had already run the tool while it resolved to brew, `bin/devbin use dev` and then `bin/devbin use opt` each pointed the link in `~/.local/bin` as they should, and `~/.local/bin` comes first on PATH. In that same shell, `<tool> --version` still printed brew's line. zsh had hashed the command's path when it first ran it, and it keeps that path until `rehash` or `hash -r`, whatever the link now says. `use`'s own report, doctor in a fresh bash and the shadow check were all right.

## Why it matters

The switch is the one verb that moves a tool between dev, opt and brew (docs/dev-opt-brew.md, T5), and the maintainer checks it by running the tool in the shell they are in. A child process cannot clear its parent's hash table, so `use` can never fix this itself. It can only say so. Today nothing in devbin says so: `use`'s report, its help, doctor and T5 never mention rehash, and T5's "What the shadow check cannot see" names processes started without the login PATH, but not a login shell that hashed the old path. The same holds for devbin's own `use`. bash hashes too (`hash -r`), and a shell that never ran the tool before the switch is not affected.

## Not yet known

- Whether `use` can tell a caller's shell has hashed the name. It can't read the parent's table, so the line would be said on every switch, or only when the tree changes.
- Whether the line belongs in `use`'s report, in T5's text, or in doctor, which runs in its own shell and cannot see the caller's either.

## Options, none chosen

- `use` ends a switch that changed a link's tree with one line: open shells that already ran `<link>` keep its old path until `rehash` (zsh) or `hash -r` (bash).
- doctor adds the same as a note under the switch row.
- T5 names the case beside "What the shadow check cannot see", with the remedy.
