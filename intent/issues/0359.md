Filed for the weigh of the release after next (vc's todo 214). Record only, with no work now. Laksa's critic review of its runners found it, reading lib/runlog as 0.1.25 ships it; lib/runlog is unchanged at main since v0.1.25.

`run_gate` does four things inline, and no function a handler can call does them. A project's handler that runs a gated tool without the wrapper must copy all four:

- the INT, TERM and HUP traps that note a signal and let the gated command end first (lib/runlog:2371-2373);
- the progress file's name, `$log.progress` (:2383);
- the exit for a run a signal ended, 128 plus the signal's number (:2430);
- the "ENDED BY SIG..." line that says why the log stops where it does (:2431).

A parity guard that derives names from `run_gate`'s body sees only the functions it calls, so it cannot see one of those copies drift. The fix to weigh: lift the four into functions `run_gate` calls (an arm, a progress-file name, a close that gives the exit and the line), so a handler calls the same ones and the guard can name them. The critic's staged arm and close shape, with its traps_restore, is in the probes below as p3.sh and traps_restore.fn.

## Resolution

Fixed by unit 0359-1, landed at 09b678ee, for 0.1.27 (written 2026-11-17 16:57Z by date -u).

run_gate's four inline pieces are functions in lib/runlog it calls, so a project's handler that runs a gated tool without run_gate calls the same ones, and a guard can name them:
- gate_signals_arm <caught> <saved> saves the caller's INT, TERM, HUP and PIPE handlers into the variable <saved> names, for traps_restore, and notes each of INT, TERM and HUP by name into the variable <caught> names.
- gate_progress_file <log> names the progress file beside the log. Pure.
- gate_signal_close <signal> <name> gives the exit, 128 and the signal's number, and the ENDED line, TAB-separated. Pure.

run_gate's behaviour is unchanged. 0360-1's SIGPIPE handling stays just before its pipeline, beside the element resets it belongs with.

Proof: dc's runs on the Desk, stacked on 0360-1 on main c614b4c6.
- Four arms: the arm, the progress name, the close for INT, TERM and HUP (exits from kill -l), and a guard that run_gate calls the three and holds no inline copy. All four read red at the base, 0360-1's tip, where the functions do not exist and the guard finds the inline copies.
- The light probe (01M7N2PXJVDZ9N1428SMEV3QXD) read them 4 of 4 at --jobs 1. The first formal run (k36s) found the arm's assertion red at --jobs 8: bats runs each arm as a background job, where bash ignores INT, so the saved handlers held an ignored INT line. The arm now reads the saved TERM line alone.
