## What happened

Reported as molt#0100. A cut's local gates leg ran for 1191 seconds and then failed with:

```
release: gates: a gate changed the tree: intent/whiteboard/vc/board.json, intent/whiteboard/vc/wip.md -- the gates examine the release commit and must not write to it
```

No gate wrote those files. They belong to a peer node's whiteboard, in a checkout that several sessions share, and the peer had left them uncommitted under the rule against writing to the shared tree during another node's slot. The candidate's CI was green at the same sha, and the run had no `not ok`. The resume passed once the two files were committed. The cost was the whole gate run, one candidate push and deletion, and a cut held up.

## The code

`release_gates_run` (lib/release.steps:609, the refusal at :627) reads `release_tree_state` before the first gate and after the last, and refuses on any path whose line differs. `release_tree_state` (:572) lists `release_dirt`'s paths, each with its content hash. A path dirty at the start and left alone does not fire. A path that a peer writes again, or commits, while the gates run does fire: any `intent wb` verb rewrites the node's `board.json` and `wip.md`, `pickup` among them on every session boot, and an event file appears with each. So in a shared checkout, a peer's ordinary boot or heartbeat during a long gate run fails the cut. Pre-flight's check after each command (:706) has the same shape and the same wording.

The HEAD check after the gates (:630-632, "a gate moved HEAD") is a different question and is right as it stands.

## Two defects

**1. The comparison takes in paths no gate reads.** The gates examine the release commit, and the check exists to say that nothing they ran wrote to it. `intent/whiteboard/**` and `intent/.canon/events/**` are the board's live state, written by every node at any time, and no release gate reads them. In a shared checkout, holding them still for the length of a gate run is a condition the run cannot ask of its peers. Under the single-writer rule, the remedy the message implies, fixing what it names, is also not open to the session running the cut, since the paths are another node's.

**2. The message claims a cause the code cannot know.** "a gate changed the tree" asserts that a gate wrote the paths. The code only knows the tree differs between two reads, and the reader goes looking for a writing gate that is not there. Something like "the tree changed while the gates ran: <paths>" is true. It points at the fix, which is to find who wrote them, and it fits a peer as well as a gate. The pre-flight line needs the same change.

## Not yet known

- Whether any gate in any consumer's release.gates reads the board or the event log. If one does, an exclusion by path hides a real write.
- Whether pre-flight should exclude the same paths. It runs short commands, so the window is small, but the wording is wrong there either way.

## Options, none chosen

- Leave out `intent/whiteboard/**` and `intent/.canon/events/**` from both reads, naming them as excluded in the run's record, and keep everything else and the HEAD check as they are.
- Scope the comparison to what the gates read: tracked paths outside the board and the event log, or a declared set of inputs. Another estate's build script already checks its own declared input paths this way, so a peer's write cannot fail its build.
- Reword both refusals to say what the code knows, eg "the tree changed while the gates ran: <paths>", whatever the scope.
