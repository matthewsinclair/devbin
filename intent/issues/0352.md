## What happened

Intent 3.3.1's published Linux musl binaries report their source kind as `dev`, while its darwin binaries report `release`; both are built at the release commit c64a42e29. Intent's linux-release workflow builds them on GitHub CI when the cut pushes candidate/v3.3.1, before the tag exists. Intent stamps `release` only where a tag sits at the commit or `DEVBIN_RELEASE_TARGET_TAG` is set. A cut hands `DEVBIN_RELEASE_VERSION` and `DEVBIN_RELEASE_TARGET_TAG` only to the commands it runs itself (docs/configuration.md, issue 0327; lib/pages/release.md): preflight, derived, the gates and legs, the macOS stage, the formula step and after. A CI workflow started by the candidate push is handed neither. Found by agentic-engineering's devvm 0.5.0 arm64 rehearsal on 2026-11-13 and diagnosed by intent-vc.

## Why it matters

Any project whose CI builds release artefacts on the candidate branch cannot read the release's target the way the rest of the cut does, so each one works it out for itself in its own workflow (Intent's interim fix is config in its workflow). That is a per-project special case of something the core already owns.

## Options, none chosen

- Document a supported way for a candidate-triggered workflow to derive the pair from the tree (the version the tree declares and `release.tag`), eg a `bin/devbin release target` verb that prints both, so a workflow step exports them.
- Carry the pair in the candidate itself, eg a file or a ref the workflow reads.
- Leave it to each project's workflow, and say so in release.md.
