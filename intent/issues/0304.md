Found by the critic-shell review of ST0011 WP02a (2026-10-31), outside that unit. The cut's steps run under two errexit states, one per mode, so the same step fails two ways.

The two code paths, at main:
- A dry run: lib/cmd/release's release verb calls cut_run directly (lib/cmd/release:3383-3384), inside bin/devbin, which runs under `set -euo pipefail` (bin/devbin:17). cut_run runs with errexit on.
- A real cut: the same verb runs cut_run as run_gate's command (lib/cmd/release:3386-3389). run_gate sets `set +e` before the gated pipeline (lib/runlog:2160) and restores the caller's errexit only after it (:2189), and the command runs on the pipeline's left side, so cut_run runs with errexit off.

What a failing step does in each mode: a command in cut_run that fails without a check of its own ends a dry run at that command, with that command's status, and no FAILED row and no summary, since cut_fail never runs; in a real cut the same failure is passed over and the cut goes on to its next statement. So a failure a dry run shows the person is invisible in the cut that tags and publishes, and a dry run can stop where the real cut would not. Nothing found today depends on it: ST0011 WP02a's review checked that the statements that unit adds check their own failures; the gap is that nothing holds cut_run to that.

Fix (cc, after ST0011 WP02b unless it bites sooner): one errexit state for both modes, the real cut's, so a dry run predicts the cut that publishes: the dry run runs cut_run with errexit off as run_gate does, and every command in cut_run whose failure must stop the cut checks it and fails through cut_fail, naming its step (No Silent Errors). An arm proves it: a step whose command fails unchecked reads the same, a FAILED row naming the step, in a dry run and in a cut.


Also (CRITIC-4 on ST0011 WP02b-1, its R4 and probe p7): release_group_start's write of the group's id (lib/release.steps) runs under its caller's errexit, so where that is on, a failed write ends the wrapper with 1 before its wait, while the run goes on in its own group with nobody waiting on it. One errexit state for every caller closes it, and the write gets a guard with its reason beside it.



Resolution (vc, 2026-11-01 15:46Z by date -u): fixed by ST0011/02b, landed at 9a0bb40f. In its own words: a dry run runs cut_run as run_gate runs the real cut, in a subshell with errexit off. So a failing command stops both at its own check, FAILED at its step, and a dry run predicts the cut that publishes. Every read in cut_run whose failure must stop the cut checks it, failing through cut_fail with its step's name or adding a pre-flight refusal. release_group_start's write of the group's id is guarded. Its arm is releasecut.bats's date +%F refusal, which stops a dry run and the cut alike, FAILED at resolve. The close commit cb404bdb has the direction backwards, so this paragraph is the record.
