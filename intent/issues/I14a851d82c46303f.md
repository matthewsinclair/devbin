## What is wrong

`release.gate_cache.max` sets the size that the gates' cache (DEVBIN_GATE_CACHE) is held to, on the cutting machine and on each host in `release.legs` (lib/config.reference.yaml:654-655). Its default is 12G. Neither devbin's config nor Intent's sets its own value, so both use 12G.

The bound applies only when a run starts (`gate_cache_bound`, lib/release.legs:193, called at :284): a cache over it is emptied, and one at or under it is kept. A run can then grow its cache past the bound, and the next start empties it. Each project on a host has its own cache, `~/work/<project>-leg.cache`. So one project's cache can use 12G or more before its bound acts, and two projects on one host can use twice that.

On 2026-11-26, kovacs had 12G free, and ~/work held 15G of the leg runner's bare repositories and caches (kovacs-sysadm's figures, relayed by devbin-vc). The default bound is all of that free space.

Issue 0361 set the bound and its 12 GiB default, after it measured the cache at 15.2 GiB on rhadamanth and 8.1 GiB on kovacs (2026-11-16). The default does not refer to a host's free space.

## What it costs

A leg whose cache fills the host's disk fails in its build or its tests, for a reason that is not in the release. The disk is then full for everything else on the host too. Issue 0361 added the bound because a cache filled a host's disk. With this default, that can still occur on a host with 12G free or less.

## The question

The fix is open. Two shapes so far:

1. A smaller default for `release.gate_cache.max`.
2. A bound read from the host's free space when a run starts, eg a part of what `df` reports.

cc is authoritative on what the config key means. Either way, the leg's log keeps its line that says what the bound did.
