Found by Gtools (gtools-vc, from gtools-dc's measurement in Gtools issue 0129), 2026-11-23 04:22Z by date -u.

On macOS, brew relocates and ad-hoc re-signs a keg's precompiled native objects (Gtools' exqlite and mdex NIFs) after the install body has hashed them, so the manifest row fails `doctor` on a keg nobody touched. devbin's T8 install body (`bin/devbin install --prefix libexec --managed-by brew`) hashes at that same moment, and devbin has no re-hash or relocation handling: a grep of `bin/.devbin/lib` and `docs/` finds none. Gtools' formula works around it today by re-hashing in `post_install`, which brew has deprecated.

So issue 0326's adoption in Gtools (Gtools I7bd0048), as filed, regresses Gtools 0129 on every macOS brew install. It blocks that adoption, and any other estate whose keg holds Mach-O files brew rewrites.

The two shapes gtools-dc offers, both in devbin:

- a re-hash step that `post_install_steps` calls, after brew's relocation; or
- `doctor` reading a brew keg's Mach-O files without their load commands and code signature.

The shape is chosen in devbin-cc's Gtools plan under 0326, and lands in devbin before Gtools' adoption.
