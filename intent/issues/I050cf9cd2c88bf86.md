## What is wrong

When an `after:` command fails, the cut's closing lines say to run it by hand (`lib/cmd/release:4282`). With I900790a they also name each command not run after it, to run by hand in order. A hand run does not get what the cut gave the command:

- **The release's target.** The cut runs each command through `release_target_run` (`lib/cmd/release:4251-4255`, `lib/release.steps:741-745`), which hands it `DEVBIN_RELEASE_VERSION` and `DEVBIN_RELEASE_TARGET_TAG`. The contract says that every `after:` command gets the pair (`lib/pages/release.md:141`). A hand run gets neither, so a project's own command that reads the release's target from them reads nothing.
- **The confirm step's yes.** The cut hands `DEVBIN_RELEASE_CONFIRMED=<tag>` when the confirm step was answered (`lib/cmd/release:4251`). `formula publish` reads it as its yes for the tap (`lib/cmd/formula:1299`). By hand it asks the person at the terminal. That run differs from the cut's, but it is not a wrong one.
- **The words of the line.** The cut splits the line on blanks and never evaluates it (`run_words`, `lib/helpers:496`): a quote, a `$` or a `;` is a literal character. A person who pastes the printed line into a shell has it evaluated, so the shell can run another argv.
- **The directory.** The cut runs each command from the project root (`docs/configuration.md:431`). The remedy does not say where to run it.

So a hand run is not the run that the cut would have made, and it comes after the tag is public. Which project commands read the pair is not measured here. The contract hands the pair to every `after:` command, so the remedy must hand it too.

## Fix outline

A. Print each command for its hand run as the cut runs it. This is in the lines that I900790a prints.

1. One line a command, in order: the failed command first, then each command not run, as I900790a prints them.
2. Each line is a shell line that runs the same argv with the same target: `DEVBIN_RELEASE_VERSION=<version> DEVBIN_RELEASE_TARGET_TAG=<tag> <word> ...`, each word quoted with `printf %q`, so that nothing in it is evaluated.
3. The remedy says to run the lines from the project root, and names the root.
4. `DEVBIN_RELEASE_CONFIRMED`: print it on the line too, as `DEVBIN_RELEASE_CONFIRMED=<tag>`, where the cut handed it, since the confirm step's question named these commands at this tag and the value binds the yes to that tag. Or leave it out, so that a command that asks, asks. The plan decides, and says why.
5. Print neither `DEVBIN_IN_GATE` nor `DEVBIN_GATE_TTY`: outside a gate a command reads the person from its own stdin (`gate_tty_flag`, `lib/helpers`), which at a hand run is the terminal.

B. Or a verb that runs the rest of the step for a released tag as the cut runs it: the same environment through `release_target_run`, the same stop at the first failure, and a confirm of its own. The remedy is then one command, and the environment is set in one place. This is a unit of its own.

The plan reads `release target` first (`lib/cmd/release:910`), which prints the pair as the tree declares it, and says whether the remedy uses it.

## Done when

- Under A: a cut whose `after:` is `false`, then a command that prints its environment and its argv. Each printed line, run by bash from the project root, gives the same `DEVBIN_RELEASE_VERSION`, `DEVBIN_RELEASE_TARGET_TAG` and argv as the cut would have given. The arm is red at the base, where the remedy says only to run what failed by hand.
- A word that holds a `$`, a quote or a `;` is printed quoted, and the hand run gets it as one literal word.
- docs/configuration.md step 11 and lib/pages/release.md say what the printed lines carry.
