## What happens

lib/bats-lanes runs the parallel lane as `bats --jobs N --filter-tags '!serial' <dir>` (lib/bats-lanes:210). N defaults to half the CPUs and never fewer than two: 2 on kovacs, which has had 4 vCPUs since hv resized it on 2026-11-12, and 8 on rhadamanth.

`bats --jobs N` runs N files at once through GNU parallel. It also runs the tests inside each file through `bats-exec-file -j N`, and every file of the run shares one semaphore of N slots, kept in the run's own temp directory (bats-core's lib/bats-core/semaphore.bash). When a file's next test finds no free slot, the file sleeps a whole second before it looks again (`sleep 1`, under "TODO: avoid busy waiting"). bats 1.12.0, kovacs's, and 1.14.0, rhadamanth's, have the same code. macOS has no flock, so there the lock around taking a slot is shlock, and that polls with `sleep 1` too. A freed slot stays idle until a sleeping file wakes, so a suite of short tests spends most of its wall time asleep.

## Evidence

- devbin 0.1.23's third cut, 2026-11-12: kovacs's leg had run 1230 tests in about 30 minutes when kovacs-sysadm stopped it at hv's word (09:28:29Z, vc's relay). rhadamanth runs all 3121 in about 10.
- hv: "The SLEEPS take more time (by a factor of 4 or 5) than the actual tests!"
- kovacs-sysadm sampled the sleeps. All of them came from `bats-exec-file -j 2` (fullcycle.bats, harness.bats) under `parallel --jobs 2`. The VM was 53 to 83% idle, with no iowait and no swap.
- The suite has sleeps of its own as well (fullcycle.bats's `sleep 3`, the `sleep 10` watchdogs, the polls in heartbeat, contract, surfaces and releasecut). Those are the tests' own waits, not the runner's.

## The fix

Cut the suite's wall time where the waiting is, on every host, without losing coverage or isolation. Measure before choosing, on rhadamanth and on kovacs, over representative files that include releasecut, fullcycle and harness. Compare:

- the current split;
- `--no-parallelize-within-files`, which runs each file's tests one at a time and whole files N at a time under GNU parallel, with no semaphore;
- N itself. Half the CPUs is low for a suite that mostly waits, and a large file run alone can become the long pole.

lib/bats-lanes ships to every estate through the sweep, so the fix says what it changes in their suites.

## Resolution

Fixed in three landings on main in devbin 0.1.23's batch: 7e1d18d2 (unit 0340-1), 0c3d5a1b (unit 0340-2) and c53e6df7 (unit 0340-3, which takes 0340-2 back). 0340-1 and 0340-2 were proved in cc's stacked run k340 beside 0334-2 and 0341-1, and 0340-3 in its own run on devbin-vc's desk. All three shipped in v0.1.23, release commit 7ab21982, released 2026-11-12 19:02Z.

- The cause, read in bats-core's source (1.12.0, kovacs's, and 1.14.0, rhadamanth's, alike). Under `bats --jobs N`, every file of a run shares one semaphore of N slots. A file that finds no free slot sleeps a whole second before it looks again, so a lane with few slots leaves freed slots idle.
- The issue's three choices were measured before choosing, at the base.
  - `--no-parallelize-within-files` was the slowest. On rhadamanth, five files (691 tests, releasecut among them) took 935.2 s at N 8 against 298.0 s for the current split, since releasecut alone takes 918 s run one test at a time.
  - N itself was the lever. On kovacs alone, harness and fullcycle (194 tests) took 157.4 s at N 2, 93.9 s at N 4 and 40.4 s at N 8. A sweep from N 8 to 64 found its knee at 16, and it was flat within noise from 12 to 24.
  - On rhadamanth, under heavy outside load (which makes a higher N look faster), the same two files took 101.8 s at N 8 and 56.2 s at N 24, its fastest point.
  - hv's word, through vc: at least 16, if not 24, and max out rhadamanth.
- 0340-1: the parallel lane's N is half the CPUs and never fewer than 24 (`_LANES_JOBS_FLOOR` in lib/bats-lanes). `DEVBIN_TEST_JOBS`, else `DEVBIN_JOBS`, still sets it, and bin/.devbin/help/test.md and lib/pages/test.md say so. In every estate's suite, once the sweep carries this release, `test shell`'s parallel lane runs at least 24 tests at a time wherever GNU parallel is installed. The 0.1.23 note's 0339 entry, under Changed, says so with this issue's reason.
- 0340-2: CI no longer sets `DEVBIN_TEST_JOBS: all` on its three Run tests steps, and no longer passes it through WSLENV (.github/workflows/tests.yml). So CI runs the suite's own default of 24 on its 3- and 4-CPU runners (hv's yes, vc's decision 165).
- 0340-3: CI sets `DEVBIN_TEST_JOBS: all` on its three Run tests steps again, and passes it through WSLENV, as before 0340-2. The floor of 24 stays for hosts. 0.1.23's first candidate, 61dbd245, ran CI at 24: on the three-CPU macOS runner the suite went red in bats' own output forwarder, and on Ubuntu it ran no faster than at one test per CPU. tests.yml says so above the Ubuntu step.
