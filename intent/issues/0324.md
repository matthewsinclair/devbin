The artefact cache's key is the sha256 of the artefact's input paths' git object ids at the commit, plus the toolchain, the platform and the architecture (lib/cmd/cache's header and `cache_key`). The commit itself is not in the key, by design: a commit that changes only what the inputs do not hold keeps the key, and the artefact is pulled.

An app that declares `macos.commit_stamp` carries in its Info.plist the commit it was built at, and `app_ship_blockers` (lib/cmd/macos) refuses a copy whose stamp is not the release's commit: "it was built off another commit". When that app is also a `build:` artefact (`cfg_macos_artefact`), app-sign's `app_build_cached` pulls it at the release commit whenever an entry was put at an earlier commit with the same input ids. Every later release commit then gets a copy stamped with the older commit, and app-sign stops the cut with nothing signed. The failure is loud, never a wrong app, but the cache turns a cut that would build and pass into one that fails, and the refusal names the app, not the cache. A reset and re-cut of one version, the case the cache is meant to speed up, makes a new release commit with the same inputs, so it meets this every time.

An app that versions apart from its project must declare `macos.commit_stamp` (issue `0243`), so every such app meets it the first time it is cached.

Wanted: a commit-stamped app is never pulled at a commit other than the one it was put at. Either the key holds the commit where `macos.commit_stamp` is declared, so each release commit is a miss and builds, or config validation refuses a `build:` artefact at `macos.app`'s path beside `macos.commit_stamp`, naming why. The second says plainly that such an app gains nothing from the cache.
