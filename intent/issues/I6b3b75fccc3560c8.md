## What is wrong

A tool that adopts devbin#0326's dev/opt/brew declares two things in its `install:` block that its own code must also know at run time. devbin keeps both where the tool cannot read them.

1. **A published tree carries no record of its manifest's name.** `install.manifest` names the manifest, eg Gtools' `.gtools-install`. A tool's own readers look the manifest up by that name: its version line in opt and brew, and its doctor's tree and drift rows. An opt tree and a keg ship no `bin/.devbin`, so the tool cannot read `install.manifest` there. It must keep the name as a literal of its own.
2. **A tool's code cannot read its own runtime set.** A script tool's dev line reads `+dirty` from the runtime set, as devbin's own does, so it needs the set that `install.files` declares. The only reader is devbin's `lib/config`. It needs bash 5: `lib/config:1470` has `;;&`, a syntax error under /bin/bash 3.2, which a tool such as Gtools still runs on, eg on Gtools.app's five-second poll. It also costs a parse on every call. So the tool must keep its own copy of the set.

Each copy is a second definition of a declared fact (the Highlander rule).

## The stopgap

Gtools I7bd0048 (Gtools' adoption of devbin#0326) keeps `gtools_runtime_pathspecs` and `GTOOLS_MANIFEST_NAME` as literals in `bin/lib/common.sh`. One ExUnit arm in test/gtools_installed_tree_test.exs holds both equal to the `install:` block: the tracked set under `install.files`, less its excludes, equals the pathspecs' set, and the name equals `install.manifest`. The arm is the stopgap until this issue lands. Ruled by devbin-vc and gtools-vc, 2026-11-24 08:38Z by date -u.

## Fix outline

devbin writes both facts into a plain file that a tool reads with no devbin parser and with any bash:

- in a published tree, beside the manifest: the manifest's name, and the runtime set as one path per line;
- in a dev checkout, the same file, written by `bin/devbin install` and `bin/devbin build`, or a verb that prints it, so a dev reader can find it without sourcing `lib/config`.

Its path is fixed by the contract (T3), so the tool needs no copy of the manifest's name to find it. The file's form and place are devbin's call.

## Resolution

Landed at bea177c0 on main (2026-11-24 13:19Z by date -u, landed by devbin-vc).

- `<root>/.devbin-tool`, a plain `key: value` file: `manifest:` (install.manifest), `set:` (the runtime set as git pathspecs, a directory entry with its excludes, no product) and `input:` (each declared build input). Any shell reads it with `while read`.
- In dev it is tracked and held to the block: build and upgrade write it where it differs, an opt publish refuses a stale one naming build, and doctor fails it. It is in no runtime set, so it alone makes no line +dirty.
- A publish writes it into the opt or brew tree beside the manifest, which does not list it. An asset formula's keg and devbin's own trees carry none.
- A sweep: an estate's first upgrade runs its old runtime, so `fleet upgrade --apply` runs one more pass in each estate whose config declares a tool, and that pass writes the file. devbin-vc's 0.1.31 sweep script adds `.devbin-tool` to its pathspec.
- docs/dev-opt-brew.md T1 and T3 name the file, its form, its writers and the sweep's pass.
- Arms: seven in tests/unit/tool.bats (the lines, the stale refusal and build's write, the opt and brew copies, doctor's row, no +dirty from the file alone, a reader under /bin/bash, upgrade's write) and one in tests/unit/fleet.bats (the one extra pass).
