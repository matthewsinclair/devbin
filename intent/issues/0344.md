## What happens

A cut's legs step starts every leg together at the release commit and reads them all in one wait loop: the candidate's push, the local gates, each reached `release.legs` host and the macOS stage (lib/cmd/release, legs_step; ST0011 AC-2.2). kovacs, devbin's one remote leg, is a VM on rhadamanth, the machine that cuts. So the leg's suite and the local gates' suite run on the same CPUs at once.

In the stacked run of 0.1.23's fixes on 2026-11-12, both at 24 jobs, kovacs ran about 49 tests a minute while rhadamanth's whole suite ran beside it, and about 200 a minute once that had ended. The load (35) also exposed issue 0342's race.

## hv's rulings (vc's decision 166)

- "we can't run rhad and kovacs at the same time, they need to be serialised", for every kit, probe and sweep.
- "yes, serialise the cut's legs too", "Fix it now, please" and "dc, now, in parallel".

## The fix

- The candidate starts first, as now, and runs throughout, since CI runs on GitHub's machines.
- The local gates start next, with the macOS stage beside them, as now: the stage is no suite.
- Each reached `release.legs` host runs after them, one at a time in the config's order, and starts only once the leg before it reads green. A red stops the cut before the next host is sent the release commit, and the stop names every host it never started.
- `ci.wait` bounds each remote leg from its own start, so a long local run spends none of a remote leg's wait.
- The dry run names the order.

The time a serialised cut takes is measured on both hosts, one after the other, each with its load read through the run. It is not derived from a contended run.

## Resolution

Fixed in one landing on main, a1bc1774 (unit 0344-1), in devbin 0.1.23's batch. It was proved in cc's stacked run k342 beside 0342-1, and shipped in v0.1.23, release commit 7ab21982, released 2026-11-12 19:02Z.

- lib/cmd/release's legs step starts the candidate first, then the local gates, with the macOS stage beside them, as before.
- Each host `release.legs` names is held until the leg before it reads green: the local gates for the first host, and the host before it in the config's order for each one after.
- A held host starts in the round where the leg before it first reads green, once that round has stopped nothing. So a cut already red sends no host the release commit. A round that starts a host is read again at once, so a host that is green at its start lets the next one start without waiting a poll.
- `legs_held` is the one test of whether a leg may start, and both the cut's starts and the dry run's row ask it.
- A stop names each host it never started (eg "legs.near was not started, since local did not read green, so nothing was sent to near"), and the RELEASE seal records each one as none, not started.
- `release.ci.wait` bounds each leg but the local gates from that leg's own start, with one deadline per leg in place of the loop's one deadline. So a long local run spends none of a remote leg's wait, and the timeout says "of its own start".
- The dry run's legs row names the order. A cut with no remote leg reads as before.
- docs/configuration.md, docs/releasing.md, lib/pages/release.md, lib/config.reference.yaml and README.md say the order and where ci.wait starts. The 0.1.23 note says it under Changed. ST0011's AC-2.2 and AT-2.7 say the order too (vc's edits at the landing).

Proof:
- releasecut.bats has three new arms under AT-2.7: the hosts run after the local gates, one at a time; a red local leg sends no host anything and names it as not started, in the output and in the seal; and the dry run's row names the order.
- Three arms were reworked:
  - the failed-start arm now holds that the host behind the failed one is never started;
  - the timeout arm reads "of its own start";
  - the AT-2.7 arm is retitled to the order.
- Five of the six were red at the base's code, each on its own finding. The sixth was green there, since it is only retitled.
- At the fix, in k342: the six and the nine legs controls beside them read green under BSD, 15 of 15, and the six under GNU, 6 of 6. kovacs's whole leg passed every one of this unit's arms.
- The whole suite ran on each host alone, one after the other, which is the time a serialised cut takes, measured and not derived from a contended run: kovacs's in 26m50s, every arm ok but harness.bats's title scan on 0342-1's old arm title, then rhadamanth's through release gates in 19m41s, green, kovacs idle.
- The arms prove the order with fake hosts. Its first run with a real host was the cut: both of 0.1.23's cuts held kovacs until the local gates read green. At 61dbd245, local read green at 15:42:09Z and kovacs started at 15:42:10Z. At 7ab21982, the release, local read green at 18:18:39Z after 975 s, kovacs started at 18:18:40Z and read green at 18:41:16Z after 2332 s, both errors files empty.
