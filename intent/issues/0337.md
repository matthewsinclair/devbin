From Intent's ST0093 (hv's word, relayed by intent-vc, 2026-11-11), half B item 1.

Intent's 3.3.0 cut was the first run of its kovacs leg, which had been declared the day before. The cut stopped red four times, once for each fault: no previous tag, a tmpfs /tmp too small, a daemon socket shared under ssh, and no release pair in the leg's tree. That lost 1h34m of the 1h56m from the first attempt to the release. Every one of those faults was a property of the leg, not of the release. A leg run before the cut would have found them with nothing stamped.

What exists:
- A remote leg runs only inside a cut, at the stamped release commit R. `_leg_remote_start` (lib/cmd/release:819) hands it to `release_leg_start` (lib/release.legs:380 on), which sends R and starts `bin/devbin release gates` in a fresh worktree at `~/work/<project>-leg-<sha12>` (lib/release.legs:179-228).
- Each host's verdicts are kept on this machine, one GATES pair per sha, in `release_leg_dir` (lib/release.legs:112), `tmp/release/legs/<host>/`. That record is enough to tell whether a host has ever gone green, and at which commit.
- `release gates` (lib/cmd/release:5427) runs locally only. Nothing starts a leg outside a cut. Pre-flight's reading of release.legs (lib/cmd/release:2583-2616) checks only that the host can be reached.

Ask:
1. `release gates --leg <host>` starts the same remote run at HEAD, a clean commit and not R, through the same `release_leg_start` and `release_leg_read`. It waits under the same deadline, keeps the pair in `release_leg_dir`, and exits 0 only on green. It is one runner, not a second copy of the leg.
2. Pre-flight refuses the cut while a leg in release.legs has no green pair in `release_leg_dir` at any commit after the previous release's tag. The refusal names the host and the command. A leg added since the last release falls under this rule, and so does a leg whose last run was red. A leg that went green at the last release, or at a rehearsal since, passes.
3. A leg also counts as changed, and is held to the same rule, when release.legs, release.gates or the gate commands those name differ between the previous tag's `bin/.devbin/config.yaml` and HEAD's.

Limit, stated rather than hidden: drift on the host itself (a new /tmp mount, a changed shell startup) is invisible to the core. The rule catches new and reconfigured legs, which is what all four of the 3.3.0 failures were.

Proof: one rehearsal of a leg on kovacs with a project's real gates, which is the leg's own run. No separate test of the test.

Size M. It reuses the leg runner end to end. The new parts are the `--leg` option, the pre-flight read, and the config diff at the previous tag. It shares the remote half with 0333 and 0334, so it lands in their batch after them.

- release gates --leg <host> runs the remote leg on a host release.legs names at HEAD, a clean commit, through the leg's own runner (release_leg_start and release_leg_read): HEAD and the newest release's tag sent there, the gates started, waited for under ci.wait with each change said with the clock, and the pair kept under tmp/release/legs/<host>/. It exits 0 only on green; a green kept for HEAD runs nothing again unless --rerun; a host release.legs does not name is refused.
- A cut's pre-flight, and a dry run's, refuses a reached remote leg that has not gone green since the previous release with the leg config HEAD declares: its kept pairs are read newest first, and the first at the previous release's commit or one after it, whose release.legs, release.gates and the commands blocks those gates name match HEAD's, must be green. A leg new since the tag, one reconfigured since its green, and one whose last such run was red are refused, naming the host and the rehearsal.
- The limit stays as the issue states it: a change on the host itself is not read, and the cut meets it.
- The macOS stage is not a release.legs host and has no rehearsal: its app-sign refuses any commit but the release's, so its first run is at the cut, which 0336 shortens.
- The release page and docs/configuration.md say so; releasecut.bats's remote-leg fixtures rehearse their leg before a cut.

Two new arms in releasecut.bats, red at the base on their own finding (release refused --leg as an unknown argument; a dry run of a never-run leg passed pre-flight) and green at the fix. devbin's own cut passes the rule with no rehearsal: its kovacs leg is green at v0.1.22's commit and its leg config unchanged since.
