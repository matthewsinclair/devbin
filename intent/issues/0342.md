k340's run (devbin 0.1.23's re-cut fixes 0334-2, 0341-1, 0340-1 and 0340-2, stacked at 0eae6ab6 on dc0e45b8) read one red, in its kovacs leg. That leg was `release gates --leg kovacs` at 24 jobs on kovacs's 4 CPUs, 0340-1's new default, under bash 5.3.9 and a load average of about 35. builtins.bats's setup_file failed there, so its 45 arms never ran:

    not ok 58 setup_file failed
    # (from function `devbin_fixture_cache_build' in file tests/unit/../lib/test_helper.bash, line 230,
    #  from function `setup_file' in test file tests/unit/../lib/test_helper.bash, line 100)
    # .../lib/helpers: line 2743: wait: pid 2701052 is not a child of this shell
    # devbin: failed to write the manifest

The fixture's one real install walks what it writes through find_walk (lib/helpers). find_walk reads find's records from a process substitution, and find's status by `wait "$!"`:

    mapfile -d '' -t _fw_marks < <(find ...)
    wait "$!" || _fw_rc=$?

`$!` names the process substitution, and whether bash still holds that child's status when `wait` asks for it is bash's own bookkeeping. Here it did not. `wait` answered 127, find_walk read the walk as failed, and the install failed with it. A status lost this way reads as a failure, never as a success.

The same bash ran 0.1.22's leg and the earlier kovacs legs green at 2 jobs. What changed is the load. rhadamanth, on bash 5.3.20, ran the same tip green in the same hour at 24 jobs on 16 CPUs. The red is the race's evidence, cited and never forced: its seal pair is k340's kov/tmp/release/legs/kovacs/20261112-1118.GATES.out and .errors, in cc's scratch.

The same idiom reads a status in nine places, each a walk, a listing or a sort that can read as failed when it was not:

- lib/helpers: cargo_build_dirs (2322), find_walk (2743), and find_list (2868, 2872)
- lib/cmd/clean: the crate scan (362) and its two sorts (378, 383)
- lib/cmd/worktrees: _wt_list_read (235)
- lib/release.steps: release_dirt (550)

lib/release.steps:2046's `wait "$!"` waits on an `&` job, whose status bash keeps, so it is outside the class.

Issue 0139's find-status scan (tests/unit/contract.bats) takes `# find-status: read by `wait "$!"` below, on this process substitution` as the mark that answers for a find in a process substitution. So the scan holds the idiom in place rather than refusing it.

A fix reads every such status in a form bash cannot lose, and the scan refuses `wait "$!"`.

## Resolution

Fixed in one unit on main, 0342-1 at acf645e69612f5f3bbb3c4e71135506ace9304bd (2026-11-12 15:26Z), released in devbin 0.1.23, proved in k342's two runs, stacked with 0344-1 at the tested tip 7fa6a4ad, on 2026-11-12 between 13:10Z and 13:56Z and between 15:02Z and 15:24Z: contract.bats's new arm read red at the base on its own finding and green at the tip, and builtins.bats's setup_file, this issue's red, read ok on kovacs at 24 jobs on its 4 CPUs and in the whole suite here.

- nul_read (lib/helpers) reads a command's NUL-terminated records into a named array and returns the command's own exit status, which the process substitution writes itself as the stream's last record, tagged for the call. Nothing waits, so the status does not depend on what bash keeps, and it holds with job control on. A status that never came is nul_read's own 2, said.
- The nine places the issue names read through it: find_walk, find_list, cargo_build_dirs, clean's crate scan and its two sorts, worktrees' _wt_list_read and release_dirt. release_group_start names its job's pid as the job starts and waits on that name.
- Issue 0139's find-status scan (contract.bats) takes `if ! nul_read <array> find ...` as a read status, and a new arm there refuses any wait on the last background job's pid under lib/, bin/ and tests/lib/. At the base it named all 10 such waits, lib/release.steps:2046's `&` job among them, a list the run read from the base by the arm's own pattern. helpers.bats holds nul_read's arms.

Two forms were set aside: lastpipe with PIPESTATUS, which reads every list empty under release_group_start's job control, and a temporary file per read. The fix rests on no bash version.

The first run's kovacs leg read 3135 of 3136 ok in 26m50s, builtins.bats's setup_file among the ok. Its one not ok was harness.bats's title scan, which refuses a dollar sign in a test name, on the new arm's first title. The arm was retitled, one line and no code, and the second run read harness.bats and contract.bats whole, then the whole suite here alone through release gates, green in 19m41s, 3136 tests each once.
