Filed for devbin 0.1.27's batch (vc's decision 205, which carries vc's todo 214), from vc's archived todo 203: devbin-cc's finding on 0327, 2026-11-10.

## What happens

Issue 0327 refuses a `release.preflight` command whose first word is `release` as config: a cut runs each pre-flight command inside its own pre-flight, so one that runs `release` would start a cut there, which would run it again, without end. `release.gates` has the same shape and no such refusal. A cut runs each gate through the project's launcher in its legs step, in place for the local leg and under `release gates` on each host `release.legs` names, and `bin/devbin release gates` runs them by hand. A gate whose first word is `release` runs a release verb from inside the gates: `release gates` would run the gates again from inside themselves, and the cut's own verb would start a cut inside the cut.

## The code

- lib/config:1402-1416, the release value check's `preflight.*` case, refuses a first word of `release` ("runs release, which would start a cut inside the cut's own pre-flight, again without end -- name the check itself").
- The same check, whose cases run from lib/config:1349 to :1492, has no case for `gates.*`, so a gate entry is checked only for its key's shape (:1825).
- docs/configuration.md:326 says it for pre-flight alone: "A `preflight` command never runs `release`".

## Not yet known

- What each release verb does when a gate runs it: whether the inner run is refused somewhere first, or loops. No such run has been made.
- Whether the other lists a cut runs through the launcher, `derived:` and `after:`, take a `release` entry too.

## Options, none chosen

- Refuse a `release.gates` entry whose first word is `release` at validation, as pre-flight's is, in the same check and with the same wording, so `release status` and doctor say it before any cut.
- Refuse it through one helper for every list a cut runs through the launcher, so a list added later cannot miss it.
