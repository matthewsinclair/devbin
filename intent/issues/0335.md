From Intent's ST0093 (hv's word, relayed by intent-vc, 2026-11-11), half B item 3. This settles the collision first, as hv's brief asks.

THE COLLISION. A project handler shadows a built-in of the same name totally (lib/resolve:774-776, AC-04.4). Intent ships `bin/.devbin/cmd/cache`, a cargo-residue report that ignores every argument except `--clean` and exits 0 when it finds no residue. The core calls its own cache through the project's launcher:
- lib/cmd/macos:1400: `"$launcher" cache get "$art" --commit ...`. On exit 0 it prints "pulled, so macos.build is not run" and skips the build.
- lib/cmd/macos:1413: `"$launcher" cache put "$art"`.
- lib/cmd/release:1440: `"$PROJECT_ROOT/bin/devbin" cache key "$art" --commit "$LEG_SHA"`. Its stdout is taken as the key.

In a project that declares a build artefact for macos.app and also has its own cmd/cache, `cache get` would answer 0 with nothing pulled, and the stage would sign whatever is at the app's path. Today nothing reaches that path, because Intent declares neither commands.macos nor a build: block. Adopting the cache (item 4 of this set, and Intent's own macOS-leg adoption) would reach it.

THE WARM TREES. A remote leg's worktree is new for each sha and is cleared once its log comes back (lib/release.legs:179-228, and the clear at :254). Intent's `gate rust` makes its own private worktree under TMPDIR, with that worktree's own target (Intent's `bin/.devbin/cut/gate:100-119`). Both are cold on every cut, on both hosts.

Ask:
1. The core calls its own cache verb by its built-in path, never through the project's launcher, at all three call sites. It goes through one helper, so a fourth site cannot regress.
2. `doctor` and config validation name a project handler that shadows a core verb which the core itself calls, starting with cache, as a finding.
3. Each leg host keeps a persistent per-project work directory beside the bare repo, `~/work/<project>-leg.cache`, which a leg clear never removes. Locally the same lives under the project's XDG cache root. The core exports its path to the gates as one variable, DEVBIN_GATE_CACHE, next to 0334's TMPDIR. A project's gate may point its build directory there, eg CARGO_TARGET_DIR for a private worktree. The core decides nothing about what goes in it.

Intent's side, its own package and not this issue: rename its cmd/cache (it is a check, not a cache), and point `gate rust`'s target at DEVBIN_GATE_CACHE.

Proof: one cut of a project that declares a macOS artefact (the leg's run is the proof), and one Intent leg run showing `gate rust` warm.

Size: S for 1 and 2, S for 3. It touches the same far-side code as 0334, so it lands in that batch.
