## What happened

Found by another estate's session on 2026-11-13 at 20:31Z, relayed by devbin-vc. On a shared checkout, `bin/devbin test mix --help` and `bin/devbin check compile --help` each ran the work instead of printing help. `test mix` compiled the test environment's deps before a SIGPIPE killed it, and `check compile` ran to the end, building into `_build/dev`. Both ran unbooked, because the user expected help.

## Where the flag goes

Three layers each pass it on:

- The dispatcher, bin/devbin:668-690, answers `-h` and `--help` in any position as `help <cmd>` only for a command not offered here. For an offered command it says "an offered command reads its own flag", and leaves the flag on the command line.
- The built-in gate handlers, lib/cmd/test and lib/cmd/check, hand everything to `run_builtin_gate` (lib/gatecmd:66). That answers `-h` and `--help` only in the option's position: `test --help` prints the usage line, but in `test mix --help` the option is `mix`.
- What follows the option goes through `gate_split_args` (lib/runlog:1969). It keeps devbin's own wrapper flags (`--purge`, `--purge-only` and `--allow-empty`) and passes every other word to the tool's argv. So `test mix --help` runs as the option's own line with `--help` appended, and mix compiles before it reads the flag.

The same holds for every gate command (`check`, `test`, `clean`, `db`, `docs` and `fmt`) and every option behind them. Whether the work runs then depends on the tool. Some tools print help at once, while mix and others like it do work first, and a `db` option's tool can do worse.

## Why it matters

A reader reaches for `--help` to learn what a command does before running it. That must never run the command. On a shared checkout the run is also unbooked, and it can write the build tree that other sessions and gates are reading. The page a reader was after, `help <cmd>`, exists and is never shown.

## Expectation

`--help` and `-h` never run work, in any position, for any command and any option.

## Not yet known

- Whether any option's tool line takes `--help` or `-h` as a word it needs, eg a gate whose run passes `-h` to its tool for another meaning, which answering it in devbin would break.
- Whether a project's own command, from bin/.devbin/cmd, should be held to the same rule, or keep reading its own flag.

## Options, none chosen

- Answer `-h` and `--help` in any position as `help <cmd> [<option>]` for every command in the dispatcher, before any handler runs. This is what it already does for a command not offered here.
- Have the built-in gate handlers answer `-h` and `--help` in any position before any work, and refuse any word that is neither devbin's own flag nor one the option declares, rather than passing it to the tool.
