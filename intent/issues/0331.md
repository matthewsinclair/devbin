A tool with a second binary that prints its own name fails doctor's dev and brew rows, so a tool like that cannot declare its link set

The dev/opt/brew contract (docs/dev-opt-brew.md, T4) has every binary of a tool print the tool's version line, and in opt and brew the line its manifest records. A 0.1.21 keg's manifest records one line naming the tool (lib/cmd/formula:501). Doctor's dev row runs each install.links path's --version against the line a build carries (lib/cmd/doctor:1134, failing at :1160), and its brew row fails each link whose copy prints another line (lib/cmd/doctor:1379).

A consumer whose second binary names itself, its daemon printing "<daemon> <version> (dev, <sha>)" while the tool prints "<tool> <version> (dev, <sha>)", fails both rows as soon as it declares both binaries under install.links: the dev row whenever the pair is built, and the brew row on every machine that installs its next release. A fresh clone with nothing built reads green, while a working checkout reads red. devbin-cc ran this on 2026-11-11 in a scratch clone of a consumer at its v0.1.21 sweep: doctor exit 1, "FAIL <tool> dev: native/rust/target/release/<daemon> prints <daemon> 3.2.8 (dev, ...), which names another tool or tree than the line a build here carries".

Until this is settled, such a consumer keeps the second binary outside the link set, as two template lines after @@INSTALL@@ (chmod 0755 and bin.install_symlink), with no install: block. That renders the same keg and reads green, but the contract no longer names the second binary.

Expected: one of two shapes, chosen by hv. Either the contract lets each link print the tool's line with its own name in place of the tool's (doctor reading each link's line under its link name), or it keeps one line per tool and says that every binary prints it, naming the consumer-side change that implies.

## Ruling

hv, 2026-11-11: the first shape. Each binary of a tool prints its own name in the first field of its line, with the tool's version, tree and sha from the core's one reader (the manifest's line in opt and brew, DEVBIN_VERSION_LINE in dev), and doctor's dev row and brew-tree row read each link's line under that link's name. Every binary of every tool reports its version the same way, so no binary keeps a formatter of its own. It ships in devbin 0.1.22, with 0329 and 0330.

## Resolution

Fixed in one landing on main, e72d6203132a3815b16ea060566b612b1bddf730 (2026-11-11 07:11Z), unit 0331-1 from the tested tip 7d43e117, the first of devbin 0.1.22's seven units, which vc landed as one stack; unpushed until devbin's next cut, proved on its own arms under hv's rule of 2026-11-05 (red at the base's code, green at the fix) in one slot on devbin-vc's desk. It takes hv's first shape.

- Every binary of a tool prints the tool's one version line under its own name, `<name> <version> (<tree>, <sha12>[+dirty])`: its own name first, then the tool's version, tree and sha. One manifest line per tool and one DEVBIN_VERSION_LINE per build, as before, and devbin's own line is unchanged.
- lib/helpers: tool_link_line <line> <name>, the line as the binary <name> prints it, read up to its closing parenthesis through tool_line_parse and rebuilt by tool_line, the one formatter.
- Doctor's dev row reads each link's copy against the dev line under that link's name, and holds the parsed name to the link's, not the formula's; its tree row reads each copy against the recorded line under the copy's own name. The publish reads each linked product's line under its own name, a bare use reports each link's opt or brew line under its name, and the cut's note back to brew names the first link. A word after the closing parenthesis still reads clean.
- docs/dev-opt-brew.md's T3 and T4 say so. T4's Rust reader takes the binary's own name from Cargo, CARGO_BIN_NAME, beside the tool's, so the block stays word for word for every binary; it compiles, and prints the line under the binary's name plain, stamped and from an opt tree. lib/pages/build.md and use.md follow.

Four new arms: three in tool.bats (tool_link_line's own; doctor's dev row, passing a second binary that prints its own name with a word after the parenthesis and failing one that prints the tool's; a second binary's publish, use's report and opt-tree row under its own name) and one in releasecut.bats (the note back to brew names the first link). The stamped project's program now prints its line under its own name, as the reader does, and five arms that read that line moved with it. Nine arms were red at the base, each on its own finding: the base reads a link's line whole, so its dev row fails the program's own-name line as naming another tool, its publish refuses it (the use and opt-tree arms publish first), its note back to brew names the formula's line, and tool_link_line is not there. Thirteen green legs, 34 arms, were green at the fix: tool.bats's arms over the tool's build, use, doctor and publish, the five arms that end on the note back to brew, and documentation.bats's two T4 arms. bin/devbin check lint at the fix was clean.
