## What is wrong

`bin/devbin infra mail dmarc report` can print `spf=pass` for a forged message that the receiver rejected.

The row printer, `row` in `lib/cmd/infra.d/mail.d/dmarc`, prints SPF as `.spf_auth | map(.result) | join(",")` at lines 401 and 403. It prints each raw SPF check's result only. It does not print the domain that the check was for. It does not print the policy-evaluated SPF result, which says if SPF aligned with the header From. The parser keeps both facts: `spf_evaluated` and `header_from` (lines 282-283, 325-326), and each `spf_auth` entry carries its domain. The printer drops them.

Evidence: Google's aggregate report 11650357786198732372, window 17 Nov, for a Prodinfra report domain. The row reads `dkim=absent spf=pass`. The record is a forgery that the receiver rejected:

- `spf_auth` holds one check, for the domain `bright.sender-point.wolf.poland.englinguisha.org`, result `pass`. That is the forger's own domain, not the header From.
- `spf_evaluated` is `fail`: the pass did not align.
- `disposition` is `reject`.
- `header_from` is a subdomain of the policy domain, so the policy's `sp=` applied. The row shows only the policy domain, so the reader cannot see which From the message used.

A reader of the row sees a pass for a message that failed DMARC and was rejected. That is the error that issue 0147 (closed) fixed for DKIM: there, the signing domain and the selector now print beside each DKIM result (`sig`, lines 391-394).

A second, smaller defect is on the same lines: `join(",")` of an empty list is `""`, not null, so `// "absent"` never applies. A record with no SPF check prints `spf=` with nothing after it.

## Fix outline

Print SPF as issue 0147 prints DKIM:

- Print each SPF check's result with its domain, eg `spf=pass d=<domain>`, at least where that domain is not the header From.
- Print the policy-evaluated SPF result, which is the DMARC verdict, eg `spf_aligned=fail`, or print that result in place of the raw one.
- Print the header From when it is not the policy domain.
- Print `absent` for a record with no SPF check.

The plan decides the words and the order of the fields, and whether the DKIM part also prints its policy-evaluated result, for symmetry. The plan reads the report's other readers first (the classes in `klass` and the summary lines), so the row and the classes agree.

## Done when

- A fixture record with an unaligned SPF pass, `spf_evaluated` fail and `disposition` reject prints a row that shows the unaligned domain and the fail.
- A record whose header From is a subdomain prints that From.
- A record with no SPF check prints `absent`.
