ci-state's verdict over the candidate (lib/cmd/ci-state, cistate_verdict_on, cistate_rows and cistate_rank) lists every run of the workflow at the release commit on the candidate's ref, through release_runs_list, and takes the worst of them: failed over pending over green. Nothing bounds that list to the runs this attempt's push started.

A cut that stops after its candidate push deletes the candidate branch, and GitHub cancels the run it started. A resume pushes the candidate again, and that starts a fresh run at the same sha on the same ref. The verdict then reads both: the old run's `cancelled` ranks as failed, the candidate leg reads red, and the resume stops and deletes the candidate again, cancelling the fresh run too. So every resume after a stopped cut inherits its predecessor's cancelled run, and none can go green.

Seen in a consumer's patch cut, 2026-11-10: the first attempt stopped at its macOS stage, which could not read the notary keychain from the shell that ran it, and its candidate run was cancelled. hv's resume 9 minutes later pushed the candidate again (a fresh run in progress) and read the old run as cancelled 39 seconds later, then stopped.

Expected: the candidate leg decides on the runs of this attempt alone, those created at or after its own candidate push, or the run that push started, and names any older run at the sha as passed over rather than ranking it.

Workaround until then: delete each cancelled run at the sha (`gh run delete <id>`, a GitHub write) before resuming.
