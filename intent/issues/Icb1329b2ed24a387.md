## What is wrong

devbin's general doctor cannot pass for a project whose tools are one dispatcher with many names. Such a project builds one binary and links it under many tool names. Each name runs the same dispatcher, which picks the tool by its name. docs/dev-opt-brew.md (T1 to T10) names one tool for each binary, and doctor reads each declared name as its own binary.

Found at another estate's devbin 0.1.34 sweep check (2026-11-26, that estate's dc, relayed by devbin-vc). There, `bin/devbin doctor` exits 1, with 35 of its 53 rows failed. Every row about devbin itself is ok at 0.1.34.

- 17 rows: `bin/<tool> --version` prints one line for the family, in the form `<family>:<v>/<tool>:<v>`. T4's line is `<tool> <version> (dev, <sha12>[+dirty])`, so doctor's dev rows fail on each (lib/cmd/doctor, the "no line in T4's shape" failures in the dev-copy check).
- 18 rows: `~/.local/bin/<tool>` resolves to the family's dispatcher, and doctor reads it as "no tree's bin/<tool>". That run was in a detached worktree, so these 18 rows must be read again from a main checkout before they count.

## The question

1. Does the dev/opt/brew contract name a dispatcher family: one binary, one tree and one manifest, linked under many names?
2. If it does, how does doctor read one: the family's line once, or each name's line from the one dispatcher, and which link resolves to which tree?
3. If it does not, what does such a project do instead, and does doctor say so in one row, not in a failure for each name?
