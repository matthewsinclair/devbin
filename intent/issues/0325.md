The artefact cache's key is the sha256 of the artefact's input paths' git object ids at the commit, plus the toolchain, the platform and the architecture (lib/cmd/cache's header and `cache_key`). The inputs are the ones the `build:` block declares (`build.inputs`, or an artefact's own `inputs`), and nothing else enters the key, so a version file is in it only when the block names it.

An app's Info.plist carries the version it was built at, and `app_ship_blockers` (lib/cmd/macos) refuses a copy whose CFBundleShortVersionString is not the release's: the project's version from `project.version_from`, or `macos.version_from`'s for an app that versions apart, "it was built from another tree". When that app is also a `build:` artefact (`cfg_macos_artefact`) and its inputs leave out that version file, a release whose version moved while the inputs did not keeps the key, and app-sign's `app_build_cached` pulls the app put at the earlier version. app-sign then stops the cut with nothing signed. For an app on the project's version, every release that leaves the app's inputs alone meets it, since each release moves the version file. The failure is loud, never a wrong app, but the cache turns a cut that would build and pass into one that fails, and the refusal names the app, not the cache.

The one arm on the cached path (tests/unit/macos.bats, "app-sign builds the app and puts it into the artefact cache ...") runs app-sign twice at one version, so it does not reach this.

Wanted: an app artefact is never pulled at a version other than the one it was put at. Either config validation refuses a `build:` artefact at `macos.app`'s path whose inputs do not hold the version file, naming it, or the key takes that file in for the app's artefact, so a new version is a miss and builds while a re-cut of the same version still pulls.
