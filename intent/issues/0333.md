Reported by Intent's dc on 2026-11-11, from Intent's 3.3.0 cut.

A release leg sends only the release commit to the leg host: `lib/release.legs:402` runs `git send-pack "$host:work/$project-leg.git" "$sha:refs/devbin/legs/$sha"`. The previous release tag never reaches the host's bare repo. On Intent's 3.3.0 cut, kovacs's `~/work/intent-leg.git` had no `v3.2.8`, so anything in the leg that reads the previous tag (eg a DEVBIN_RELEASE_* comparison, or notes since the last tag) had nothing to read, and the leg went red. v3.2.8 was sent into the leg repo by hand before the run that passed.

Ask: the leg's send-pack carries the previous release tag, the baseline the release core resolves, alongside the release commit, so a fresh leg repo needs no hand step. Intent's cut passed with the hand send; nothing to build for Intent.
