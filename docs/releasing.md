# Releasing devbin

devbin releases with its own release core, `bin/devbin release`, declared in the `release:` block of `bin/.devbin/config.yaml` like any other project's. There is no devbin-only procedure: what follows is what a person decides, the commands that do the rest, and the tripwires that are specific to devbin being a consumer of itself. devbin publishes each release as a snapshot of its product (ST0010, issue 0240): a cut releases into this development repository and makes the release's snapshot public itself, through CI on that very commit.

## What a person does

1. **Write `RELEASES/<version>.md`.** It is the only hand-written record of a release, and `CHANGELOG.md` and `RELEASES.md` are generated from it (`notes.kind: releases`, see `docs/configuration.md`). Its changelog entry comes from the headings that begin with a Keep a Changelog section, `## Added` to `## Security`, and a qualifier after them is kept (`## Fixed -- reaches every project`); a note with none is refused unless its header says `changelog: none`. Include a `## Known limitations` section naming the open issues: a release that ships a clean list nobody can check is worse than one that says what it knows. Its header is `key: value` lines ended by a blank line -- `headline:` is its row in `RELEASES.md`, and `status:` is required -- and everything below the blank line is the body the tag and the GitHub release carry. Leave it `status: unreleased` with no `date:` line at all (an unreleased note carrying one, even an empty one, is refused); the cut sets `status: released` and writes today's local date.
2. **Decide the version.** The bump is the one judgement in a release, so no tool infers it from commits. Name it on the command line, or with `--patch`, `--minor` or `--major`, which bump the newest `vX.Y.Z` tag rather than `VERSION`. Once the tag exists a relative target names the NEXT version, so a cut that stopped after its tag is resumed by naming the version, as the cut's summary prints.
3. **Bump `devbin_version` in `bin/.devbin/config.yaml` if the new version no longer satisfies it**, and commit that first. No step of the release owns that file, so the cut refuses to start while it is dirty (see the tripwire below).
4. **Cut, publishing through CI** (issue 0240). Every local gate runs on this Mac, and releases have gone red on CI's Linux job after the tag more than once (issue 0223 names them), so nothing becomes public before CI is green on the very commit that does. The cut pushes the workroom to `local` alone. Its legs step makes the snapshot of the release commit and pushes it to `candidate/v<version>` in the public repository, where the push runs the whole matrix, macOS and WSL included, while the local gates run beside it, and only once `bin/devbin ci-state`, its `ci.query`, reads that run green, and the gates are green, does the cut tag, move the public `main` to the snapshot and push the tag at it. The verdict is the run's Test Summary job's, so a red WSL job, which blocks nothing, does not stop the cut, and a summary absent, skipped, cancelled or still going is not green. A run that failed stops it with nothing tagged and nothing public, the candidate deleted, and the fix is the next version; a run still going at `ci.wait` stops it the same way, and running the same command again reads CI again.
5. **Once the tap has the release, put this machine back on brew.** The switch rests at brew (`docs/dev-opt-brew.md`, T5), so a release ends on the install it just made: `brew upgrade devbin`, then `devbin use brew`, then `devbin --version`, whose line must read `devbin <version> (brew, <sha12>)` at the released version, `<sha12>` being the release commit's. The cut's report ends with this step as a note. Nothing runs it for you: only `use` points the link, and a change to the machine is the person's to make. Until it is done, `doctor` notes a switch left on dev or opt once brew has caught up.

## The command

```
bin/devbin release v<version> --dry-run
bin/devbin release v<version>
```

The dry run makes no stamp, commit, tag, push or release object, and runs no gate: it does the same reads and prints every step with what it would do, naming anything it could not predict. It never asks, and runs no `derived:` or `after:` command. Where its commit step would make the release commit, the confirm, legs and tag rows name the commit the cut would tag as the release commit the commit step makes, never `HEAD`'s sha, and the confirm step plans that commit's push to every remote, one `HEAD` was already pushed to included. Where the release commit exists already, its gates row reads the record the cut reads: `already` where a sealed green stands for that commit on this platform. Its header names the cut as the command that releases for real, and when no step failed its last line is its verdict: `release: dry run of v<version> -- no step failed; the cut stops to ask at the confirm step`. A dry run that fails stops at its FAILED row instead, exit 1, as the cut does, and its last line says where it stopped. The real run is itself a sealed gate, logged under `tmp/release/`, and it:

1. resolves the version and the tag, and pre-flights: the branch, the tree, the version, the note, `local` and that it names no public repository, the public repository's refs and `tests/shipped.paths`, `gh` signed in to the repository's host, and kovacs, the one host `release.legs` names, reached by ssh (one that does not answer is named absent, not run and not waited for), naming every refusal in one run;
2. asks once, before anything runs, naming the tag, the release commit and everything other machines will see (`--yes` answers it; with neither a terminal nor `--yes` the cut stops there, before anything is stamped, exit 1, saying nobody was there to ask), and everything after this runs under that one yes;
3. stamps `VERSION`, dates the note, regenerates the views, and commits them as the release commit;
4. runs the gates on that commit -- `check all`, `test all` and `doctor` -- under one seal of their own, `tmp/release/<stamp>.GATES.{out,errors}`, unless a green one already stands for that commit on this platform, as it does when a stopped cut is run again; runs the same gates on kovacs at that commit, its seal copied back under `tmp/release/legs/kovacs/`; and beside them makes the snapshot of that commit over `tests/shipped.paths` on the public `main` and pushes it to `candidate/v<version>`, then waits up to `ci.wait` for CI green on it and for the gates on kovacs;
5. reads `local` again, now the release commit exists, stopping if it changed since the question, then makes the annotated tag, whose message is the note's body, and pushes the commit and the tag to `local`, the one remote `release.remotes` names; reads the public repository again, then fast-forwards the public `main` to the snapshot and pushes `v<version>` at it, lightweight, each read back, and deletes the candidate branch;
6. waits for `.github/workflows/release.yml`, in the public repository, to make the GitHub release from that tag (`object: ci`), failing, naming it, if none appears within `object_wait`, then runs its `after:` command.

Nothing is forced, and each step reads its postcondition first, so running it again continues. Its push to the public repository goes over the maintainer's own git config, a `url.<base>.pushInsteadOf` naming the https url, since the config declares the url brew reads. The first publication made a snapshot with no parent, the public `main` not being there yet, and every one after it is made on the last.

Those are the core's steps, resolve, pre-flight, confirm, stamp, commit, legs, tag, push, object and after, and devbin declares one `after:` command, `bin/devbin formula publish` (the next section); the candidate's run, of the same commit, was the whole matrix, and was green. **The tag starts no run of its own** (ST0011 WP-04): the candidate's run, on the commit the tag names, is the release's whole matrix. **Once the cut is done, read the candidate's run, macOS and WSL included, and file what it finds**: `gh run list --limit 5` shows it, and `bin/devbin ci-state <sha>` with `DEVBIN_RELEASE_TAG=candidate/v<version>` reads its Test Summary as the core would. Each step reads its own postcondition first, so running the same command again after a failure continues from where it stopped. `bin/devbin release status v<version>` prints the same table without changing anything, and `bin/devbin release check` prints the `release:` declaration, every key marked declared or default, whether the views are current, and whether a push of the next cut's candidate branch starts the test workflow (`ci-state --fires`), which it asks where the candidate is read by the built-in query.

A defect found after the push is fixed forward: fix it, write the next patch's note, and cut again. The core never moves or deletes a tag, and neither should a person.

## The Homebrew formula

devbin's formula is a template in this tree, `packaging/homebrew/devbin.rb`, outside the published set, holding one placeholder for the release tag and one for its commit, and devbin renders it with its own built-in `formula`, in source mode (`formula: mode: source` in `bin/.devbin/config.yaml`, issue 0227). `bin/devbin formula publish` renders the newest release into a fresh clone of the tap, `matthewsinclair/homebrew-devbin`, commits it and pushes it, and running it again publishes nothing; `bin/devbin formula render <tag> <out>` writes the formula for one tag, for a look first. Both read the commit from git, never from a person: brew checks out the tag at install and stops when its commit is not the formula's revision, so a typed commit fails every install, and the offline `brew audit` accepts any 40 hex digits, so it would not catch one. brew fetches the public repository, over https, whose tag names the release's snapshot, so the commit is that tag's, read there with `git ls-remote` (issue 0240), and a release not public yet is refused. `bin/devbin help formula` has the rest.

The tap is pushed only after the tag is, since a formula naming a commit brew cannot fetch fails every install. devbin declares it as an `after:` command, which the cut runs once the public tag is pushed, so the order holds by construction:

```yaml
release:
  after:
    - bin/devbin formula publish
```

**The yes for the tap is the yes the cut's confirm step was given, at its prompt or by `--yes`.** The cut asks before anything runs, and `formula publish`, as an `after:` step, takes that yes, whose question named the `after:` commands as running under it, and says so. A confirm step that had nothing left to ask about gives no yes, so an `after:` step re-run on a finished release asks; run by hand, `bin/devbin formula publish` asks too.

**A formula publish that fails does not undo the release, and does not pass quietly**: the after step is FAILED, the release stands, and the run exits 1 naming the command, so run `bin/devbin formula publish` by hand once the cause is fixed. publish takes the newest release by the rule `--patch` reads, so it publishes the release just cut, and it refuses a template with changes no commit holds.

## What CI covers, and when

**A push to `main` runs Ubuntu and ShellCheck. A push of a release's candidate, `candidate/v<version>`, runs those plus macOS, which is the only runner carrying the bash 3.2 refusal proof, and plus WSL on a Windows runner (ST0008): it is the commit a cut makes public once its run is green (issue 0240). A tag starts no run (ST0011 WP-04): it is pushed only once the candidate's run on its commit is green.** A macOS minute costs ten times a Linux one, so since issue 0108 that leg runs on a candidate and on demand, and never on a push to `main`. None of what follows is visible from a green tick alone.

- **A cut runs the whole matrix once, on the candidate, and that run is the verdict it waits for.** Pushing the candidate starts the whole matrix. Moving `main` starts the run a push to `main` gets, Ubuntu and ShellCheck, where GitHub starts one at all: the first publish, which created the public `main`, started none. The tag pushed after it starts none. No leg runs `check critic`: CI runs on the public snapshot, which carries no `intent/`, so the commit gate is where the critic runs (issue 0293). After a cut, read the run whose ref is the candidate -- `gh run list --limit 5` shows them.
- **An intermediate pushed commit can have no verdict at all**, because a newer push to `main` now cancels the run the older one started. "CI is green on the pushed commit" therefore reads on the LAST pushed commit.
- **A push that moves only a board starts no run either**, because the workflow ignores pushes confined to `intent/whiteboard/**` AND `intent/.canon/**` (issue 0110). BOTH entries are load-bearing, and naming only the first is how the filter gets deleted by someone tidying: GitHub skips a push only when EVERY changed path matches an entry, and `intent wb` writes a canon event beside every board view it renders, so a board write touches both trees. Measured over fourteen days of pushes: the whiteboard line alone would have suppressed 0 of 32; with the canon line beside it, 6 of 32. Taken with the line above, a pushed sha with no run of its own is ORDINARY here and is not a signal: the verdict to read is the last run there was.
- **Nothing the macOS runner supplies is exercised between releases**: its image and Homebrew are met only at a candidate. When that side has been quiet, ask for it before cutting rather than meeting it during one -- `gh workflow run tests.yml --ref main` runs the full set on demand, including macOS.
- **The WSL leg blocks nothing.** It runs on a candidate and on demand, as macOS does, and runs the suite and the smoke list (`.github/wsl-smoke.sh`, on its fixture projects) inside WSL, from a clone in WSL's own filesystem. Test Summary does not wait for it, so a red WSL run does not make the candidate's verdict red: read its job on its own. Its name says which WSL version ran, and the job fails if the kernel disagrees. It installs Intent's Linux package from Intent's public release, at a pinned tag and sha256, so `check all` on the fixture that carries `intent/` runs the critic gate.
- **`release.yml` is untouched by any of this.** It is the one workflow a tag starts: it runs on the tag, on Ubuntu, and makes the release object.

## Tripwires

**`VERSION` and the declared constraint live in different files, and only one of them looks like the version.** `bin/.devbin/config.yaml` carries a `devbin_version:` caret constraint -- devbin declaring, as any consumer does, which runtime satisfies it. (Deliberately not quoted here: a document naming the current version is the staleness this section is about.) Stamp `VERSION` past that caret without touching the constraint and devbin fails its own `doctor`. That is why `doctor` is one of devbin's release gates: it runs on the release commit, after the stamp, so a forgotten constraint stops the release before anything is tagged. `documentation.bats` holds the same check.

**The constraint must stay a literal.** It is the one place in the tree where a hardcoded version is correct, and deriving it from `VERSION` would be a defect rather than a tidy-up: a constraint that always equals the current version can never fail, so `doctor`'s check would pass vacuously forever. `documentation.bats` asserts that no authored file but `bin/.devbin/config.yaml` names the current version, and that the config carries the constraint's own.

**A version used as an EXAMPLE must not be the current version.** Examples name a version devbin is not, and `documentation.bats` catches a regression.

**The views cannot be hand-edited.** `bin/devbin release check` regenerates into a temporary and compares, and the suite runs it against this repository, so a hand-edited `CHANGELOG.md` or a note added without regenerating goes red. `bin/devbin release notes` regenerates them; the cut does it for the release's own note.

**The release object depends on GitHub Actions starting a job.** `release.yml` refuses a tag whose version is not `VERSION`, a missing or empty note, or stale views, and publishes the note's body. If Actions does not start the jobs -- a spending limit, eg, stops them before they start -- the tag and the pushes stand and the object step fails at `object_wait`. Once Actions runs again, re-run the release workflow's run for that tag (`gh run rerun <run-id>`), since the tag is already pushed and nothing else triggers it, then re-run the same command.

**A job GitHub refused to start printed nothing, and only the run's ANNOTATIONS say why.** It does not read as a refusal from the run list: every test job is green and the summary alone is red after about three seconds, which reads exactly like a flaky gate. `gh run view <run-id>` prints the annotation that names the cause, and annotations outlive the job logs, so a run whose logs have expired can still be diagnosed.
