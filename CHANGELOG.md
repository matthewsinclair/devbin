## [0.1.19] - 2026-11-02

### Added

- **`release gates` runs a project's `release.gates` under one seal for HEAD, and a sealed green stands.** Run again over a sealed green for HEAD on this platform, it prints the gates row and runs nothing, at exit 0, and `--rerun` runs the gates regardless. It refuses a tree that is not one clean commit before anything runs, and `gates` joins `release.verbs`' default. A cut's gates read the same record: over a sealed green for the release commit on this platform they read `already` and run nothing.
- **The built-in `ci-state` reads CI's verdict on a commit in the release core's own words.** `bin/devbin ci-state <sha>` prints `<verdict><TAB><detail>` from the runs of `release.ci.workflow` (default `tests.yml`), the verdict green, failed, pending, none or unknown. With `release.ci.summary` declared, a run's verdict is that job's. A failed verdict names the run's failed jobs. `ci-state --fires <ref> <sha> [<path>...]` answers whether a push of the branch `<ref>` starts the workflow, read as committed at `<sha>`: fires, quiet, missing or unknown, with the reason. Both keys are read only when `release.ci.query` is the built-in, `bin/devbin ci-state`.
- **`bin/devbin cache` keeps a machine's built artefacts under a key made from the inputs they read, so a build whose inputs did not change pulls what it built before.** A project declares a `build:` block: `build.inputs`, and `build.artefacts.<name>` with its `tool`, `path` and `inputs`. `key`, `get`, `put`, `list`, `rm` and `gc` work on the registry at `DEVBIN_CACHE_HOME`, or at the XDG cache directory's `devbin` when that is unset. A project's own build handler calls `get` before it builds and `put` after; the core's `build` command does not change. An input with uncommitted or untracked changes has no key, so a dirty build runs and records nothing. Whatever a verb cannot do is a refusal at exit 7. `doctor` names the root and whether it can be written.
- **An option declares the platforms it runs on with `platforms:` under `commands.<cmd>.options.<opt>`, the words `macos` and `linux`.** On a host its list leaves out, the option is inactive, never failed. `all` counts it, `help --why` names it with its reason, and an option run by name is refused with that reason. `doctor` refuses a value outside the words. Until that is fixed, the command you run reads such a list as absent, and the option runs everywhere.
- **`DEVBIN_TEST_JOBS=all` runs the suite on every CPU the machine has**, and is refused where nothing counts them. Half the CPUs, never fewer than two, stays the default.
- **Every sealed run records the commit it stood on and its clock.** Its log opens with `commit:`, `start:` and `host:`, and the close adds `commit at close:` and `end:`, so a record says which commit it proves and when.
- **`release.legs` runs a project's gates on other machines, each as a leg of the cut.** It lists ssh host aliases, and pre-flight reaches each before anything is stamped. A host that answers runs the gates at the release commit, sent to a bare repository on it, as the leg `legs.<host>`. Its seal pair is copied back under `tmp/release/legs/<host>/` and read as the local gates' pair is, so a green that stands for the release commit is `already`. The confirm names the release commit sent to each host. A host pre-flight cannot reach is named on its row, gets a `leg:` line of its own in the cut's log, and is never waited for. A host that answers and cannot be read as a leg refuses the cut, naming it, and so does a project name no host's repository can take. A start that fails, or does not answer, stops the cut at once. Every ssh and scp to a host is bounded, so a host gone silent never holds the loop past its deadline.

### Changed

#### a script or a config may get a different result

- **A cut asks its one yes before anything runs.** The order is resolve, pre-flight, confirm, stamp, commit, legs, tag, push, object, after. The question names the tag, the release commit the commit step makes, each remote's push, the candidate's push, the object, its assets and the `after:` commands, which run under the same yes. `--yes`, or a `y` at the prompt, sets `DEVBIN_RELEASE_CONFIRMED` for those commands. Once the release commit exists, the tag step reads every remote again, and a plan that differs from the one confirmed stops the cut before anything is tagged.
- **Every leg of a cut starts at once, one loop reads them all, and the tag is cut only once every leg is green.** The legs step takes the gates step's place. The candidate's push goes first, then the local gates run at the release commit in a process group of their own. The loop prints a clocked line each time a leg's word changes. A failed leg stops the cut at once, and `release.ci.wait`, counted from the loop's start, bounds every leg but the local gates. A stop leaves nothing tagged and nothing public, deletes the candidate, and writes each leg's line into the RELEASE seal.
- **A project's `ci.query` is asked about the candidate, never the tag.** A project's ci.query is now asked about the candidate, the release commit pushed to its candidate branch (release.publish.candidate, default candidate/{tag}), with DEVBIN_RELEASE_TAG set to that ref, never the tag. Under release.publish.url the candidate is the release commit's snapshot at the public repository. A query that read the tag's run must read the commit on that branch.
- **The candidate goes to the remote that pushes to the project's repository.** The remote a cut pushes its candidate to is judged by where a push to it goes: its push urls where it has any, else all its urls. It is the first that pushes to the project's repository on its own host, else the first that pushes to its OWNER/NAME on any host. Pre-flight refuses a cut where none does, and one where remotes push to that OWNER/NAME on more than one host and none on its own host.
- **The candidate is deleted once the tag is pushed, and at any stop.** A ref holding another commit is left and named. One that will not go is named with the command that deletes it, and the cut ends at exit 1 with the release standing.
- **A publishing cut makes its snapshot public itself.** Under `release.publish.url`, the cut makes the release commit's snapshot at the legs step and pushes it to the candidate branch at the url for CI. Once every leg is green, the push step fast-forwards the public branch and puts the tag at the snapshot, reading each back. A public tag at another commit, or a public branch that moved while CI ran, is refused by name, and nothing is forced. Pre-flight requires `ci.query`, the snapshot list, `release.repo` under an object, and no remote of the project naming the public repository.
- **The dry run runs no gate, and runs as the cut runs (issue `0304`).** Its gates row reads the record, already or would, and its legs row names the legs that would start. A failing read stops a dry run and the cut alike, FAILED at its own step.
- **A run a signal ends is sealed red, naming the signal (issue `0297`).** A gate's run catches INT, TERM and HUP while it runs. Once the run has ended, it is sealed red, with the signal named in its log and its seal, and the exit is 128 plus the signal's number.
- **`release status` reads the new shape.** Its confirm row comes second. Its legs row reads the local gates' record and names the candidate as a cut's to read. It has no ci, snapshot, candidate or publish row. Under `release.publish.url`, its push row reads the public repository.
- **The cut, `release status`, `release gates` and `macos app-sign` clear git's local variables once, at their start.** Each names any that were set and the repository used instead, so an inherited `GIT_DIR` never moves what they read or write.
- **`macos app-sign` signs at the release commit, and `publish` ships only a copy signed at the tag's commit.** Before the tag exists, app-sign takes HEAD as the release commit and records the commit it checked beside the stage. publish refuses a copy signed at another commit, and a stage with no record.
- **Where the built-in `macos` is enabled, the cut runs the macOS stage itself, as a leg beside the local gates.** `macos app-sign`, then `macos app-notarize`, run at the release commit in a process group of their own, under a seal of their own, `tmp/release/<stamp>.MACOS.{out,errors}`, so a green that stands for the release commit is `already`. A run that fails, or whose record does not read green, fails the leg, naming why, and a stop stops the stage with the local gates. The confirm names the app's submission to Apple's notary service, and pre-flight refuses the stage on a host whose platform word is not `macos`. The stage and the local gates run at once in one tree, so `macos.build`'s products and the artefact's path must be ignored by git.
- **The macOS stage takes its app from the artefact cache.** Where `macos.build` is declared and an entry of the `build:` block has `macos.app`'s path, `app-sign` pulls the app from the cache at the release commit and runs no `macos.build`, or builds it and puts it there. Two such entries are refused at config read, naming both, and `doctor` notes a stage with none, which builds its app uncached. Once every leg is green, the cut writes the artefact's `cache<TAB><artefact><TAB><key>` line into the RELEASE seal, which `cache gc` keeps, and prints it.
- **Pre-flight refuses a `RUNLOG_KEEP_RUNS` value the gates' purge would refuse**, before anything is stamped.
- **`release attach` reads the assets run CI made for the release commit on the candidate's branch or at the tag, and never another branch's.** It lists the assets workflow's runs by the release commit's sha and keeps those on the candidate's branch or at the tag, so a run of the same commit on the branch the push step pushes is never shipped. The earliest success among them ships, as before. A standalone `release attach` names the candidate as the cut would, and refuses a tag the repository does not have. Under `release.publish.url` it reads the run on the commit the public tag names, as the cut's own attach does, which did not work in the publish shape before.
- **A cut has a candidate leg unless its project opts out: `release.ci.query` defaults to the built-in `bin/devbin ci-state`, and `ci.query: -` opts out.** The cut's pre-flight asks `ci-state --fires` whether a push of the candidate's branch starts the test workflow, `release.ci.workflow` (default `tests.yml`), with the files the release commit changes, and refuses the cut unless it does, naming the reason and the three ways out: fix the workflow's push trigger, declare `ci.query: -`, or declare a query of the project's own, which reads its own trigger and is not asked. `release check` asks the same where the cut is offered, and a publishing cut asks again once it has made the snapshot, refusing, before anything is pushed, one whose workflow is not the release commit's. `release.ci.wait` defaults to 60m.
- **An adopting project makes its test workflow start on a push of the candidate's branch, or opts out.** Add `candidate/**` to the workflow's `on: push: branches:` (the candidate is `candidate/{tag}` unless `release.publish.candidate` says otherwise), with any `paths:` filter met by the files the release commit changes. Or declare `release.ci.query: -` to cut with no candidate, and drop `ci.workflow`, `ci.summary` and `publish.candidate`, which are then refused, and `ci.wait` unless a host in `release.legs` or a macOS stage reads it. A project with a query of its own keeps it, and declares no `ci.workflow` or `ci.summary` beside it.
- **Config validation refuses a `release.tag` that git would not take as a tag name, once filled, and a `release.snapshot.message` that holds a skip marker** such as `[skip ci]`, in any case of its letters, its default template included, since a push of such a snapshot starts no run of CI.
- **Pre-flight refuses a gate in `all` whose option's `platforms:` hold it back on every leg the cut will run**, naming the gate, the option, its platforms and each leg's platform word, with a host absent at pre-flight named as not counted.

### Removed

- **`release publish` and `--expect` are retired.** release publish and --expect are retired, since a cut under release.publish.url makes its snapshot public itself, and release status reads the public repository on its push row.
- **A bespoke post-cut script that calls `release publish` breaks.** `release publish` is now refused before anything acts, naming the cut that publishes. `release snapshot` stays. `publish` leaves `release.verbs`' default, and a declared `publish` verb is refused, naming what replaced it.
- **The ci step, `release.ci.tag` and `release.ci.base` are retired.** CI is read on the candidate before the tag, never after it. Both keys are refused as unknown keys, with a clause saying what replaced them, so drop them from a project's config. `release.ci.wait` is now the legs loop's deadline.
- **A cut's snapshot, candidate and publish rows and steps are gone, and so are the `not reached` and `not read` row states.**

### Fixed

#### reaches every project

- **A red run's seal is never read green while its red text is written (issue `0306`).** The red text is staged beside the seal and renamed over it. Until the rename, the seal holds its in-flight marker, which no reader takes for green.
- **The release commit is read through the repository first, then the tag's existence, then the commit the tag names.** A tag that names no commit, or one whose object the repository lacks, now stops the cut, `release status` and `macos` with git's own words, rather than naming HEAD as the release commit.
- **A tree with an untracked file reads dirty whatever `status.showUntrackedFiles` says**, as the cut's tree rule already refused it, so a seal never names a commit whose bytes the tree was not.
- **`release.repo` read off a remote's url takes git's `host:/OWNER/NAME` form, as every other form is taken.**
- **`formula render` and `formula publish` read the cut's release repository (issue `0296`).** With `remotes:` declared and no `release.repo`, render read the sums from origin's repository, and publish named its default tap under origin's owner, while the cut read the first declared remote's. Every reader of the release repository is now the cut's: `release.repo`, else the first declared remote's, else origin's or the only remote's.

#### devbin's own tree

- **CI runs devbin's suite on every CPU its runner has**, with `DEVBIN_TEST_JOBS: all` on Ubuntu, macOS and WSL.
- **A test fixture project carries its own git identity (issue `0300`)**, so the release commit a cut makes there reads the same on every host, a host with no domain included.
- **No tag starts a run of devbin's tests workflow, and its Candidate verdict job is gone**, so a release's CI is its candidate's run, read before anything is public. `release.yml` keeps its tag trigger, since it makes the release object. A project that copies `tests.yml` and whose cut has no candidate keeps a tag filter there.
- **The infra-check test that runs with no `dig` on PATH passes on a runner whose `/usr/bin` holds a dangling link (issue `0317`)**, as GitHub's Ubuntu runner does. The PATH it builds skips a name it has already linked by asking `-L`, which a dangling link answers, where `-e` followed the link and linked the name again on its pass through `/bin`.

## [0.1.17] - 2026-10-29

### Changed

#### a script or a config may get a different result

- **doctor prints the version line unchanged, on a line of its own, as `--version` prints it (issue `0246`).** In devbin's own checkout it is doctor's first line, and the tree row says whether it names the checkout's commit. In a project, the install's line is printed alone, with what named that install on a detail row beneath it.
- **With no link left, a bare `use` and doctor's switch row report brew only when the first `devbin` on PATH is Homebrew's (issue `0273`)**, and otherwise fail, naming the copy that answers, or saying that none does.
- **`use dev` and `use opt` on a shadowed link leave it pointed, say so, and exit 1 (issue `0275`)**, naming what shadows it, with the remedy: fix PATH as that says, or run `use brew`.
- **The remedy for a machine with no Homebrew devbin is keyed by its cause, and said once (issue `0250`):** export `HOMEBREW_PREFIX` when it is unset or relative, install devbin with Homebrew under an absolute prefix that holds none, and `use dev` or `use opt` only from a dev or opt tree.
- **Where the commits cannot say which way an upgrade moves, the versions do (issue `0276`).** A source at a higher version reads as forward, a lower one as BEHIND, and equal versions still cannot tell. upgrade's direction lines name both versions where both read.
- **`version set` refuses an immutable file before it writes anything (issue `0279`):** `uchg` or `schg` on macOS, `i` on Linux, read in each platform's own spelling, so an immutable `Cargo.toml` sidecar no longer leaves the set half-written. Where the machine has no reader for the flag, the preflight says the file was not checked for it.
- **An install whose manifest cannot be read is refused naming the manifest (issue `0282`)**, never told to run `install`, which would make it a project.
- **`version check` words an empty sidecar in the one table's words, `holds nothing (expected <version>)` (issue `0289`)**, as `show` and `doctor` do.
- **`worktrees` reads every patch a bank carries (issue `0290`)**, so a staged diff matching a bank's second patch is matched to that bank, and the banks line counts the patches and names each bank that carries more than one.

## [0.1.16] - 2026-10-29

### Added

#### new commands, checks and routes

- **`release snapshot` makes a release's public snapshot, one deterministic commit over the list of what ships (issue `0239`).** `release snapshot <vX.Y.Z> <new-dir> [--no-parent]`, or `--commit <rev>` for an audit ahead of a cut, builds a commit holding exactly the files `release.snapshot.list` selects from the tag's tree, in a new repository outside the project, by git plumbing alone. Its author and committer are `release.snapshot.author`, its dates the source commit's at +0000, its message `release.snapshot.message`, and it is never signed, so the same release always makes the same sha. It is made on the tip of the publish branch, fetched first and refused unless every commit behind it is such a snapshot, made by the same identity; a first snapshot is made with `--no-parent`. A `release.publish.url` naming the repository one of the project's own remotes names is refused before anything is fetched. Every git call runs with git's local variables cleared and its hooks off.
- **`release publish` makes a release public through CI on the snapshot itself (issue `0240`).** `release publish <vX.Y.Z> [--expect <sha>] [--dry-run] [--yes]` builds the tag's snapshot, pushes it to `candidate/<tag>` on `release.publish.url`, waits for `ci.query` to read green on that sha, then fast-forwards the publish branch, pushes a lightweight tag, reads each back and deletes the candidate. Nothing is ever forced. `--expect` takes the whole sha an audit approved and refuses any other. A publish stopped part-way, or run again once finished, finds what is already public and carries on from there, and an older release run again after a later one is published is refused as public already.
- **`worktrees` reports each linked worktree as landed, held or unknown, with its evidence, and `worktrees remove-landed` removes the landed ones it is named (issue `0245`).** The report reads, for each worktree, its HEAD against `worktrees.branch` (default `main`), its own commits by patch-id, its staged and unstaged changes by patch-id and by content, against the branch and any bank refs `worktrees.banks` names, its untracked files and linked build targets, stash entries naming it, processes standing in it, and its lock. Plain directories beside the worktrees are listed with their size. `remove-landed` reads each named worktree again and refuses the main worktree, one gone, locked or stood in, the one the run itself runs from, and anything not landed; it runs a plain `git worktree remove`, never `--force`, and reports git's refusal as a finding. `--repo` reads another repository, report only. Every read is read-only, each worktree's index through a scratch copy.
- **`macos` signs an app that versions apart from its project, and checks the build it signs (issue `0243`).** `macos.version_from` names the file the app's own version is read from; an app that versions apart declares `macos.commit_stamp`, the Info.plist key its build writes its commit into, and `macos.kind_stamp` and `macos.kind_value` check the build's kind. Each is checked against the tag at `app-sign` and again at `publish`. A path key may open with `~`, `$HOME` or an XDG base-directory variable; any other leading form is refused, naming the key. Every copy `macos` makes has its Launch Services record dropped on every path out, interrupts included, and the record list is read back; after the upload, `publish` drops the records under `macos.build_root`, refusing a root that would sweep the home directory or an applications folder.

### Changed

#### a script or a config may get a different result

- **A project that declares `release.publish.url` cuts to `release.remotes` alone, and stops after its push (issue `0240`).** A remote it would push to that names the publish repository is refused at pre-flight, so a cut never pushes the workroom's history to the public repository; the snapshot, candidate and publish rows wait on `release publish`. Without `publish.url` a cut runs as before. Under `publish.url` the formula's revision is the public tag's commit, and the formula template's url is https. CI runs on `candidate/**` pushes, the macOS and WSL legs included, as on a tag.
- **A built-in the project does not offer answers `--help` and `-h` as `help <cmd>` does, and running it names that page (issues `0255`, `0271`).** `help <cmd>` prints devbin's page for a built-in this project does not offer, at exit 0, under a line saying why it is not offered and what would offer it, where it refused as if the command did not exist. `<cmd> --help` and `<cmd> -h`, in any position, answer the same way and read none of the other arguments, and the refusal of a run ends `(its page: bin/devbin help <cmd>)`. A command devbin does not ship is still refused, at exit 2.
- **From a machine install, help answers, and `devbin devbin` says what an install is (issue `0251`).** A bare `devbin`, `-h`, `--help`, `help` and `devbin devbin` were refused at exit 5 outside a project, so nobody could read how to seed one before seeding it. The upgrade remedy names `--from` only where the machine does not already name the install.
- **On macOS a brewed devbin runs from a PATH without Homebrew's bin, as cron or a GUI-started hook has (issues `0253`, `0266`).** The keg's `bin/devbin` is a script that puts the formula's bash first on PATH, so macOS's bash 3.2 never refuses it, and every path devbin prints for a keg names that `bin/devbin` through Homebrew's opt link, never the launcher inside the keg. The bash floor's refusal names a bash 5 the machine has, and tells only a machine with none to install one. `use brew` reads the keg's `bin/devbin` as Homebrew's whether it is a link or that script.
- **A brew install carries devbin's guides beside its README, and every message naming a guide names its path on this machine (issue `0254`).** The formula installs `docs/`, `RELEASES/` and `RELEASES.md` in the keg. `devbin devbin` and `release --help` name the guides where they are: in a checkout, in a keg, or, for a project, in the install its upgrades read; an opt install says it carries none.
- **The version line's sha field is always twelve hex digits, then `+dirty`, or `unknown` (issue `0244`).** A recorded commit of seven to eleven digits printed short, and a 64-digit one printed its first twelve and then its digits from the 41st on; one of fewer than twelve now prints `unknown`.
- **`install --into` refuses a target that is not a directory, saying what is there, and an empty `--into` is refused by name (issues `0258`, `0268`).** A file, a link to nothing and a quoted `~` are named as what they are, and a path with nothing at it gets a `mkdir -p` line to paste. `--into ""` read as no `--into`, and vendored a machine install into the current directory at exit 0.
- **infra's machine-wide profile follows `XDG_CONFIG_HOME` (issue `0272`):** `$XDG_CONFIG_HOME/devbin/infra.yaml` when that is absolute, `~/.config/devbin/infra.yaml` otherwise.
- **devbin finds PlistBuddy on PATH first, then at macOS's own `/usr/libexec/PlistBuddy` (issue `0264`)**, as it finds every other tool it runs.
- **The exit-code contract is stated once, in `docs/authoring-commands.md` (issue `0241`)**, which now lists exit 6 and why a new refusal takes a new code.

### Fixed

#### reaches every project

- **A version that does not read is never passed on as one (issue `0259`).** With no version file, `version show` printed `unknown` at exit 0 and `version check` passed. Now `show`, `check`, `bump` and `sync` refuse, naming the file, the key that names it and a remedy, `doctor` notes it, `version set 0.1.0` starts a missing bare version file, and a release cut refuses at pre-flight.
- **`version set` refuses, before it writes anything, every file its write could not change (issue `0260`)**, so a file with no version devbin reads, or one it cannot write, no longer leaves the files before it at the new version. A sidecar devbin cannot read is refused, never taken as empty and overwritten.
- **Each structured recipe rewrites the one line devbin reads the version from, and no other (issue `0263`).** `version set` rewrote every version-shaped line of a `Cargo.toml`, a dependency table's included, and a nested `"version"` in a `package.json` and a second `version:` in a `mix.exs` alike. A manifest that gives its version another way, such as `version.workspace = true`, is refused.
- **`set`, `bump` and `sync` read every file back after writing it, and refuse unless each reads the version written (issue `0264`).** PlistBuddy exits 0 when it cannot write, so a plist could stay at the old version while `set` exited 0.
- **One classifier says what stands at a version file or a sidecar, and one table words each state, for `set`, `check`, `show` and `doctor` alike (issue `0265`).** `check` no longer prescribes for a missing sidecar the `sync` that refuses it.

## [0.1.13] - 2026-10-24

### Added

#### new commands, checks and routes

- **`release attach vX.Y.Z` puts a project's CI-built assets on the tag's release, with one `SHA256SUMS` over every asset (ST0008 WP-08).** A project declares `release.assets.workflow`, the workflow file whose run at the tag builds its packages, and may bound the wait with `release.assets.wait` (default `30m`). Both are read under `object: local` only and refused under `ci` and `none`, as `title` is, since under `ci` the workflow writes the object and an attach would be its second writer. The attach reads each stage's result before it acts, so running it again continues where the last run stopped. Its own result comes first: once `SHA256SUMS` agrees with every other asset on the release, the attach reads no run and writes nothing, so a finished release stays `already` after the run's artifacts expire. The release object must already exist; the attach makes none. It uses the earliest successful run of that workflow at the tag, matched by the tag's name and its commit, and names the run. Builds of one commit are not byte-identical, so a later run never changes what ships. While no run is listed, or the run is queued or in progress, it waits within `assets.wait`; a run that failed, or no run by then, is FAILED, with the cause read from the run's jobs and the remedy named (`gh workflow run <file> --ref <tag>`, or `gh run rerun <id>`, then the attach again). The attach never starts a run. Every file in every artifact of that run is an asset, hashed from the downloaded bytes. Zero files, a name given twice or a file named `SHA256SUMS` is refused. An asset missing from the release is uploaded, one present with the same sha256 is `already`, and one present with a different sha256 is refused, never replaced. `SHA256SUMS` lists every asset on the release, the ones it did not upload included, in `sha256sum -c` format sorted by name, from bytes the attach downloaded and hashed itself; it is written last, and it is the only asset the attach replaces, only when its content differs. Each uploaded asset's digest as GitHub reports it must equal the local sha256. Under devbin's own cut, step 9 runs the same attach once the object is made, and `release status`'s row 9 reads it.

## [0.1.8] - 2026-09-26

### Changed

#### a script or a config may get a different result

- **A bare `bin/devbin shell-init` exits 1, not 2, and prints its usage on stderr (issue `0119`).** Naming no shell is a usage error, and 2 is the code the contract keeps for an unknown or inactive command, which `shell-init` is not. The usage moved to stderr because a shell rc evals this command's stdout and the usage carries runnable examples, so an eval of the bare command now evaluates nothing. `-h` still prints the usage on stdout and exits 0.
- **`infra check` and `infra init` exit 1, not 2, when something could not be measured (issue `0126`).** In a project where infra is inactive, `bin/devbin infra check` also exits 2, so a caller could not tell "infra is not set up here" from "a DNS read failed". Drift and an unmeasured domain now both exit 1, and the report ranks them, printing COULD NOT MEASURE above any drift, so a script that told the two apart by the code must read the report. When this was measured, nothing in any consuming project read the 2: no workflow or script invokes infra, and the one infra user outside devbin documents only zero against non-zero.
- **`bin/devbin release` exits 1, not 2, when nobody is at a terminal to confirm and `--yes` was not given (issue `0130`).** 2 is the dispatcher's code for an unknown or inactive command, so a script could not tell a cut that stopped for want of a person from a release that is not enabled here. Exit 1 is what `fullcycle` and `clean` already do; step 6's row says which refusal it was, "declined at the prompt" or "nobody to ask". This supersedes the exit 2 of ST0007's AC-5.3.
- **`version set`, `version bump` and `version sync` are refused, exit 4, from outside the project they would write (issue `0124`).** The wrong-tree guard exempted `version` whatever followed it, so `<project>/bin/devbin version bump patch` typed in another directory rewrote that project's VERSION at exit 0, and `dvb`, which falls back to `$DEVBIN_SOURCE` when it finds no project, bumped whichever tree that names. Only the forms that write nothing are exempt now: `version` alone, `show`, `check` and its help, and `-v` and `--version`.
- **`infra` refuses a `$DEVBIN_INFRA_PROFILE` that names a missing file, and `infra profiles` refuses a profile that does not validate (issue `0121`).** A typo in the variable fell through to `<project root>/infra.yaml` and checked a different profile without a word, while the same file named with `--profile` was refused. `infra profiles` said it validated every profile and only loaded them, so one that `show` and `check` would refuse passed; it now prints what validation says under each file and stops at the first that fails. Three smaller fixes ride with it: a profile with no `name:` shows as `(unnamed)`, as the reference promises; `infra mail dmarc --help` calls `check` planned instead of offering a verb that does not exist; and `infra --help` names the reference where it really is, which was wrong in devbin's own checkout.
- **`db all` leaves `reset` out, and `MIX_ENV=prod` is refused before any `db` line runs, whoever supplies it (issue `0132`).** `db all` ran setup, migrate, reset and seed, then reported that all db options passed, and reset is `mix ecto.reset`, which drops the database. `reset` now ships outside `all`: `db reset` by name still runs, `in_all: true` on it brings it back, and every `db all` names it as skipped. - **`install --into <project> --force` removes the files devbin stopped shipping, edited or not, and names each one (issue `0129`).** It copied devbin's half back, deleted nothing, and dropped the retired file from the manifest, after which no `upgrade` could reach it: a retired `lib/cmd/<name>` handler went on answering its name. A re-vendor now retires each file the previous manifest recorded that the source no longer ships, including an edited one, since `--force` already copies over edits; a plain `upgrade` still hands an edited file back to the project instead. A file no manifest recorded is left in place, since it may be the project's own, and nothing outside `bin/.devbin/lib/` is touched.
- **Whether a project owns a command is decided in one place, and `all` is refused over a command-level `run:` with no option to run (issue `0128`).** A `run:` line now owns its command as a handler does, so `clean all` no longer runs devbin's own removal where `commands.clean.run` replaced it. `all` sweeps where there are options, is handed to `server`, `iex`, `cli` and `repl` and to a project handler with no declared options, and over a `run:` with no option to run is refused at exit 1, naming the bare command: handed `all`, `commands.test.run: cargo test` ran no test and exited 0 over a failing suite. The same holds when `all` or an option name follows devbin's gate flags, as in `test --purge all`. `--iex` no longer counts over a `run:` line unless `options.iex.commands` names it, and `help --why`, `doctor` and `check format` read the same answer the dispatcher acts on. - **A file that is a symbolic link is written through, and the link survives (issue `0084`).** Every writer that replaces a file through a temporary renamed the temporary over the path it was given, so a link became a regular file holding the edit, the file it named kept its old content, and the command exited 0. `version set` wrote a linked `VERSION` through its link and left a linked `Cargo.toml`, `package.json` or `mix.exs` target at the old version, after which `version check` agreed with the copies; `release notes`, dating a note, `generated_doc_write` and `fleet doc` did the same to a linked view, note or document, and `fleet doc`, which staged its document in TMPDIR, also left that document 0600 on every run. A link that leads to no file, dangling or in a loop, is refused naming it. Writing through a link to a file in a directory that cannot be written is refused, naming that file, where it replaced the link with a regular file at exit 0. - **Every `run:` word is a glob pattern, devbin says so, and a `run:` with no words in it is refused naming its key (issue `0082`).** A declared command line was expanded unquoted at eight sites -- an option's `run:` bare and under a gate, a command's exec'd and under a gate, `commands.fullcycle.restore`, `release.notes.run`, and the two that run devbin's own catalogue lines -- so how a command line becomes words was stated eight times, each reading the caller's `IFS` and whatever glob options the process happened to have. Since `0082` the argv holds the RESULT of the glob matching, which means the declared line could not be recovered by reading it either. The one that already named its source was an option's `run:`; a command's `run:`, the catalogue's own command line, a catalogue option implemented by a devbin function, `fullcycle` and devbin's own test handler all said nothing. Each now names what it is: a config key in the same sentence for the two declared sites, the catalogue row for the catalogue's line, and the function for the three that run devbin's own code, where there is no command line to go looking for. **The comment above the command-level gate asserted that it "seals on exactly the terms an option-level one does"** and it did not; `0082` had widened the difference by making the one source line that existed say more. A test compares the two seals with their keys removed, and another holds every `run_gate` call in `lib/` and `bin/` to carrying a source -- which is what found the sixth site, a project handler the census had read past.
- **A replace of a read-only file no longer stops dead on a terminal prompt, so `test all` from a terminal finishes (issue `0086`).** `rename_staged` renamed its temporary over the file with a bare `mv`, and POSIX `mv` prompts when the destination exists, permissions do not allow writing it, and standard input is a tty -- which is exactly a replace of a read-only file, the case `stage_beside` goes to the most trouble to support. `bin/devbin test all` run from a terminal reached the arm that replaces a `chmod 444` file, printed nothing further, and waited **8h13m** until it was interrupted. `mv` is now `mv -f`, as `lib/install` already wrote for its own rename; those are the only two `mv` calls in the runtime. **The reach is wider than the suite**: `replace_file` and `sed_inplace` are how devbin rewrites a file whose mode it does not own -- the version stamp, a dated note, a generated view, the `fleet` census document -- so any of those replacing a read-only file from a terminal blocked the same way. **Why it was never seen: the prompt is tty-gated and nothing that normally runs the suite has a tty**, so every agent run and both CI jobs passed, including the run that reported 1372 ok. A test holds the runtime's `mv` lines to exactly those two, byte for byte: any other line naming `mv` in `lib/` or `bin/` fails it, and so does either known line disappearing. It is an allowlist because two rules about flags were each beaten by spellings they did not read (a second `mv` after `;`, an `-i` on a continuation line, a quoted `'-n'`). **The limit, declared:** the arm reads text, because a bats run has no tty and so no arm here can watch the prompt appear. It cannot see an `mv` behind a variable, an alias or a function of another name, or one spelled so its text does not read `mv`, and it does not scan `tests/`, where nineteen bare `mv` calls each move a file the test just created and can write. A test that moved over a read-only fixture would hang the suite identically and the arm would not see it.
- **`--purge`, `--purge-only` and `--allow-empty` work at a command-level gate, and are no longer handed to the tool as arguments (issue `0087`).** A command with its own `run:` and `log:` is a sealed gate like an option, but it forwarded its argv whole: `devbin <cmd> --purge` ran the tool with `--purge` on its command line and purged nothing, and `--allow-empty` -- the per-invocation "this emptiness is intended" override -- reached the tool instead of the gate, so the gate still failed. No warning either way. The option-level and catalogue gates already split these flags out through one parser, whose own comment said it served "both" gate sites; the command-level gate was a third, added later. It now takes the same path, and the sites are held by an arm that refuses any gate forwarding a raw argv rather than by a comment that counts them.
- **`fullcycle` asks a person at a terminal before it removes the build trees: once, after showing what goes (issue `0089`).** Without `--force` it refused with `no tty` every time, at a terminal too. Each phase got the rest of the phase list on its stdin, and since `0088` a phase's own gate reports that nobody is there. It now shows what the clean phase would remove, asks on the terminal, and on a y runs the cycle. An n stops it before anything is removed. With nobody to ask it refuses and says to pass `--force`. `clean` and `fullcycle` ask through one helper, so the rule for whether a person is there is written once. ## [0.1.1] - 2026-09-16

### Added

- **`infra`: an estate's DNS and mail configuration, declared in a profile and checked against the live records** (ST0003). `infra check` reads authoritative nameservers only -- a recursive resolver reports the remaining TTL, not the configured one -- and sorts every assertion into four channels: ok, drift, COULD NOT MEASURE, and blind spot. It exits 2 when anything could not be measured, ahead of 1 for drift, because an unmeasured domain is what a scripted caller would count as covered. With no vendor table, `mail:` is checked for consistency across the estate, and an estate of one domain is reported as a blind spot rather than a pass. `infra profiles <dir>` checks that no domain is claimed by two profiles. `infra init` measures live domains and prints a profile to start from: a value reaches the target only through the RFC layer or a strict majority of the estate above two domains, and everything else goes to `unreviewed:`, which `check` refuses to run past. A domain naming a sender must describe its SPF and DKIM pair, and a profile that does not is refused when it is parsed. The schema is `lib/infra.reference.yaml`.
- **`infra mail dmarc parse` and `report`: DMARC aggregate reports, read in the containers reporters actually send.** Measured on 17 real reports from three reporters, none arrived as bare XML, so `parse` reads `.zip` and `.xml.gz` and decides the kind from the file's bytes, never its name. A zip that does not hold exactly one member is refused. `parse` takes a directory and accounts for every file on stderr -- parsed, not a report, or FAILED -- keeping stdout as JSON Lines, and an empty directory is an error. `report` summarises them; over those 17 reports the pipeline surfaced 10 records carrying no DKIM result at all, which is the forgery signature the subsystem exists to find.
- **`dormancy`: how many tests a Rust project does not run.** It runs the declared suite and the same suite with `--all-features`, and reports the difference, since tests behind a feature the declared invocation never enables compile, sit in the tree and are never reported. It is a verb rather than a `check` arm because it costs two full builds.
- **`fleet upgrade`: the sweep of every consuming project, dry-run by default.** It distributes the machine install's bytes to every project that vendors devbin and needs `--apply` to write. A project counts as `level` only when its recorded provenance matches the install, and an upgrade that holds back an edited or released file is reported by name, counted as `HELD BACK` and exits 1 (issue `0074`, and the `0069` entry below).
- **`clean --dry-run`** (issue `0042`). The scan used to be reachable only through the confirmation prompt, so in CI, a script or cron the only two outcomes were refusing and deleting.
- **The run log names the machine that produced it** (issue `0052`). A seal was a true record of one OS's run and said nothing about which, so a local `824 tests, 0 failures` read as a fact about devbin while CI was red on Ubuntu. Every sealed log now carries a `platform:` line, and run-log stamps read UTC (issue `0055`).
- **`--version` names the bytes it is running.** On a dirty tree the commit alone names no bytes, which is exactly when an identity matters, so the line also carries a digest of the runtime: `devbin 0.1.1 (<sha> +dirty, runtime <digest>)`.
- **An unreleased release note.** `CHANGELOG.md` and `RELEASES.md` render `Unreleased` in place of a date, per Keep a Changelog, so an open series can accumulate notes without either view claiming it shipped. An unreleased note carrying a `date:` is **refused rather than ignored** -- an ignored date survives the flip to `released` and ships as a claim nobody re-checked.

### Changed

- **`status:` in a release note is now read, and required.** It was written into the 0.1.0 note and consumed by nothing for the whole of that release -- a field that looked like a control and controlled nothing. It is now `released` or `unreleased`, and **absent is an error rather than a default**: defaulting it would rebuild the same hole one layer down, since a note that meant `unreleased` and forgot the field is exactly the mistake the field exists to catch.
- **`install.prefix` has NO DEFAULT, and publishing refuses without it.** `lib/install` carried `$HOME/Devel/opt/devbin` as the fallback -- one operator's directory layout, written into the runtime that fourteen projects vendor. Every consumer carried it, and a publish from any of them would have gone to a path named after somebody else's home directory and **would have succeeded**, because a publish to the wrong place is indistinguishable from a publish to the right one. devbin's rule already said the location is configuration; a default does not soften that rule, it relocates the decision from a key somebody wrote to the absence of one. `install`, `upgrade` and `fleet upgrade` now refuse by name through one shared message, and `--prefix <dir>` supplies it for a single run. It is the same rule `fleet` follows, which removed a hardcoded machine root for the same reason.
- **`shell-init` no longer emits a path invented from `$HOME`.** A consumer project has no reason to know where the machine install lives, so `dvb` generated there now carries no machine-install fallback rather than one aimed at a directory named after somebody else. Removing the default made the empty case reachable, which exposed a second defect: an unguarded `-x $prefix/bin/devbin` with an empty prefix tests `/bin/devbin` -- a real path on the system PATH that the function would have RUN. Guarded, and the message now says the prefix is unconfigured instead of naming a location it does not have. The bootstrap example in its usage named one machine's checkout; it names `/path/to/devbin`.
- **`docs/infrastructure.md` is deleted.** Half of it was one project's vendor snapshot -- MX forms, SPF includes, DMARC phases -- carried in a tool other projects vendor, which is the rule above applied to documentation. The machinery half survives in two places that reach a reader: the schema at `lib/infra.reference.yaml` (vendored) and the command's argument at `bin/.devbin/help/infra.md`. **The guard moved with it rather than being retired quietly**: the old arm read `[ -f "$doc" ] || skip`, so deleting the document would have made a guard stop guarding with nothing reporting the change. ST0003's design records the one thing this costs -- `infra init`'s STANDARD proposal source now has no home, and WP-03 carries that as an open dependency rather than inheriting a broken pointer.

Suppressed at the function with the rationale, matching what `release`'s renderers already do. `check all` is rc 0 again.

Installing from the install is the only route that gets bytes and provenance both right, and it was the blocked one. `install` is now exempt, matching the exemption the wrong-tree guard has always had for the same verb.

Installing from the machine install into the development checkout has a different source and an identical consequence -- and while testing the exemption above it happened: `bin/.devbin/lib/` and a manifest landed in devbin's own tree, where a vendored copy sits ahead of `lib/` in the dispatcher's search order and every edit stops taking effect with the suite still green against the copy. **A first attempt at this guard required `--into` instead and was wrong**: `--into` defaults to the cwd, and that default is correct for the documented `DEVBIN_SOURCE` bootstrap, which runs `install` from inside the new project on purpose. Inheritance is the rule -- a `fullcycle` is one run, witness or not -- except at a witness boundary, where sharing the parent's id made `grep -l "run: <id>"` count a gate's nested witness runs as that gate. `DEVBIN_RUN_WITNESS` carries whether the parent was a witness, because the flag alone cannot tell. **Declared limit:** inside a witness run, a child started as a witness on purpose cannot be told from one that inherited the flag, so it is part of that run, its id and its ledger rows alike.
- **`fleet upgrade --apply` counted a project whose upgrade held back edited files as upgraded (issue `0074`).** The sweep discarded each project's upgrade output and judged it by exit code and recorded provenance, and an upgrade that skips a file edited in place exits 0 and still stamps the new commit. In the 0069 sweep that read `16 upgraded ... 0 FAILED` while one project had kept two patched files. **Every pass of each project's upgrade is now read**: a project with `skipped` or `released` files is reported in its own table with the files named, left out of the upgraded count, and counted as `HELD BACK` on the summary line, and the sweep exits 1, because a held project is not level. Every pass, because a `released` file leaves the manifest on the pass that releases it and a second pass never mentions it. Each kind gets its own remedy -- `--force` replaces an edited file and cannot reach a released one -- and when a pass counts more skipped files than it names, the difference is reported. A FAILED project now says how it failed (the upgrade's exit code, provenance that did not converge, or no scratch file to read the output into) and keeps its held files; a `skipped` or `released` line in wording the sweep does not recognise is reported as unrecognised rather than counted as named, where every FAILED row used to say the provenance had not converged.
- **Publishing the machine install named a `fleet` command that refuses to run (issue `0073`).** `install` and `upgrade` in devbin's own tree ended with `bin/devbin fleet upgrade --dry-run`, and `fleet upgrade` has no `--dry-run`: its dry run is the default, so the line died with `unknown argument '--dry-run'` at the moment the projects were behind. Both now print `bin/devbin fleet upgrade` from one helper, and the tests run the printed line through the real `fleet` parser rather than comparing strings.
- **`version check` said every sidecar agreed when there were none to agree** (issue `0061`). Zero sidecars and two agreeing ones printed byte-identical output at rc 0. It now names the count, and still exits 0 at zero, because most projects correctly declare no sidecar.
- **A refusal for an undeclared language named neither list it read nor the file it lives in** (issue `0062`). `project.languages` in `bin/.devbin/config.yaml` scopes devbin's gates, and Intent's language list is a separate fact by design, so "does not declare the 'rust' language" sent Utilz to change a correct declaration. Both refusals now say `in project.languages (<file>)`, and the option-level one checks that the language really is undeclared before saying so. `doctor` states which languages arm the built-ins and notes when none do.
- **A project could not decline the log wrapper** (issue `0065`). `log: "-"` sealed a gate named `-`. `-`, `false`, `no` and `0` now mean no seal, resolved once for both the option and the command path.
- **`check critic` was red for a week with a sentence blaming the runner** (issue `0075`). Intent 3.0.3 takes one path per `--files`, and the gate passed the whole corpus after one flag. It now passes one flag per path, and a runner that refuses the call is reported with its exit code and its own words.
- **`release notes --help` regenerated both views, and `release check --help` ran the check** (issue `0067`). The command read only its first argument, so asking a verb for help ran the verb, and a hand edit to `CHANGELOG.md` -- the state `check` exists to catch -- was silently discarded. `--help` in any position now prints usage, and a word after either verb is refused before anything is written.
- **`fullcycle` skipped a declared restore, without saying so, when the tests failed after a passing build** (issue `0070`). The restore was gated on the whole cycle passing, so the toolchain was left dark in exactly the projects that declared a restore to prevent it. It now runs after any build that passed since the clean. The failing phase's exit code stays the run's verdict: a failed restore or a dark link no longer overwrites it.
- **`infra profiles` and `infra mail` read a forgotten argument as success.** Both exited 0 with usage text when called with no argument. Asking for help still exits 0, and a missing argument is now a refusal.
- **The upgrade notice warned it would REVERT the runtime when the commits differed and the bytes did not** (issue `0053`), and **the `fullcycle` preview printed a weaker `clean` than the run executed** (issue `0054`).
### Found in a consuming project, and three of the four were real
- **The flagship profile example did not parse, and it was somewhere no consuming project could read it.** It used flow collections (`dmarc: { policy: none }`), flow sequences, and a `domains:` map keyed by FQDN rather than by handle -- three forms this parser rejects, in the first thing a new reader copies. It also named eleven real domains of a live estate. Fixed and genericised; then moved, because the deeper defect was its address: it lived in `docs/infrastructure.md`, and `docs/` is devbin's own repository. **The fourteen projects that RUN `infra` vendor `bin/devbin` and `lib/` and nothing else**, so the only documentation of the profile schema sat in the one tree where `infra` is never pointed at a real estate. It is now **`lib/infra.reference.yaml`**, vendored to `bin/.devbin/lib/infra.reference.yaml` in every project exactly as `config.reference.yaml` is, and **parsed by the suite on every run** -- the only assertion that cannot rot, since a test grepping for forbidden punctuation would pass the day somebody invented a fourth way to write it wrong. It is a profile outright, so there is no extraction step left to break.
- **Cross-profile domain uniqueness had no owner: `infra profiles <dir>`.** One-entry-per-domain was enforced WITHIN a file for a stated reason, and that reason does not stop at the file boundary -- an estate laid out as `profiles/<name>/infra.yaml` can have two profiles claiming one domain with the identical consequence and nothing reporting it. A directory holding no profiles is an **error**, not a clean report. An unparseable profile stops the comparison rather than being skipped, because a skipped profile is a domain that vanishes from the population and makes a real collision read as clean.
- **Recorded for WP-02, not built:** a DMARC store must key on `report_id`, not on the reporter's filename. Measured on real data -- two reports sharing reporter, domain AND window, differing only in `report_id`. A store keyed on `reporter!domain!begin!end` would overwrite one with the other and say nothing.

## [0.1.0] - 2026-09-01

### Added

- **A declarative dispatcher.** `bin/devbin` plus a vendored runtime under `bin/.devbin/lib/`, driven by a project-owned `bin/.devbin/config.yaml`. The commands a project offers follow from what it declares.
- **Built-in commands** -- `test`, `check`, `fmt`, `clean`, `build`, `version`, `docs`, `new`, and the surfaces (`server`, `iex`, `cli`, `repl`) -- scoped to the languages the project declares, so an Elixir project never sees `cargo` gates and a shell project never sees `mix`.
- **Sealed gates.** A gate's verdict is a **file**, not terminal output: `test all` writes `tmp/test/<stamp>.<SUFFIX>.{out,errors}` per option, and the `.errors` companion is empty exactly when a completed run was green. CI reads the file; a human reads the scroll.
- **A toolchain gate that reads the deploy image.** `check toolchain` proves the running versions match the `.tool-versions` pin and, where a Dockerfile builds the deploy image, that the image's pinned `ARG` versions agree with the same file. A project with a `fly.toml` and no Dockerfile fails rather than passes: a deploy nobody can check is a breach, not a gap.
- **A free `all`.** Any command with more than one option gets `all` synthesised from the option list, so adding an option puts it in `all` in the same edit.
- **Generated help.** `devbin help` is derived from what actually resolves, so it can neither list a command that does not exist nor omit one that does.
- **Project commands, first class.** An executable dropped in `bin/.devbin/cmd/` is registered with no config edit and no help edit. A project handler shadows a built-in of the same name, totally and by design, and `doctor` announces every such shadowing rather than leaving it silent.
- **`install`, `upgrade`, `vendor` and `doctor`.** Devbin vendors itself into a project; the devbin doing the installing is whatever you are running, so a fresh clone and an already-installed project seed the next one by the same path. `upgrade` re-syncs the vendored runtime, refuses to overwrite files the project has edited, and records what it refused. `vendor` compares the vendored runtime against the source it came from -- a different question from `doctor`'s tree-vs-manifest, and the two are deliberately not merged.
- **A checksum manifest** at `bin/.devbin/manifest.sha256`, checksummed against the TARGET rather than the source, so a copy that silently failed cannot verify clean. It carries the devbin version, the source path and the source commit.
- **`shell-init`**, emitting a shell function that finds the nearest `bin/devbin` by walking up from `$PWD`, with a `DEVBIN_SOURCE` fallback so the function can bootstrap a project that has no devbin yet.
- **`fleet`**, auditing every devbin install on the machine and generating a report of the installs from what it finds.
- **`fullcycle`** -- from a total clean: remove the cargo trees, rebuild, test. **Destructive by design and it says so.** It snapshots the PATH symlinks resolving into the tree *before* it removes anything, re-checks them after, and goes red naming any it darkened and did not restore. Read `## Known limitations` before relying on it.
